02 Part I: Language core · Chapter 2

Interfaces and methods

Introduce the Policy interface, add UCB1, and swap policies without touching the runner.

Starting point

Your own project as it stood at the end of Chapter 1. If yours has drifted, or you are skipping ahead, tools/start.sh ch01 work/banditlab copies the reference version into a new directory.

What you will build

A Policy interface that lets the simulation run any selection strategy, and a second strategy, UCB1, that plugs into it without changing a line of the runner. Along the way you will see how Go decides that a type satisfies an interface, why pointer versus value receivers matters the moment interfaces are involved, and how embedding lets two policies share bookkeeping.

The result: go run . -policy epsgreedy,ucb1 compares two policies on identical conditions in one table.

Concepts introduced

  • Interfaces and structural typing: no implements keyword
  • Method sets, and value vs. pointer receivers
  • Struct embedding and method promotion (composition, not inheritance)
  • Compile-time interface assertions
  • "Accept interfaces, return structs"
  • The factory-function-with-switch pattern

Step 1: the interface

Chapter 1's Run took a *EpsilonGreedy. To run something else, the runner needs to say what it needs from a policy rather than which type it is:

An interface is a set of method signatures. Any type that has those methods, with exactly those signatures, satisfies it automatically. Nothing in EpsilonGreedy's source mentions Policy, and nothing has to: the declaration of the interface and the declaration of a type that satisfies it can live in different packages that have never heard of each other.

Why Go does it this way

In Python you get this with duck typing (checked at runtime, if at all) or typing.Protocol (checked by an external tool). Java-style nominal interfaces check at compile time but force the implementer to name the interface, so the interface has to exist before the implementation. Go's structural interfaces are checked by the compiler and defined by the consumer. So Go code declares small interfaces next to the code that uses them: Policy lives in the package that runs simulations because that is the code that needs one. The standard library's io.Reader, one method long, is the model.

Step 2: share bookkeeping with embedding

Every policy so far needs per-arm pull counts and running means. Rather than copy that into UCB1, pull it into a small type:

Now EpsilonGreedy embeds it: a field with a type but no name.

The values slice is gone, replaced by armStats.means, so Select and greedy change only in that name. The Name method is new.

Embedding promotes the embedded type's fields and methods, so p.means, p.counts, and p.Update(arm, r) all work directly on an EpsilonGreedy. The policy no longer defines Update itself; it inherits the method from armStats.

It looks like inheritance, but it is composition: armStats is an ordinary field (it even has a name, armStats, that you can use to reach it), and the promoted method runs with armStats as its receiver. It cannot see the outer type, and there is no super and no virtual dispatch back into the outer type. If you need to override, you define a method with the same name on the outer type, as exercise 2 does.

The type armStats starts with a lowercase letter, so it is invisible outside the package, but its exported method Update is still promoted onto the exported EpsilonGreedy and counts towards satisfying Policy.

Step 3: value or pointer receivers

So far every method has a pointer receiver, (p *EpsilonGreedy). With interfaces in play the choice has a visible consequence. Try to use a value where a Policy is expected:

The compiler is telling you about method sets. The method set of a type T contains the methods with receiver T; the method set of *T contains methods with receiver T and *T. Since Select, Name and (via armStats) Update are declared on pointers, only *EpsilonGreedy satisfies Policy. That is not pedantry. If a value could be stored in an interface, each method call would operate on a copy and Update would change a copy that is immediately thrown away. Go refuses to let you write that bug quietly.

Which receiver to choose:

  • Pointer receiver if the method modifies the receiver, if the struct is large, or if it holds anything that must not be copied (a mutex, chapter 6). Every policy here qualifies.
  • Value receiver for small, immutable value types, such as a time.Time or a two-field Point.
  • Do not mix both kinds on one type. Mixed receivers make the method sets confusing and linters complain.

Exercise 3 hands you a value-receiver bug to fix. It is instructive because it is partly working: writes through a slice field survive the copy, while a plain int field silently does not.

Go vs. Python

Python passes references to objects everywhere, so mutating self just works. Go is pass-by-value throughout: a struct assigned, passed, or used as a value receiver is copied. A pointer is how you say "share this one". Slices, maps and channels are small headers that point at shared data, which is why copying a Tally that contains a slice appears to half work.

Step 4: a second policy

UCB1 ("upper confidence bound") is deterministic. After trying each arm once, it always pulls the arm with the highest optimistic estimate:

score(a) = mean(a) + √(2 · ln t / n(a))

where t is the total number of pulls and n(a) is how often arm a was pulled. The square-root term is a bonus that is large for an arm that has been tried rarely and shrinks as evidence accumulates. Arms that might be better than they look get pulled; arms that are clearly worse stop being pulled, with no random exploration at all.

UCB1 embeds the same armStats, so it gets Update by embedding and only has to provide Name and Select. Nothing else in the codebase had to learn that UCB1 exists.

Step 5: the runner accepts an interface

The change to the simulation is one word:

pol is now a Policy, and the runner records pol.Name() in the result. An interface value is a pair (concrete type, pointer to the value), and calling pol.Select() looks the method up dynamically. This has a cost: a method call through an interface is an indirect call that the compiler usually cannot inline. It is small, but not zero.

The guideline this illustrates is accept interfaces, return structs: Run takes the narrowest interface that describes what it needs, while NewEpsilonGreedy returns the concrete *EpsilonGreedy. Callers keep access to fields such as Epsilon, and a new method added later is not a breaking change to an interface anyone else implements.

Because satisfaction is implicit, a typo in a method name would only show up when you try to use the type as a Policy, possibly far from where you wrote it. A compile-time assertion catches it at the definition:

Step 6: choosing policies by name

main should be able to build a policy from a string. A small factory function does that:

The function returns the interface type, so callers get a Policy whichever branch ran. One trap to know about: never return a typed nil pointer such as (*UCB1)(nil) as a Policy. An interface value holding a nil pointer is not equal to nil, so the caller's if pol == nil check would pass and the first method call would panic. Return a literal nil on failure, as the code does. Chapter 3 shows the trap firing. The error return is new; chapter 3 covers Go's error handling properly.

2. A logging wrapper via embedding

In exercises/ch02/ex2, Logged embeds a Policy. Make it record "select 2" and "update 1 1"-style lines to its Log while still delegating to the wrapped policy. You should not need to write Name.

Reference answer

Defining Select and Update on *Logged shadows the promoted ones; the embedded policy is still reachable as l.Policy. Name is promoted unchanged. This is the decorator pattern. HTTP middleware in chapter 8 has the same shape.

3. Find the bug (value receivers)

exercises/ch02/ex3 contains a Tally that miscounts. The test fails on Total() but passes on Count(). Explain why before fixing it, then fix it without editing the tests.

Reference answer

Every method had a value receiver, so each call worked on a copy of the struct. counts is a slice header pointing at one shared array, so t.counts[arm]++ reached the original; total is a plain int inside the copy and its increment vanished. The fix is pointer receivers throughout, and returning *Tally from the constructor so the test's Counter interface variable holds a pointer.
