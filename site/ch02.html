02 Part I: Language core · Chapter 2

Interfaces and methods

Introduce the Policy interface, add UCB1, and swap policies without touching the runner.

Starting point

Work in ch02/start in your clone of the repository. It is the previous chapter's finished project with the parts you will write left out, so every chapter begins from a project known to work. Run go test ./... there to see what is missing. To start over, git restore ch02/start; to keep the original untouched, copy the folder somewhere else first.

What you will build

A Policy interface that lets the simulation run any selection strategy, and a second strategy, UCB1, that plugs into it without changing a line of the runner. Along the way you meet the three ideas that make Go code reusable without inheritance: interfaces, embedding, and the choice between value and pointer receivers.

The result: go run . -policy epsgreedy,ucb1 compares two policies on identical conditions in one table.

The Go in this chapter

  • Interfaces. A set of method signatures. Any type that has those methods satisfies the interface automatically; there is no implements keyword. This is the main idea of the chapter.
  • Embedding. A struct field with a type but no name. The outer type gains the inner type's fields and methods, so common code is written once. It looks like inheritance and is not.
  • Method sets. Why a pointer receiver decides whether a value or only a pointer satisfies an interface.
  • The factory function. A switch that builds a value by name and returns the interface type.
  • Mentioned, explained in chapter 3: the error in NewPolicy's return, and the typed-nil trap.

Why Go does it this way

In Python you get this with duck typing (checked at runtime, if at all) or typing.Protocol (checked by an external tool). Java-style nominal interfaces check at compile time but force the implementer to name the interface, so the interface has to exist before the implementation. Go's structural interfaces are checked by the compiler and defined by the consumer. So Go code declares small interfaces next to the code that uses them: Policy lives in the package that runs simulations because that is the code that needs one. The standard library's io.Reader, one method long, is the model.

Two guidelines follow. Accept interfaces, return structs: Run takes the narrowest interface that describes what it needs, while NewEpsilonGreedy returns the concrete pointer, so callers keep access to fields like Epsilon. And an interface call has a small cost: it is looked up at run time and usually cannot be inlined. It is tiny, but not zero.

Sharing bookkeeping with embedding

Every policy needs per-arm pull counts and running means. Rather than copy that into UCB1, the starter pulls it into a small type, which is given:

and EpsilonGreedy embeds it: a field with a type but no name. Compare with chapter 1:

The values slice is gone, replaced by armStats.means, so Select and greedy change only in that name. The Name method is new, and Update has moved into armStats.

Embedding promotes the embedded type's fields and methods, so p.means, p.counts and p.Update(arm, r) all work directly on an EpsilonGreedy. The type armStats starts with a lowercase letter, so it is invisible outside the package, but its exported method Update is still promoted onto the exported EpsilonGreedy, and callers can use it.

It looks like inheritance, but it is composition: armStats is an ordinary field (it even has a name, armStats, that you can use to reach it), and the promoted method runs with armStats as its receiver. It cannot see the outer type, and there is no super and no virtual dispatch back into the outer type. If you need to override, you define a method with the same name on the outer type, as exercise 2 at the end does.

Value or pointer receivers

So far every method has a pointer receiver, (p *EpsilonGreedy). With interfaces in play the choice has a visible consequence. Before you run this program, decide whether you think it compiles:

Run it with go run ./_examples:

The compiler is telling you about method sets. The method set of a type T contains the methods with receiver T; the method set of *T contains methods with receiver T and *T. Since Select, Name and (via armStats) Update are declared on pointers, only *EpsilonGreedy satisfies Policy. That is not pedantry. If a value could be stored in an interface, each method call would operate on a copy and Update would change a copy that is immediately thrown away. Go refuses to let you write that bug quietly.

Which receiver to choose:

  • Pointer receiver if the method modifies the receiver, if the struct is large, or if it holds anything that must not be copied (a mutex, chapter 6). Every policy here qualifies.
  • Value receiver for small, immutable value types, such as a time.Time or a two-field Point.
  • Do not mix both kinds on one type. Mixed receivers make the method sets confusing and linters complain.

Go vs. Python

Python passes references to objects everywhere, so mutating self just works. Go is pass-by-value throughout: a struct assigned, passed, or used as a value receiver is copied. A pointer is how you say "the same one".

Exercise 3 at the end hands you a value-receiver bug to fix. It is instructive because it is partly working: writes through a slice field survive the copy, while a plain int field silently does not.

A second policy: UCB1

UCB1 ("upper confidence bound") is deterministic. After trying each arm once, it always pulls the arm with the highest optimistic estimate:

score(a) = mean(a) + √(2 · ln t / n(a))

where t is the total number of pulls and n(a) is how often arm a was pulled. The square-root term is a bonus that is large for an arm that has been tried rarely and shrinks as evidence accumulates, so exploration fades on its own; there is no ε to tune. Its type, constructor and name are given. It embeds the same armStats, so Update comes for free:

Task 2: UCB1.Select

Write it as the comment says. The tests set counts, means and total directly and then call Select, so it must read exactly those and change nothing. You will need math.Sqrt and math.Log, so add import "math". Go does not let an unused variable or import go unnoticed, so the compiler will tell you if you forget one or leave one behind. Run go test -run UCB1 ./bandit.

Hint 1: the shape

Two passes over the arms. The first handles arms that have never been pulled, since the formula divides by the count. The second picks the best score.

Hint 2: the loops

The first loop returns the first arm whose count is zero. The second keeps the best score so far (start it at math.Inf(-1), negative infinity) and the index that produced it, replacing them only when a score is strictly larger. for arm, n := range p.counts gives you each arm and its count.

Hint 3: the score

Inside the second loop: score := p.means[arm] + math.Sqrt(2*math.Log(float64(p.total))/float64(n)). p.total and n are integers, so both need float64(...) before they go into math.Log and the division.

Answer

The first loop guarantees no division by zero in the second, and math.Log(float64(p.total)) is safe because by then total is at least the number of arms. The comparison is strict, so on equal scores the earlier arm wins and the policy stays deterministic. Nothing else in the codebase had to learn that UCB1 exists.

Task 3: NewPolicy

A switch on name. The function returns the interface type, so callers get a Policy whichever branch ran. It also returns an error: return nil for it on success, and fmt.Errorf("unknown policy %q", name) for a name you do not know. Chapter 3 covers Go's error handling properly. Run the whole suite with go test ./....

Hint

On failure, return a plain nil as the first value, not a typed nil such as (*UCB1)(nil). The test checks this, and the answer explains why.

Answer

One trap to know about: never return a typed nil pointer such as (*UCB1)(nil) as a Policy. An interface value holding a nil pointer is not equal to nil, so the caller's if pol == nil check would pass and the first method call would panic. Return a literal nil on failure, as here. Chapter 3 shows the trap firing.

Extra tasks

Three more, in the same project: ch02/start/bandit/extras.go, with tests in extras_test.go. Nothing else uses them, so do them now or come back later. They are the practice for this chapter's ideas: implementing an interface, embedding, and receivers.

Extra 1: a round-robin baseline

Make RoundRobin a policy that pulls arms 0, 1, 2, ..., n-1, 0, ... and ignores rewards. Any learning policy should beat this baseline. The test has a compile-time assertion that *RoundRobin satisfies Policy; you should know why it is there.

Answer

The receiver is a pointer because Select advances next. The modulo keeps the cycle in range without a branch. It is not added to NewPolicy: the tests that loop over PolicyNames() expect policies that learn.

Extra 2: a logging wrapper via embedding

Logged embeds a Policy, so it already has all three methods. Override Select and Update so they record "select 2" and "update 1 1"-style lines in Log (arm, then reward printed with %g) and then call the embedded policy. Name needs no code.

Answer

Inside an overriding method you reach the embedded value by its type name, l.Policy.Select(). Without that qualifier the method would call itself forever. The wrapper still satisfies Policy, so Run accepts it with no change: this is how middleware is built in Go.

Extra 3: find the receiver bug

The tests fail even though every method looks reasonable. Find the bug and fix it without changing the tests. It fails in an interesting way: one of the two checks passes.

Answer

The methods have value receivers, so each call works on a copy of the Tally. The slice inside the copy shares its array with the original, so counts[arm]++ still lands; the total field is a plain integer, so total++ changes the copy and is lost. Pointer receivers, and a constructor that returns a pointer, fix both. Once the methods have pointer receivers, only *Tally has them in its method set, which is why NewTally must return a pointer for the interface test to compile: the rule from the receivers section again.
