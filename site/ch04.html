04 Part I: Language core · Chapter 4

Generics and the comparison harness

Add Thompson sampling, write generic helpers where they earn their place, and chart regret across many seeds.

Starting point

Your own project as it stood at the end of Chapter 3. If yours has drifted, or you are skipping ahead, tools/start.sh ch03 work/banditlab copies the reference version into a new directory.

What you will build

The third policy, Thompson sampling, and a comparison harness that runs every policy across many seeds and turns the results into a table, a CSV file, and the regret chart below. One seed can mislead; a hundred seeds with an error band show whether a difference is real, and the rest of the course relies on that.

Generics arrive along the way, because Thompson sampling and the harness both have small pieces that are the same for several types. Just as important is where they do not help, and the chapter marks both.

Step 1: Thompson sampling

Epsilon-greedy explores blindly and UCB1 explores by a formula. Thompson sampling asks a more direct question: given what I have seen, what could each arm's true probability be?

For a Bernoulli arm the answer has a closed form. Start with a uniform belief, Beta(1, 1). After s successes and f failures the belief becomes Beta(1 + s, 1 + f): the Beta distribution is the conjugate prior for Bernoulli data, so updating means adding to two counters. To choose an arm, draw one sample from each arm's Beta and pull the arm with the largest draw. An arm with little data has a wide posterior and will sometimes draw high (exploration); an arm with a lot of data and a low mean will almost never win (exploitation). No ε and no bonus formula to tune.

Those two counters per arm are worth remembering: they are plain sums, and in chapter 12 they are what lets replicas combine what they have each learned.

The standard library's math/rand/v2 has uniform, normal and exponential draws but no Beta. A Beta sample can be built from two Gamma samples, X / (X + Y), and a Gamma sample from the Marsaglia-Tsang rejection method, which needs only normal and uniform draws:

How do you test a random-number routine? By its moments. A Beta(a, b) has mean a / (a + b) and variance ab / ((a + b)²(a + b + 1)); with a seeded generator and 100,000 draws the sample statistics land close to those, and the same seed means the test can never flake:

The parameter sets include (0.5, 0.5) and (1, 100) on purpose: shapes below 1 exercise the boost branch, and a heavily skewed shape exercises the tail.

Step 2: your first generic function

Both epsilon-greedy (with ties broken at random) and Thompson sampling need "the index of the largest element". In chapter 1 that loop lived inside EpsilonGreedy, and it worked on []float64 only. It is now needed for several slices of floats, and it would be equally useful on counts or names. This is a straightforward case for generics: the algorithm does not depend on the element type, only on the ability to compare two of them.

Reading the signature: [T cmp.Ordered] declares a type parameter T and constrains it. A constraint is an interface, but one that describes a set of types; cmp.Ordered in the standard library is the set of all types that support <, > and friends (all integer and float types, and string). Inside the function you may do anything the constraint permits, so it can call cmp.Compare.

At the call site you rarely write the type: Argmax(p.means, p.rng) works because the compiler infers T = float64 from the argument. You can write Argmax[int](counts, nil) to be explicit. A slice of a type that is not ordered ([]struct{}, say) is rejected at compile time with a clear message, not at run time.

Passing nil for the generator selects "lowest index wins" and keeps UCB1 deterministic. Using nil to mean "lowest index" is a compromise; if the two behaviours diverged further, two functions would be clearer.

The test calls the same function with floats, ints and strings, which is the point of the exercise.

Go vs. Python

A Python function taking a list already works on any element type that supports >, checked at run time, and TypeVar annotations are advisory. Go generics are checked at compile time and the constraint states what the function needs. Underneath, Go does not box everything as an object; the compiler generates code that is specialised by the shape of the type arguments, so Argmax on []float64 is as fast as a hand-written loop. What Go deliberately does not have: generic methods (a method cannot introduce its own type parameters, only use those of its receiver type), operator overloading, or inheritance-style constraints. Constraints describe sets of types and operations, nothing more.

Step 3: where generics do not help

Chapter 3's NewPolicy repeated a four-line if err != nil block per policy to avoid returning a typed nil. It is tempting to reach for a type parameter to remove it. The better tool is the one we already have:

asPolicy takes a Policy and an error. Calling asPolicy(NewUCB1(nArms)) is legal because a call that returns two values can be passed directly as two arguments, and because the helper checks err itself and returns a true nil when there is one, the trap never escapes. No type parameter is needed: the function only asks "is there an error?", not anything about the concrete type. A rule of thumb that holds up: if a function only calls methods, take an interface; if it needs to hold, compare, or return values of the caller's own type, use a type parameter.

The same reasoning is why the Policy interface stays an interface. Turning the runner into Run[P Policy](env, pol P, ...) would work, but every caller would pay for a more complicated signature and gain nothing, and you could not put policies of different kinds in one slice of a type parameter (you can in a []Policy, which the harness relies on).

Step 4: a numeric helper package

The harness needs the mean and the standard error of a set of numbers, and later chapters will want them for integers (latencies, counts) as well as floats. That is a second natural home for generics, this time with a constraint we define ourselves:

The Number constraint is a type set: a union of types. The ~ means "any type whose underlying type is this one", so a named type such as type Reward float64 qualifies; without the tilde it would not. Inside Mean, float64(x) is the only operation used, and it is legal because every member of the union is numeric. The constraint guarantees at compile time that the body is valid for every type it may be called with.

Step 5: the harness

The harness answers one question: how much regret does each policy accumulate, on average, in a given scenario? It runs each policy against many independent environments (one per seed), collects each run's regret curve, and reduces them to the mean and standard error at every step.

Some design points:

  • The policies are strings. Spec.Policies holds the same spec strings the CLI accepts, and runOnce builds a fresh environment and policy for every seed through bandit.NewPolicy. A policy has state, so each run needs its own.
  • Seeds are consecutive integers from BaseSeed, which makes runs reproducible: Compare with the same Spec always returns the same numbers, which a test pins down.
  • Errors carry context (which policy, which seed) with %w, as in the previous chapter.
  • It runs sequentially. Everything here is independent per (policy, seed), which is the ideal shape for parallel work. Chapter 5 uses this exact function as its first concurrency exercise.

Step 6: CSV and SVG output

Results should be usable outside Go. CSV is one encoding/csv writer:

The method takes an io.Writer, not a filename. A file, a bytes.Buffer in a test, an HTTP response body and os.Stdout are all writers, and io.Writer is one of the most widely used interfaces in the standard library. It uses the generic stat.Sample to thin 5,000 steps to 100 rows per policy, so the file is small enough to open anywhere:

The chart is generated the same way, as a text SVG written with fmt.Fprintf into a strings.Builder. Two details make it fit a documentation site. First, colours are CSS custom properties with fallbacks (var(--series-1)), so the page can restyle it for dark mode while the standalone file still looks right. Second, it carries a <title> and <desc> that state the final numbers in words for screen readers, and each line is labelled directly at its right end with a marker in its colour. Lines also differ by dash pattern, so identity never rests on colour alone.

"Nice" tick values (round steps of 1, 2 or 5 times a power of ten) are the one piece of real plotting logic. The rest of WriteSVG is straightforward coordinate arithmetic: map a step to an x position, a regret to a y position, emit a <polyline> for each policy's mean and a translucent <polygon> for its ±1 standard-error band. It is around 140 lines and teaches little Go beyond fmt and strings.Builder, so copy the whole file rather than typing it:

Step 7: the compare subcommand

The CLI now has two subcommands. main only dispatches; each subcommand gets its own flag.FlagSet, so run and compare can have different flags:

Chapter 3's run function moves to its own file as runCmd. Its flag set gets a new name and thompson joins the default policy list; the rest is unchanged.

The new subcommand wires flags to the harness and writes the optional files:

writeFile uses a named result err and a defer so the close error is joined with the write error instead of being dropped. A failed Close on a file you have written to can mean the data never reached the disk. defer runs its function when the surrounding function returns, whichever path it takes, which is how Go does the job of Python's with blocks and finally.

Step 8: what the numbers say

Run the harness on three scenarios with 100 seeds of 5,000 steps each:

The ± is the standard error of the mean regret across the 100 seeds. The mean curve is plotted at the top of this page; here are the other two scenarios:

What to take from this, and what not to:

  • Thompson sampling has the lowest mean regret in all three scenarios, by a wide margin in easy and needle. Its curve visibly flattens, which is what logarithmic regret looks like on a linear axis.
  • UCB1 is the worst of the four on needle and close. That comes from the standard √(2 ln t / n) bonus, which is large relative to the gaps in these scenarios: with ten arms, it keeps sampling all nine 0.10 arms until, roughly, the bonus falls below the 0.20 gap. Tuned or variance-aware UCB variants do much better; this is plain UCB1.
  • Epsilon-greedy's result depends heavily on ε, and the error bars tell you why. At ε = 0.01 the standard error is large (38.6 on needle, 18.8 on easy): some seeds lock onto a good arm early and pay almost nothing, others lock onto a bad arm and stay wrong for thousands of steps. On easy its mean beats ε = 0.1, but a policy whose outcome is a coin flip is not what you want in production. A single seed can't show this at all.
  • These are three fixed scenarios and one horizon. Nothing here says Thompson is always better; with delayed or batched feedback, which the serving chapters introduce, the ranking can change, and chapter 12 measures exactly that.

Exercises

Starters and tests are in exercises/ch04.

1. Generic SumBy and MaxBy

In exercises/ch04/ex1, implement SumBy[T any, N Number](xs []T, f func(T) N) N (total of a projection, e.g. total reward across a slice of result structs) and MaxBy[T any, K cmp.Ordered](xs []T, key func(T) K) (T, bool). Notice that callers never write the type arguments.

Reference answer

Two type parameters is normal when a function relates two types. var sum N is the generic way to say "zero of whatever this is": no literal 0 would compile for every N. MaxBy returns (T, bool) rather than a special value, the comma-ok idiom from chapter 1 applied to a generic type.

2. Quantiles for a percentile band

A ±1 standard-error band assumes the regret is roughly bell-shaped across seeds; the spread in the ε = 0.01 results suggests it is not. Implement Quantile(xs []float64, q float64) float64 in exercises/ch04/ex2 (linear interpolation, must not modify its input). As an extension with no provided test, add a -band percentile flag to compare that draws the 10th to 90th percentile instead.

Reference answer

slices.Clone before slices.Sort protects the caller's slice, since sorting is in place. !(q >= 0 && q <= 1) handles NaN for the same reason as chapter 3's probability check.

3. A generic type with a useful zero value

Counter[K comparable] in exercises/ch04/ex3 counts occurrences of keys (arms, policy names, anything comparable). Implement Inc, Get and MostCommon so that var c Counter[string] is usable immediately, with no constructor.

Reference answer

Generic types take type parameters on the type and its methods repeat them in the receiver, (c *Counter[K]). The zero-value trick relies on two facts about maps: reading from a nil map is fine, and only writing panics, so Inc creates the map lazily. It is the pattern behind sync.Mutex and bytes.Buffer, both usable as declared. comparable is required because map keys must support ==.
