Go in an hour

The basics of Go you need before chapter 1: values, functions, control flow, slices and maps, structs, tests.

Starting point

Nothing to set up yet beyond installing Go. The examples and the tasks are both in the primer/ directory of the repository.

What this page is for

The rest of the course builds one program, a simulation of a multi-armed bandit that grows into a set of services. Each chapter introduces the Go it needs as it goes. This page is the short version of the basics you should have seen once before chapter 1 starts, so that the first chapter can spend its time on the project.

It is a warm-up, not a full tutorial. The examples are small programs in the primer/ directory of the repository. Run each one, change something, and see what happens. At the end of each section is a small task with tests; write the function, run go test, and open the answer only when you are done or stuck. If a section already feels familiar, skip to its task. If you want more depth on any of it, A Tour of Go and Effective Go are the standard references.

Nothing needs explaining twice: when a later chapter uses something this page only mentions, that chapter explains it.

Setup

Install Go from go.dev/dl. This course was written against Go 1.27, and the go.mod files pin the toolchain, so any Go 1.21 or later will download the right version by itself. Check that it works:

Then clone the repository. The examples and the tasks are both in primer: each example is a directory, and the tasks are ex1 to ex5. Go programs are built from modules (a directory with a go.mod file) that hold packages (one directory each, all files declaring the same package name). The examples here are a module called primer; each subdirectory is a small program.

1. Hello, and the tools

A program starts in func main() of package main. import lists the packages you use; fmt is the standard library's formatting package. A name from another package is written package.Name, and only names that start with a capital letter are visible outside their package. That one rule is all Go has in place of public and private.

go run . compiles and runs the package in the current directory. Go is a compiled language, so go build produces a single executable with no dependencies, which is much of why it is popular for services. Three other commands you will use constantly:

  • gofmt -w . reformats code into the one standard style. Nobody argues about formatting in Go; your editor probably runs it on save.
  • go vet ./... finds suspicious code the compiler accepts.
  • go test ./... runs the tests. Section 7 shows one.

2. Values and types

Three things here differ from a dynamically typed language:

  • Types are checked before the program runs. reward / pulls with a float64 and an int does not compile. You convert explicitly with float64(pulls). It is more typing and it removes a class of bugs.
  • Every type has a zero value and variables start there: 0, "", false, nil. There is no "undefined". Well-designed Go types are useful in their zero state, and section 6 uses that.
  • := is declaration, = is assignment. x := 1 creates x; a second x := 2 in the same scope is an error because it is already declared.
Your turn: a percentage

In primer/ex1/percent.go, write Percent(hits, total int) float64. Convert to floating point before you divide, and return 0 when total is 0. Run go test in that directory.

Answer

Dividing two integers first would truncate: 1/4 is 0, and 0 times 100 is still 0. Converting first keeps the fraction.

3. Functions and errors

A function can return several values, and the standard way to report failure is to return an error as the last one. nil means success. The caller checks it with if err != nil, and you will write that line thousands of times. There are no exceptions: an error is an ordinary value you must decide what to do with. fmt.Errorf builds one, and %w wraps another error inside it so that the cause is not lost. (Chapter 3 is about errors properly.)

Go vs. Python

Python would raise ValueError from int("seventy") and let it climb the stack. Go returns the failure to the immediate caller, every time. The code is longer and the control flow is visible on the page.

Your turn: parse a probability

In primer/ex2/probability.go, write ParseProbability(s string) (float64, error): parse the text with strconv.ParseFloat, and reject anything that is not a number from 0 to 1. Chapter 1's command line will use this idea for its flags.

Answer

The range check is written as !(p >= 0 && p <= 1) instead of p < 0 || p > 1 because NaN ("not a number", which ParseFloat accepts) is neither less than nor greater than anything, so the second form would let it through.

4. Control flow

Go has one loop keyword, for, in four shapes: the classic three-part loop, a condition only (its while), range over a collection, and range over an integer. switch takes the first matching case and stops; there is no fall-through and no break to write. An if may begin with a short statement, and the variable it declares exists only inside that if and its else branches, which keeps temporary values from leaking into the rest of the function.

Your turn: the longest winning streak

In primer/ex3/streak.go, write LongestStreak(rewards []int) int: the longest run of consecutive 1s. You need a loop, an if, and two counters.

Answer

current counts the run in progress and resets on a 0; best remembers the largest it ever reached. max is a built-in function (since Go 1.21).

5. Slices and maps

A slice is the everyday list. It is a small header (a pointer to an array, a length and a capacity), so assigning a slice or slicing one, as in a[:2], gives you another view onto the same elements. That is why changing b[0] changed a above. When you need independence, copy with slices.Clone. append returns the (possibly new) slice, so you always write a = append(a, x). make([]int, n) creates a slice of n zeros.

A map is a dictionary. Looking up a key that is missing gives the zero value, which makes counting easy (m[k]++ works on a new key). To tell "missing" from "present and zero", use the two-value form v, ok := m[k], called comma-ok. Iteration order is random by design, so sort the keys if the order matters.

Your turn: count the pulls

In primer/ex4/tally.go, write Tally(pulls []int, arms int) []int: for a list of arm numbers, return how many times each arm appears. Ignore numbers that are not valid arms.

Answer

The result slice has to exist before you index into it, which is what make is for. The bounds check matters: indexing outside a slice is a runtime panic, not a silent zero.

6. Structs, methods and pointers

A struct groups fields. A method is a function with a receiver written before its name. A receiver of type *Arm (a pointer) works on the caller's value and can change it; a receiver of type Arm would get a copy. Structs are copied when assigned or passed, pointers are not, which the last lines of main demonstrate. Go has no constructors. By convention a function called NewArm returns a ready-to-use *Arm, and lowercase field names keep other packages from bypassing it.

You do not need to master pointers now. The rule that covers most of what you will write: if a method changes the struct, give it a pointer receiver, and use the same kind for all methods of a type.

Your turn: a running mean

In primer/ex5/mean.go, fill in the type RunningMean and its three methods. Its zero value must work without a constructor. This is the same update rule the bandit policy uses in chapter 1, so it is worth doing now.

Answer

Both fields start at 0, and the first Add computes 0 + (x - 0) / 1, which is x. Designing the type so the zero value is valid is a habit worth forming: callers get one less thing to remember.

7. Packages and tests

Tests are ordinary Go, in files ending _test.go, in the same package. A test is a function named TestSomething(t *testing.T). This one is table-driven: a slice of cases, run in a loop, each as a named subtest with t.Run. It is the usual shape for Go tests, and chapter 3 is about writing them well. go test compiles the package with its tests and runs them. From now on every task in the course comes with tests that define "done".

The test file is in the same directory as the code it tests, and the package is imported elsewhere by its path: the module path plus the directory. In chapter 1 your project's module is called banditlab, and the package in its bandit directory is banditlab/bandit.

Ready?

You have seen enough to start. Chapter 1 sets up the project and asks you to write the first pieces of the simulation. When something in it is unfamiliar, the chapter's own introduction says what you need, and anything it does not explain yet it says will come later.
