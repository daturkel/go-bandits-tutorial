01 Part I: Language core · Chapter 1

Modules, packages, first simulation

Set up a Go module and write an epsilon-greedy bandit simulation that prints its regret.

Starting point

Work in ch01/start in your clone of the repository. It is the previous chapter's finished project with the parts you will write left out, so every chapter begins from a project known to work. Run go test ./... there to see what is missing. To start over, git restore ch01/start; to keep the original untouched, copy the folder somewhere else first.

What you will build

A command-line program that simulates a multi-armed bandit and reports how much reward it left on the table. You start from a project that is partly written. The plumbing is there, and eight pieces are missing, each with tests that fail until you write it. By the end you have a reproducible random-number source, an environment whose arms pay out with fixed probabilities, an epsilon-greedy policy that learns which arm is best, a simulation loop, and a program you can run with different settings.

Everything later in the course builds on these types, so it is worth being precise about the problem first.

The bandit problem

There are k arms. Pulling an arm pays 1 with some hidden probability and 0 otherwise. You want the most total reward over a fixed number of pulls, but you do not know the probabilities. Pulling the arm that looks best exploits what you know; pulling another arm explores, which costs reward now and might reveal something better. Regret measures the cost: the reward you would have collected by always pulling the best arm, minus what you collected.

Epsilon-greedy is the simplest policy: with probability ε pull a random arm, otherwise pull the arm with the best average reward so far.

Modules and packages

A Go module is a tree of packages versioned together, described by a go.mod file at its root. A package is a directory of .go files that share a package clause; it is the unit of compilation and of import. The starter is already a module. Had you started from an empty directory you would have created it like this:

go mod init records the Go version you happen to have installed. This project pins both a language version and an exact toolchain, so every reader builds with the same compiler:

The go line is the minimum language version the module needs; the toolchain line is the exact release the go command uses, downloading it if yours is older. This module has no dependencies, so there is no go.sum and nothing else to manage.

The layout is small on purpose:

The import path of the library package is the module path plus the directory: banditlab/bandit. Every file in bandit/ starts with package bandit, and anything defined in one file is visible to the others without importing. Code outside the package can use only the names that start with a capital letter.

Go vs. Python

Python packages are found by searching sys.path, and a directory becomes a package by convention or an __init__.py. In Go the module path in go.mod is the root of every import, and a package is exactly one directory. There is no search path to get wrong.

Random numbers you can reproduce

A simulation you cannot reproduce is a simulation you cannot debug, so randomness comes from generators we create and seed ourselves, never from the global one. math/rand/v2 provides rand.New(rand.NewPCG(seed1, seed2)): a PCG generator, fast and statistically sound, that produces the same numbers for the same two seeds on every machine. NewRNG wraps this with a seed and a stream number. The environment and the policy each get their own generator, made from the same seed but different stream numbers. If they shared one, adding a single extra random draw to the policy would silently change every reward the environment produces, and comparing two policies on "the same" world would not be fair.

The constants naming the two streams are given. The const block uses iota, a counter that starts at zero in each constant group, so StreamEnv is 1 and StreamPolicy is 2. Read it as "two named numbers"; chapter 3 shows what the idiom is for. The function is yours:

Task 1: NewRNG

Right now every caller gets the same numbers, because the function ignores its arguments. Build the generator from seed and stream as described above. Two functions from math/rand/v2 do it: rand.NewPCG(seed1, seed2 uint64) *PCG creates the source of random bits from two 64-bit seeds, and rand.New(src Source) *Rand wraps a source in a rand.Rand, the type that has the methods for drawing numbers. Run go test -run RNG ./bandit.

Hint

rand.NewPCG takes two uint64 values and rand.New wraps the result in a generator. You already have exactly two numbers.

Answer

One line. The seed picks the sequence; the stream picks an independent sequence from the same seed. Same pair in, same numbers out, on any machine.

The environment: structs and methods

An environment is a set of arms with hidden success probabilities. A struct groups its data, and methods are functions declared with a receiver. Here you write the whole type: the fields, a constructor, and four methods. Start with the state and the two simple ones.

Task 2: Env, NewEnv, NumArms, Prob

Give Env two fields, the probabilities and the generator. NewEnv fills them in and returns a pointer. NumArms and Prob read them. One requirement is not obvious: if the caller changes the slice they passed in afterwards, the environment must not change. Run go test -run 'NumArms|Copies' ./bandit.

Hint 1: the fields

Two fields are enough: the probabilities, a []float64, and the generator, a *rand.Rand. NumArms is the length of the first, and Prob indexes it.

Hint 2: the copy

A slice is a small header onto an array, so assigning one shares the elements. The standard library's slices package has slices.Clone(s S) S, which returns a copy of a slice with its own array (the S is a generic type parameter, which chapter 4 explains: read it as "a slice of anything"). Add "slices" to the imports and use it in the constructor.

Answer
  • There are no constructors in Go. NewEnv is an ordinary function that, by convention, returns a pointer to a ready-to-use value. The fields are lowercase, so code outside the package can only get a working Env through it.
  • slices.Clone copies the caller's slice. Without it, the caller could change the probabilities under our feet. The test for that is the one named Copies.
  • The receivers are pointers (*Env), the rule of thumb from the primer: types with state use them, and one kind per type. Chapter 2 is about the choice.
Task 3: Env.Pull

Pulling an arm returns 1 with the arm's probability and 0 otherwise. The generator gives you a random number with (*rand.Rand).Float64() float64: uniform in [0, 1), so e.rng.Float64(). Run go test -run Pull ./bandit. The tests check that rewards are only 0 or 1, that the long-run rate matches the probability, and that a seed gives the same sequence twice.

Hint

Compare the random number with the probability. A draw that falls below probs[arm] happens with exactly that probability.

Answer

A number drawn uniformly from [0, 1) is below p with probability exactly p. The function returns a float64 (0 or 1, not a bool) so rewards can later be fractions, and so the policy code can add them up without conversions.

The simulation also needs to know which arm is really best, to measure regret:

Task 4: Env.Best

Best returns two values. Its results are named (arm and p), which declares them as variables at the top of the function, set to zero. Loop over the probabilities and keep the largest. If two arms tie, the first wins. Run go test -run Best ./bandit.

Hint

The first arm is the best so far by default. After that, an arm replaces it only if its probability is strictly larger. A for i, q := range e.probs loop gives you both the index and the value, and i == 0 is a convenient way to say "first".

Answer

The named results start at zero, so the i == 0 test is what makes the first arm the starting champion whatever its probability. The comparison is strict (>), so on a tie the earlier arm keeps its place, which is what the test for ties expects.

Go vs. Python

Every type has a usable zero value (0, "", false, nil for pointers, slices and maps), and variables are never "undefined". There is no None to forget to check for a number or a string. Well-designed Go types work in their zero state, which is why make([]int, n) in the next part needs no initialisation loop.

Named test beds: maps

To compare behaviours we want a few standard test beds we can select by name. This file is given; it is a map from name to probabilities:

Scenario returns ([]float64, bool). Reading a map with two variables, probs, ok := scenarios[name], is the comma-ok form from the primer: a missing key yields the zero value and ok == false, not an error. The function clones the slice for the same reason NewEnv does. Map iteration order is random on purpose, so ScenarioNames collects the keys with maps.Keys and sorts them. The policy: slices and a running mean

The policy keeps, for each arm, how many times it was pulled and the running mean of its rewards. Two parallel slices indexed by arm are all it needs, and both are created with make so they start as zeros. This part is given:

Epsilon is capitalised, so callers can read and change it; counts, values and rng are private to the package. The three methods are yours, in the order they depend on each other.

Task 5: Update, the running mean

After a reward arrives, the arm's average must include it, without storing every reward. The primer's RunningMean exercise used this update rule: after n observations, mean += (reward − mean) / n. The tests read counts[arm] and values[arm] directly, so that is where the count and the mean must end up. Run go test -run Update ./bandit.

Hint

Increment the arm's count first, then use the new count as n. Convert it with float64(...) before dividing.

Answer

Counting first means the divisor is never zero, and the first reward sets the mean to exactly that reward, since 0 + (r - 0) / 1 is r. The identity avoids keeping a list of rewards or a running sum.

Task 6: greedy, and ties

Return the arm with the highest mean. The subtle part: at the start every mean is 0, so every arm ties. Returning the first maximum would make the policy always try arm 0 first, and then keep choosing it until its mean falls below another arm's. Break ties evenly at random, using (*rand.Rand).IntN(n int) int, which returns a random integer from 0 to n−1 (p.rng.IntN(3) is 0, 1 or 2). The lowercase name greedy means only this package can call it: it is an implementation detail. The tests set p.values directly and then call greedy, so decide from p.values alone. Run go test -run Greedy ./bandit.

Hint 1: the shape

One pass over p.values, remembering the best index so far. Start with arm 0 as the best. Then think about what should happen when two values are exactly equal.

Hint 2: the idea

Also remember how many arms have tied with the current best. When you meet another equal value, that is one more tied arm, and it should replace the current pick with probability 1 out of the number of ties so far. Then every tied arm ends up equally likely, and you never need a list of them. A better value starts a new count at 1.

Hint 3: nearly the code

Start with best, ties := 0, 1 and loop for i := 1; i < len(p.values); i++. Inside, a switch with conditions and no value has two cases: a strictly larger value sets best, ties = i, 1; an equal one does ties++ and then if p.rng.IntN(ties) == 0 { best = i }. Return best.

Answer

This is reservoir sampling with a reservoir of one: when the kth tied arm turns up, it replaces the current choice with probability 1/k, and a short induction shows every tied arm is equally likely at the end. It does one pass and needs no list of the tied arms.

Task 7: Select, explore or exploit

With probability Epsilon, return a uniformly random arm; otherwise return the greedy arm. You have both tools already: p.rng.Float64() compared with p.Epsilon decides whether to explore (as Pull did with a probability), and p.rng.IntN(n) picks the arm. Run go test -run Select ./bandit.

Answer

The same generator makes both random choices. That is fine, because it belongs to the policy alone; it is why the environment has its own.

The simulation loop

A run plays the policy against the environment for a fixed number of steps and records what happened. The result type is given:

Regret here is expected regret. Each pull adds bestP - env.Prob(arm), the gap in probabilities, rather than comparing the random rewards actually drawn. A lucky pull of a bad arm therefore still counts against the policy, which makes the curve much less noisy and lets us compare policies with fewer runs. The curve stores the cumulative regret after every step, for the charts in chapter 4.

Task 8: Run

Write the loop. In each step: ask the policy for an arm, pull it, tell the policy what happened, and update the result. res needs its two slices allocated before you use them, with make. for t := range steps counts t from 0 to steps-1. Run go test ./bandit; when the last test passes, every task is done.

Hint 1: the shape

Set up before the loop, then one loop with the same three calls every time: choose, observe, learn. The result's bookkeeping happens after those calls, inside the loop.

Hint 2: the set-up

You need the best probability once: _, bestP := env.Best(). The blank identifier _ discards a return value you do not need. Build res with Steps set and the two slices allocated: RegretCurve with make([]float64, steps) and Pulls with make([]int, env.NumArms()).

Hint 3: the loop body

arm := pol.Select(), then reward := env.Pull(arm), then pol.Update(arm, reward). After that: add the reward to res.TotalReward; add bestP - env.Prob(arm) to res.Regret; store the running res.Regret in res.RegretCurve[t]; count the pull in res.Pulls[arm]. Return res after the loop.

Answer

The order of the three calls is the whole simulation: choose, observe, learn. Notice what Run does not do: it never looks inside the policy. Chapter 2 makes that explicit with an interface, so any policy can be plugged in.

Run it with go run .:

Out of 10,000 pulls, arm 2 (the 0.8 arm) got 9,331; the rest went to exploring. Cumulative regret is about 304, and almost all of it is the price of exploring: exploring uniformly one time in ten across three arms wastes about 0.1 × (0.6 + 0.3) / 3 = 0.03 regret per pull, or 300 over the run. A fixed ε pays this cost for the whole run, even after the answer is obvious. The next chapters replace it with policies that explore less as they learn.

Because generators are seeded, this output is identical on every machine. Change the scenario, ε or step count to see how the numbers move:

On needle with a smaller ε, 95,310 of 100,000 pulls go to the good arm, but regret still reaches 938: with only 0.05 of exploration spread across ten arms, roughly nine in ten of those exploratory pulls go to a 0.10 arm that is 0.20 worse.

The unknown-scenario case shows the shape of error handling so far: a message on stderr and exit status 2. (go run prints the exit status line itself.)

Try it

Before you run each of these, say what you expect. The point is to notice when the result surprises you.

  • go run . -eps 0: never exploring. Does it find the best arm on easy? On close? Try a few seeds with -seed.
  • go run . -eps 1: always exploring. What should the pulls per arm look like, and what should the regret be after 10,000 steps on easy? You can work it out on paper.
  • go run . -scenario spread -steps 100000. Which arms get most of the pulls?

Extra tasks

Three more, in the same project: ch01/start/bandit/extras.go. Nothing else uses them, so do them now or come back later. Their tests are in extras_test.go and fail until you write them.

Extra 1: empirical rates (zero values)

Return each arm's success rate, wins[i] / (wins[i] + losses[i]). An arm that was never pulled has rate 0, not NaN. If the two slices differ in length, return nil, false.

Answer

Checking n > 0 before dividing is what prevents NaN. rates starts out zeroed, so the never-pulled case needs no code at all: not assigning is the answer.

Extra 2: reading the regret curve (maps and comma-ok)

Given the per-step regret curve and a list of step counts (1-based, like the milestones main prints), return a map from each mark to its regret. If any mark is out of range, return nil, false. Create the map with make(map[int]float64) (the primer used a map literal; make is the way to get an empty one), set entries with m[key] = value, and loop over the marks with for _, mark := range marks.

Answer

The map is created with make and a size hint. Reading the mark m as a one-based index means subtracting one, which is the classic off-by-one; the test pins it down.

Extra 3: decaying epsilon

Fixed ε keeps wasting pulls long after the best arm is obvious. Write the function the comment describes: an exploration rate that halves every halfLife steps but never drops below floor. Two functions from the math package help: math.Pow(x, y float64) float64 is xy, and math.Max(x, y float64) float64 is the larger of two numbers. Both take and return float64, so convert integers first. Then, as an extension with no provided test, make EpsilonGreedy.Select use it and compare regret on the easy scenario.

Answer

math.Pow and math.Max operate on float64 only, so the step count is converted explicitly: Go never converts between numeric types implicitly, even int to float64.
