13 Part IV: Distributed · Chapter 13

Splitting into services

Protobuf and gRPC: a policy service, feedback ingest and an aggregator.

Starting point

Your own project as it stood at the end of Chapter 12. If yours has drifted, or you are skipping ahead, tools/start.sh ch12 work/banditlab copies the reference version into a new directory.

What you will build

Three small services that talk to each other over gRPC, replacing the single banditd process for the distributed setup. A policy service answers "which arm?". A feedback service receives rewards. An aggregator merges the counts that come from feedback and streams the merged state to every policy instance. This is the design chapter 12 pointed at: the mergeable counts stay, but the polling loop in every replica is replaced by one place that knows the totals and pushes them out.

You will write the API in Protocol Buffers, generate the Go code from it, implement the three services, test them in-process over an in-memory connection, and run them as separate processes against one PostgreSQL database. Along the way you meet all the RPC shapes gRPC offers, status codes, deadlines, interceptors, and what graceful shutdown means when some calls never end by themselves.

Concepts introduced

  • Protocol Buffers: messages, field numbers, and how a schema evolves without breaking old clients
  • Code generation with buf (no protoc needed) and what the generated interfaces look like
  • The four RPC shapes; unary, server-streaming and client-streaming are used here
  • Status codes as the error vocabulary between services; deadlines and cancellation propagating across processes
  • Interceptors, gRPC's middleware; the standard health-checking service
  • Broadcasting a change to many waiting goroutines with a closed channel
  • Testing network services without a network (bufconn)
  • Graceful shutdown when a service has long-lived streams

Should you split it at all?

Often not. A single binary is easier to run, debug, deploy and reason about; chapter 12 already showed it scaling out with replicas. Splitting buys three specific things, and you should want at least one of them:

  • Different scaling. Selecting arms is on the request path of every user; recording rewards can lag behind by seconds without anyone noticing. They want different numbers of instances.
  • Different failure behaviour. If the aggregator is down, policy instances should keep answering from their last snapshot. In one process that separation does not exist.
  • Different owners. In a larger organisation the team that collects feedback is not the team that serves decisions, and an explicit API is the agreement between them.

The costs are real: every call is now a network call that can be slow, fail halfway or arrive twice; the API is a contract you must evolve carefully; and there are more things to run. This chapter is about paying those costs deliberately.

The shape of the system:

  • Select path: client → policy (choose an arm, record the selection as pending in the store)
  • Reward path: client → feedback (claim the pending selection in the store, add the reward to the totals) → aggregator (merge the delta, publish)
  • Learn path: aggregator → every policy instance, over a stream of snapshots

The PostgreSQL store from chapter 10 stays the source of truth and the place selections are matched to rewards. The aggregator is a fast path in front of it, not a replacement, and it reconciles against the store, as step 5 shows.

Step 1: the API, in protobuf

Protocol Buffers is a schema language and a compact binary encoding. You describe messages and services in a .proto file; tools generate the types and the client and server code for Go, Python, Java and others from it. That is why it is the usual choice between services written in different languages, and chapter 14 will call this API from Python.

Things to notice:

  • Field numbers are the identity of a field on the wire (= 1, = 2), not the names. You may rename a field freely; you may never change or reuse a number. You can add a field at any time: old readers skip numbers they do not know, and new readers see the zero value in messages from old writers. This is how a service and its clients can be upgraded at different times.
  • Every field has a zero default (0, empty string). A message cannot tell "reward = 0" from "reward not sent" for plain scalars. That is why the services validate what they receive, and why RewardRequest is checked for an empty id.
  • Package and version in the name (bandit.v1): when a breaking change is unavoidable you publish v2 alongside and migrate callers.
  • Each RPC has its own request and response type, even when a message would be empty (SelectRequest {}). Adding a field to one call later then does not touch any other. buf lint enforces this.
  • stream marks the streaming side. RewardBatch is client-streaming: many requests in, one response at the end. Watch is server-streaming: one request in, responses for as long as the caller stays. A call with stream on both sides is bidirectional; this API does not need one.
  • Report takes deltas, never running totals. Adding a total twice counts it twice; adding a delta once is exactly what happened. The exercise in chapter 12 built the tool for computing them.

Step 4: errors as status codes

An HTTP service says "404" or "409"; gRPC has its own small vocabulary of status codes (NotFound, AlreadyExists, InvalidArgument, DeadlineExceeded, Unavailable, and a dozen more) that every language shares. A client decides what to do from the code, not from the text: retry on Unavailable, give up on InvalidArgument. FromStore maps what the store returns onto those codes:

The default case matters. An unexpected error (a database driver message, say) becomes a generic Unavailable, never the raw text: the message may contain hostnames or worse, and the client cannot act on it anyway. The details go to the server's log. The test checks a "password" in the underlying error does not reach the caller:

Step 5: the aggregator

The aggregator holds the merged totals, accepts deltas, and streams the state to anyone watching. Its state is a mutex, the totals, a version number that increases with every change, and a channel:

The odd part is changed. How do you wake an unknown number of goroutines when something changes? A sync.Cond can, but it does not compose with select, so a waiter cannot also watch its context. The pattern used here is to give every change its own channel: waiters grab the current channel and wait for it to be closed; a change closes that channel (waking everyone at once, since a receive from a closed channel returns immediately) and installs a fresh one for the next round.

Each loop iteration takes a consistent snapshot under the lock (state, version and the channel to wait on) and sends it if it is new. A slow client skips intermediate versions, which is fine because every message is the full state. Two ways out: the client goes away (ctx.Done()), or the server is shutting down (Close, which sends Unavailable so the client knows to reconnect, step 8 explains why the server has to end the stream itself).

The aggregator's copy of the totals can fall behind the store: a feedback service records a reward, then crashes before reporting it. The store is the truth, so the aggregator periodically replaces its state from it, and only publishes when something actually differs:

That turns a lost message from a permanent error into a delay of at most one reconcile interval. It is the same idea as in chapter 12, with the hierarchy made explicit: the fast path may be wrong for a moment, the slow path fixes it.

Step 6: the feedback service

Feedback validates the reward, claims the pending selection in the store (atomically, as in chapter 10), and tells the aggregator. It knows the aggregator only through a one-method interface, so tests substitute a recorder and the gRPC client is one implementation:

The choice in tell is the interesting one. Once store.Reward has succeeded, the reward is durable. If telling the aggregator then fails, returning an error to the caller would make them retry a reward that was in fact recorded, and the retry would get AlreadyExists. So the failure is logged and the call succeeds; the aggregator catches up by reconciling. The report also runs on context.WithoutCancel plus its own short timeout: a caller whose deadline is nearly gone should not cause a half-delivered report.

RewardBatch is the client-streaming call. It reads requests until the client signals the end (io.EOF), rewards each, and sends a single summary. It accumulates one delta for the whole batch, so a batch of 10,000 rewards is one report to the aggregator, not 10,000, and that is where Merge-style addition earns its keep:

Step 7: the policy service

The policy service is the one users wait on. It selects, records the selection, and on the side follows the aggregator. It does not update its policy when a reward is handled, because it does not handle rewards; it learns from snapshots.

Apply replaces the policy's totals with the snapshot and refreshes the pending counts from the store, the same two steps as chapter 12's Sync, and remembers the snapshot's version so Stats can report how current this instance is.

Following the aggregator is a loop that must survive the aggregator going away. If the stream breaks, wait and resubscribe; meanwhile Select keeps answering from the last snapshot. A snapshot that fails validation is logged and skipped, not fatal: an instance that keeps its old view is better than one that drops its connection to a peer that just had a bad moment.

Step 8: interceptors, deadlines, shutdown

Middleware for gRPC is an interceptor: a function that receives the call, does something, and calls the next handler. There are separate types for unary and stream calls. Three go on every service here, outermost first: recovery (a panic becomes Internal instead of killing the process; the stack trace goes to the log, not the client), logging (one line per call with the code and duration, at a level that depends on the code), and a default deadline.

On deadlines. A gRPC client sets a deadline for a call, and it travels with the call: the server's handler sees it on its context, and so does any further call the handler makes. When the deadline passes, every hop is cancelled, not only the first. This is the same context from chapter 7, now spanning processes. The default-deadline interceptor exists for clients that forget to set one; without it a stuck handler would hold its resources forever. The tests check that the client's own deadline is left alone, that it does reach the handler, and that a panic leaves the server able to answer the next call:

Then serving. rpcx.Serve registers the gRPC health service (the standard protocol that load balancers, Kubernetes and grpc_health_probe understand), and on shutdown marks every service NOT_SERVING and calls GracefulStop, which stops accepting new calls and waits for running ones. There is one trap. To GracefulStop, a Watch stream is a running call, and one that only ends when the client leaves. An aggregator asked to stop would wait out the whole grace period and then have its connections cut. The OnStopping hook lets the aggregator end its streams first (the integration test below hangs for the full grace period if you remove it and stop the aggregator before its policy services).

The connections here use insecure.NewCredentials(): plain text, no authentication. That is right for loopback and for a private network you trust. What the output shows:

  • Policy B reports outcomes for selections made on policy A, and marks the unrewarded selection as pending (pending=1 on arm 2). Neither happened through any direct connection between A and B.
  • The four status codes come back by name. A repeated reward is AlreadyExists, an unknown id NotFound, a reward of 5 InvalidArgument, and a call with an impossible deadline DeadlineExceeded.

Exercises

Starters and tests are in exercises/ch13. The module has the gRPC dependency already.

1. Exponential backoff

The policy service waits a fixed time before resubscribing. Implement Backoff(attempt, base, max) in exercises/ch13/ex1: base, then double each attempt, capped at max, without overflowing for large attempt numbers. A peer that has just come back up should not be hit with a full-rate retry storm from every client at once.

Reference answer

Comparing d > max/2 before doubling avoids ever computing a value past max, so nothing can overflow however large attempt is; a shift like base << attempt wraps to zero or negative around attempt 63. Real clients also add random jitter, as in the chapter 12 exercise, so that clients that failed together do not retry together.

2. Limit calls in flight

Write an interceptor in exercises/ch13/ex2, MaxInFlight(n), that lets at most n unary calls run at once and rejects the rest at once with ResourceExhausted. Slots must come back even when the handler fails or panics.

Reference answer

A buffered channel is a counting semaphore: a send takes a slot and a receive gives it back, and the non-blocking select with a default is what turns "full" into an immediate rejection instead of a wait. defer returns the slot on every path, including a panic. Rejecting early is deliberate: a queue in front of an overloaded service only turns overload into latency, and the client would rather hear "busy" and decide.

3. Wait for a change

Implement Latest[T] in exercises/ch13/ex3: a value with a version, where Wait(ctx, after) blocks until the version exceeds after. It is the aggregator's Watch loop with gRPC taken away, and a generic type this time.

Reference answer

The same close-and-replace channel as the aggregator. Wait reads the value, the version and the channel under one lock, so a Set cannot slip in between "no change yet" and "start waiting"; without that, a wakeup could be lost. A follower that passes the version it last saw never blocks on a change it already has and, if the writer is faster than it, skips straight to the latest.
