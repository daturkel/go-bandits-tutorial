03 Part I: Language core · Chapter 3

Errors, tests, benchmarks

Make failure explicit with error values, then pin behaviour down with table-driven tests, golden files and benchmarks.

Starting point

Work in ch03/start in your clone of the repository. It is the previous chapter's finished project with the parts you will write left out, so every chapter begins from a project known to work. Run go test ./... there to see what is missing. To start over, git restore ch03/start; to keep the original untouched, copy the folder somewhere else first.

What you will build

Chapter 2 left failure modes open: a probability of 1.7 is accepted, an unknown scenario comes back as a bare false, and a misbehaving policy crashes the runner with an index error. This chapter turns each into an explicit, testable error, then puts a real test suite around the simulator: table-driven tests, a golden-file test for the command line's output, and a benchmark that says what one policy step costs.

The Go in this chapter

  • Errors as values. error is an interface with one method. A function that can fail returns one, and the caller deals with it on the next line.
  • Sentinels and error types. A package-level value answers "what went wrong"; a struct answers "where, and with what".
  • Wrapping. %w, errors.Is, errors.As and errors.Join add context without losing the cause.
  • The typed-nil trap promised in chapter 2.
  • Testing. The testing package, table-driven tests and subtests, golden files, benchmarks with b.Loop, coverage, gofmt and go vet.

Errors are values

Go has no exceptions. A function that can fail returns an error as its last result, and the caller decides what to do on the very next line:

error is an interface with one method, Error() string, so the same mechanism covers a plain message, a rich struct, and a chain of causes.

Go vs. Python

In Python an exception unwinds the stack until something catches it, and any line can raise. In Go, control flow is visible: every place that can fail says so in its signature, and every caller writes down what happens. It is more typing, but reading a function shows all of its exits. Unwinding exists (panic and recover) but is reserved for bugs. If a caller could reasonably cause the failure, return an error; if only a programmer mistake could, panic.

The error vocabulary for the project lives in errors.go. The sentinels and the type are given; two methods are yours.

Task 1: make ArmError an error that unwraps

There are two kinds of error here. Sentinels like ErrNoArms are package-level values made with errors.New; they answer "what went wrong?" and callers compare against them with errors.Is. Error types like ArmError carry data; they answer "where, or with what?" and callers extract them with errors.As.

Implement Error so the text reads arm 3: at least one arm is required (arm index, then the wrapped error's own message), and Unwrap so it returns the wrapped error. Unwrap is what links an outer error to the one inside it: it is why errors.Is(err, ErrInvalidProbability) can see through an ArmError. Run go test -run ArmError ./bandit.

Answer

The receivers are pointers, so *ArmError is the error type: code creates and matches it as a pointer, &ArmError{...}. The task's title asks for an ArmError that satisfies error; the compiler checks that wherever one is returned as an error.

Validating the environment

Task 2: NewEnv reports every bad probability

Reporting all problems at once is kinder than making the user fix them one at a time. Follow the comment. Three tools:

  • fmt.Errorf("...: %w", err) wraps an error: the message gains context and the original stays reachable through Unwrap. With %v you get the same text but the chain is cut, which is a bug whenever a caller needs the cause.
  • errors.Join(errs...) combines several errors into one. errors.Is and errors.As search every branch of it.
  • A test for "outside [0, 1]" that also has to reject NaN needs care: every comparison with NaN is false, so p < 0 || p > 1 lets NaN through.
Hint 1: the shape

Handle the empty case first and return. Then loop over the probabilities with for arm, p := range probs, appending to a var errs []error. After the loop, if errs is not empty, return the wrapped join.

Hint 2: the NaN-safe condition

Write the valid case and negate it: if !(p >= 0 && p <= 1). For NaN both comparisons are false, so the negation is true and NaN is rejected.

Answer

The %w in the last error makes the join reachable, and each element is an *ArmError around the sentinel, so both errors.Is(err, ErrInvalidProbability) and errors.As(err, &armErr) succeed on the result.

Constructors that refuse nonsense

Task 4: validate in NewEpsilonGreedy and NewUCB1

Follow the comments. An epsilon error should carry the offending value: fmt.Errorf("%w: got %v", ErrInvalidEpsilon, epsilon) is the pattern, wrapping the sentinel and adding detail. Return nil for the policy along with the error.

Answer

Same NaN-safe trick as before: !(epsilon >= 0 && epsilon <= 1).

An interface value is a (type, value) pair and is nil only when both are empty. In direct, the type slot holds *main.Greedy, so the comparison with nil is false even though the pointer inside is nil, and the first method call would panic. Your NewPolicy must not do that.

Task 5: NewPolicy parses specs

The comment lists the behaviour. strings.Cut(spec, ":") returns the text before and after the first colon and whether one was found. Tests check the sentinel with errors.Is, that the strconv error is still reachable inside a bad-number error, and that a failed constructor gives back a literal nil Policy.

Hint 1: the shape

Cut the spec into name, arg, hasArg, then switch name. In the "epsgreedy" case, start with eps := defaultEpsilon and override it if hasArg. In the "ucb1" case, hasArg is an error.

Hint 2: parsing and wrapping

eps, err = strconv.ParseFloat(arg, 64); on failure, return nil, fmt.Errorf("policy %q: %w", spec, err). The %w keeps the *strconv.NumError reachable.

Hint 3: the typed-nil guard

Call the constructor into a variable, check err, and only then return the pointer as a Policy:

p, err := NewUCB1(nArms)
if err != nil {
    return nil, err // a literal nil interface
}
return p, nil

Writing return NewUCB1(nArms) would type-check and reintroduce the trap.

Answer

The unknown-name error uses %w with ErrUnknownPolicy and lists PolicyNames(), just as scenarios do. A regression test for the typed-nil case is in the suite, and chapter 4 removes the repetition with a generic helper.

A runner that does not trust its policy

A Policy is an interface anyone can implement, so Run should not trust the arm it returns.

Task 6: Run catches an out-of-range arm

Check the arm before using it. The error should carry three layers of context (the step, the policy's name, the arm and the arm count) and wrap ErrArmOutOfRange, so a caller can test for the category without parsing text. Return the partial res with it.

Answer

Returning a partial result alongside an error is legal, but by convention the other results are only meaningful when err == nil; the doc comment states the exception so callers know.

A testable main

A function that calls os.Exit cannot be tested. The standard fix is to move the work into a function that takes its inputs and outputs as parameters and returns an error, leaving main a thin shell. That is already done in your starter:

flag.ContinueOnError makes flag parsing return errors instead of exiting, and io.Writer lets tests capture output in a buffer while main passes os.Stdout. A second sentinel, errUsage, marks "you invoked the program wrong", so main exits with status 2 for those and 1 for everything else; with the two-%w form of fmt.Errorf (Go 1.20+) the error keeps both the usage marker and the specific cause. Tests

A test is a function TestXxx(t *testing.T) in a file ending in _test.go, in the same directory as the code. There are no fixtures and no assertion library: you use ordinary if statements and report with t.Errorf (mark failed, keep going) or t.Fatalf (mark failed, stop this test).

Table-driven tests and subtests

For a function with many cases, the idiomatic shape is a slice of structs, one per case, run in a loop with t.Run. Each case becomes a named subtest that can pass, fail and be selected on its own. This is the test for NewEnv that your Task 2 code passes:

Adding a case is one line. The test checks both ways of inspecting an error: errors.Is for the category and errors.As to reach the *ArmError inside the join and the wrapper.

Subtest names come from the case's name field with spaces turned into underscores; the last policy case has an empty spec, so Go names it #00. Run one case with go test -run 'TestNewEnvValidation/nan'.

Task 7: write the table test for Scenario

Your first test from scratch. Cases go in a slice of an anonymous struct; use errors.Is(err, tc.wantErr), which is true when both are nil, so one line handles success and failure. slices.Equal compares slices.

Hint: the skeleton 
tests := []struct {
    name      string
    wantProbs []float64
    wantErr   error
}{
    {name: "easy", wantProbs: []float64{0.2, 0.5, 0.8}},
    // ...
}
for _, tc := range tests {
    t.Run(tc.name, func(t *testing.T) {
        probs, err := Scenario(tc.name)
        // compare err, then probs
    })
}
Answer

Since Go 1.22 each loop iteration has its own tc, so capturing it in the subtest closure is safe. The second test guards a bug the compiler cannot see: a Scenario that returns the shared slice instead of a copy passes the first test and fails this one.

Determinism and a golden file

Because every random draw comes from a seeded generator, simulations are ordinary deterministic functions and can be tested with equality. The command's whole output is pinned with a golden file: the expected text lives in testdata/ (a directory the Go tool ignores when building), and the test compares against it:

-update is a flag the test registers itself. When you change behaviour on purpose, go test -run TestGolden -update rewrites the file and git diff shows exactly what changed. If a refactor shifts a number by accident, the test tells you.

gofmt and go vet

gofmt is the single canonical formatter: no config, no style debates, and gofmt -l . lists files that differ. go vet is a static checker for mistakes the compiler accepts, such as a format-verb mismatch:

Both belong in your editor's save hook and in CI. go test also runs a subset of vet's checks automatically.

Benchmarks

A benchmark is a function BenchmarkXxx(b *testing.B). Since Go 1.24 the loop is for b.Loop() { ... }: the framework decides how many iterations to run, and setup before the loop is excluded from the timing. (Older code writes for i := 0; i < b.N; i++; it still works.)

Task 8: benchmark one policy step

Write BenchmarkSelectUpdate as its comment describes. b.Run creates a sub-benchmark per policy and b.ReportAllocs() adds memory columns. Run only benchmarks with go test -run '^$' -bench . -benchmem ./bandit (-run '^$' selects no tests).

Answer

The policy is built before b.Loop, so construction is not timed. The second benchmark, BenchmarkRun, was given and measures a whole 10,000-step simulation.

Read the columns as: iterations run, nanoseconds per operation, bytes allocated per operation, allocations per operation. On the machine that produced this output, one Select plus Update costs on the order of a hundred nanoseconds with zero allocations, and a whole 10,000-step run takes about a millisecond. The 82 KB and 11 allocations per run are setup costs paid once per simulation (the 80 KB regret curve, plus the environment, policy and generators the benchmark builds inside its loop), not per-step garbage. Timings are hardware-specific; only the relationships transfer. That matters later: when the service is under load (chapter 11), "zero allocations per decision" is the property to protect.

Benchmarks tell you what a change did, not what to change. Compare runs with benchstat and profile with pprof, which chapter 11 introduces.

Coverage

Coverage shows which lines tests execute, not whether they check anything. The uncovered part of the root package is mostly main itself, which is exactly why the logic was moved into run.

Answer

Extra 2: remove an allocation

Make Normalize write into dst so a caller who reuses a buffer pays nothing. The test uses testing.AllocsPerRun and requires zero allocations when dst has capacity.

Answer

dst = dst[:0] keeps the backing array but resets the length, and append only allocates if the capacity runs out. This append-into-a-caller-buffer shape is used throughout the standard library (strconv.AppendInt, for one); functions like it usually have Append in the name.
