05 Part II: Concurrency · Chapter 5

Goroutines and channels

Run simulations in parallel with fan-out and fan-in.

Starting point

Your own project as it stood at the end of Chapter 4. If yours has drifted, or you are skipping ahead, tools/start.sh ch04 work/banditlab copies the reference version into a new directory.

What you will build

A parallel version of the comparison harness. Chapter 4's Compare runs 400 independent simulations one after another; here each run gets its own goroutine, the results come back over a channel, and the report is assembled from them. On four cores the benchmark below drops from about 0.7 seconds to about 0.2, with output byte-for-byte identical to the sequential version.

The simulations are a good first concurrent workload because they share nothing: each has its own environment, policy and random generator. That lets this chapter concentrate on goroutines and channels. Chapter 6 deals with what happens when goroutines do share state.

Step 1: goroutines and channels on their own

Putting go in front of a function call starts it in a new goroutine and returns immediately. A goroutine is a lightweight thread managed by the Go runtime rather than the operating system. It starts with a stack of a few kilobytes that grows as needed, so programs routinely run tens of thousands at once. The runtime multiplexes them onto a small pool of OS threads, by default one per CPU core.

Go vs. Python

Python has two concurrency models, and neither maps directly. Threads share memory but the GIL lets only one run Python bytecode at a time, so CPU-bound work does not speed up; multiprocessing gets real parallelism at the price of separate processes and pickled messages. asyncio multiplexes many tasks on one thread, and every function that can wait must be marked async and called with await. Goroutines are closer to threads that are cheap and truly parallel: any ordinary function can be started with go, blocking calls are fine because the runtime parks the goroutine and runs another, and there is no async colouring to spread through your code. The trade-off is that goroutines share memory by default, which is what chapter 6 is about.

Goroutines need a way to hand values to each other. A channel is a typed conduit: ch <- v sends, v := <-ch receives. On an unbuffered channel a send waits until another goroutine is ready to receive, and the reverse, so it doubles as synchronisation. A buffered channel, make(chan int, 2), holds up to that many values before a send waits. The program below shows both, and the pattern for ending a stream:

Things to take from it:

  • sync.WaitGroup counts running goroutines: Add(1) before starting one, Done() when it finishes (deferred, so it runs on every exit path), Wait() blocks until the count is zero.
  • Only the sending side closes a channel, and only when nothing else will send. Here a helper goroutine waits for all senders and then closes. Sending on a closed channel panics; receiving from one returns what is left and then the zero value.
  • for v := range ch receives until the channel is closed and drained. v, ok := <-ch reports the same condition with ok == false.
  • The three messages arrive in whatever order the goroutines finish. The program counts them because printing them would make the output differ between runs.

When every goroutine is blocked, the runtime detects it and aborts, naming the state each one is stuck in (chan send here). The detector only fires when all goroutines are stuck. In a larger program, one blocked goroutine among many running ones is silently leaked. Chapter 7 covers how to avoid and find those.

Step 2: fan out, fan in

The shape of the harness is one job per (policy, seed) pair, all independent. The parallel version starts a goroutine for each job, and every goroutine sends its outcome on one shared channel; the collecting loop is the fan-in.

The pieces, in order:

  1. Per-job goroutines. Each closure captures p, policySpec and i. Since Go 1.22 every iteration of a for loop has its own copy of the loop variables, so this is safe. Older code had to write p := p first, and if you read such code, that is why.
  2. defer wg.Done() guarantees the count drops even if the goroutine returns early.
  3. The closer. A separate goroutine waits for every worker and then closes results. It cannot be the collecting loop itself, since that loop is what the workers are waiting on.
  4. The collector is the range loop. It runs on the calling goroutine and is the only one that touches runs, names and errs, so those need no protection.

The loop keeps receiving after it sees an error rather than returning at once. If it returned early, the remaining workers would block forever trying to send to a channel nobody reads, and those goroutines would leak. Draining everything is the simplest way to be sure none are left behind; chapter 7 shows the alternative, cancellation.

Step 3: keep the output deterministic

Goroutines finish in an arbitrary order, and the report must not depend on it. The approach is to give every job a fixed slot. An outcome carries its policy and seed indexes, and the collector stores it at runs[policy][seed]. Because each seed's random streams are independent (chapter 1), the same slot always receives the same curve, and summarise then reads them in index order. Appending outcomes as they arrive would produce a report that changes from run to run.

Errors get the same treatment. If two policies are misspelled, which error should you see? Whichever goroutine happened to fail first would be a different answer on each run. firstError scans the stored errors in (policy, seed) order, so the answer is always the earliest:

What this version does not do

  • It starts as many goroutines as there are jobs. With 400 runs that is fine. With 400,000 they would all exist at once, each holding a 40 KB regret curve. The usual remedy is a fixed number of worker goroutines pulling jobs from a channel, which chapter 7 builds.
  • It cannot be cancelled. Once started, Compare runs to the end. Chapter 7 adds context.Context.
  • It shares nothing mutable. That is the reason no locks appear. When goroutines do share a policy, as a server's request handlers will, the next chapter's tools are needed.

Exercises

Starters and tests are in exercises/ch05. Their tests use timeouts, so a wrong answer fails after a couple of seconds instead of hanging.

1. ParallelMap

Implement ParallelMap[T, U any](xs []T, f func(T) U) []U in exercises/ch05/ex1: call f on every element in its own goroutine and return the results in input order. One test makes all calls wait for each other, so it only passes if they really overlap.

Reference answer

Each goroutine writes to out[i], a different memory location from every other goroutine's, so there is no race and no lock. wg.Wait() also guarantees the writes are visible to the caller before it reads the slice. This is the same trick as the harness's runs[policy][seed] slots.

2. Merge several channels into one

Implement Merge(chans ...<-chan int) <-chan int in exercises/ch05/ex2. Every value from any input must appear on the output, and the output must close after all inputs have closed. <-chan int is a receive-only channel; a function that only reads from a channel should say so in its type.

Reference answer

This is fan-in as a reusable function. One forwarding goroutine per input, plus one closer that waits for them all. Closing from the forwarders themselves would be a bug: the first one to finish would close a channel the others are still sending to, and that panics.

3. A two-stage pipeline

In exercises/ch05/ex3, implement Generate(nums ...int) <-chan int (send the numbers, then close) and Square(in <-chan int) <-chan int (square each value, close when the input closes). The test chains them: Square(Square(Generate(1, 2, 3))).

Reference answer

Each stage owns the channel it creates: it is the only sender, so it is the one that closes it, and defer close(out) makes that hard to forget. Stages connected this way run concurrently, so a slow consumer applies backpressure all the way up the chain through the unbuffered sends. A consumer that stops reading early would strand the upstream goroutines, and chapter 7 fixes that with cancellation.
