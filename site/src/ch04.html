What you will build

The third policy, Thompson sampling, and a comparison harness that runs every policy across many seeds and turns the results into a table, a CSV file, and the regret chart below. One seed can mislead; a hundred seeds with an error band show whether a difference is real, and the rest of the course relies on that.

Generics arrive along the way, because Thompson sampling and the harness both have small pieces that are the same for several types. Just as important is where they do not help, and the chapter marks both.

Your first generic function

Both epsilon-greedy (with ties broken at random) and Thompson sampling need "the index of the largest element". In chapter 1 that loop lived inside EpsilonGreedy and worked on []float64 only. It is now needed for several slices of floats, and would be equally useful on counts or names. This is a straightforward case for generics: the algorithm does not depend on the element type, only on the ability to compare two of them.

Task 1: make Argmax generic

Reading a generic signature: [T cmp.Ordered] declares a type parameter T and constrains it. A constraint is an interface, but one that describes a set of types; cmp.Ordered in the standard library is the set of all types that support <, > and friends (all integer and float types, and string). Inside the function you may do anything the constraint permits.

Write it as the comment says. The tests call it with floats, ints and strings, so until this compiles no test in the bandit package can run. That is expected: everything else waits on this task. Run go test -run Argmax ./bandit. Once it passes, all of the bandit tests compile again, and from here on each task turns failing tests green.

Hint 1: the signature

func Argmax[T cmp.Ordered](xs []T, rng *rand.Rand) int, and add "cmp" to the imports.

Hint 2: the loop

Start with if len(xs) == 0 { panic("bandit.Argmax: empty slice") }. The built-in panic(v) stops the program with a message and a stack trace; it is for programmer mistakes, such as asking for the largest element of nothing, rather than for errors a caller should handle. Then keep best (an index) and ties (how many elements are tied with it). For each later element, cmp.Compare(x, y T) int returns a negative number if x < y, zero if they are equal and a positive number if x > y: here cmp.Compare(xs[i], xs[best]). Greater: new best, ties = 1. Equal, and rng != nil: increment ties, and replace best with probability 1/ties, which is rng.IntN(ties) == 0. That picks uniformly among the tied elements without remembering them.

Answer

At the call site you rarely write the type: Argmax(p.means, p.rng) works because the compiler infers T = float64 from the argument. You can be explicit with Argmax[int](counts, nil). A slice of a type that is not ordered ([]struct{}, say) is rejected at compile time with a clear message, not at run time.

Task 2: use Argmax in both policies

Your EpsilonGreedy and UCB1 each contain their own "find the largest" loop. Replace both with calls to Argmax:

  • In EpsilonGreedy.Select, the greedy branch becomes Argmax(p.means, p.rng): random tie-breaking, which is what your greedy method did. Delete greedy.
  • UCB1.Select needs its scores in a slice to pass to Argmax. Add a field scores []float64 to UCB1, allocate it in NewUCB1 with make, fill p.scores[arm] in the loop instead of tracking the best score, and return Argmax(p.scores, nil). Passing nil for the generator means "lowest index wins", which keeps UCB1 deterministic.

The existing tests for both policies are the check: go test ./bandit should fail only on the Thompson and policy tests that the next tasks deal with.

Answer

Allocating scores once, in the constructor, keeps Select free of allocations, the property chapter 3's benchmark measured. Using nil to mean "lowest index" is a compromise; if the two behaviours diverged further, two functions would be clearer.

Go vs. Python

A Python function taking a list already works on any element type that supports >, checked at run time, and TypeVar annotations are advisory. Go generics are checked at compile time and the constraint states what the function needs. Underneath, Go does not box everything as an object; the compiler generates code specialised by the shape of the type arguments, so Argmax on []float64 is as fast as a hand-written loop. What Go deliberately does not have: generic methods (a method cannot introduce its own type parameters, only use those of its receiver type), operator overloading, or inheritance-style constraints. Constraints describe sets of types and operations, nothing more.

Thompson sampling

Epsilon-greedy explores blindly and UCB1 explores by a formula. Thompson sampling asks a more direct question: given what I have seen, what could each arm's true probability be?

For a Bernoulli arm the answer has a closed form. Start with a uniform belief, Beta(1, 1). After s successes and f failures the belief becomes Beta(1 + s, 1 + f): the Beta distribution is the conjugate prior for Bernoulli data, so updating means adding to two counters. To choose an arm, draw one sample from each arm's Beta and pull the arm with the largest draw. An arm with little data has a wide posterior and will sometimes draw high (exploration); an arm with a lot of data and a low mean will almost never win (exploitation). No ε and no bonus formula to tune.

Those two counters per arm are worth remembering: they are plain sums, and in chapter 12 they are what lets replicas combine what they have each learned.

The standard library's math/rand/v2 has uniform, normal and exponential draws but no Beta. A Beta sample can be built from two Gamma samples, X / (X + Y), and a Gamma sample from the Marsaglia-Tsang rejection method, which needs only normal and uniform draws. That is numerics rather than Go, so it is given:

How do you test a random-number routine? By its moments. A Beta(a, b) has mean a / (a + b) and variance ab / ((a + b)²(a + b + 1)); with a seeded generator and 100,000 draws the sample statistics land close to those, and the same seed means the test can never flake:

The parameter sets include (0.5, 0.5) and (1, 100) on purpose: shapes below 1 exercise the boost branch, and a heavily skewed shape exercises the tail.

Where generics do not help

Your chapter 3 NewPolicy repeats a four-line if err != nil block for each policy, to avoid returning a typed nil, and adding Thompson sampling would make it three. It is tempting to reach for a type parameter to remove the repetition. The better tool is one you already have: a function whose parameter is the Policy interface.

Task 4: Thompson in NewPolicy, via asPolicy

In your policy.go:

  • Add a helper asPolicy(p Policy, err error) (Policy, error) that returns a plain nil and the error when err is set, and p otherwise.
  • Use it for every policy: return asPolicy(NewUCB1(nArms)). That call is legal because a call that returns two values can be passed directly as the two arguments of another function, and it is safe because the helper, not the caller, decides what nil to return.
  • Add "thompson" to PolicyNames and to the switch, built with NewThompson(nArms, rng). Like ucb1, it takes no argument.

The tests TestNewPolicy and TestNewPolicyFailureReturnsNilInterface check both the new policy and the trap. Run go test -run Policy ./bandit.

Answer

No type parameter is needed: the function only asks "is there an error?", not anything about the concrete type. A rule of thumb that holds up: if a function only calls methods, take an interface; if it needs to hold, compare, or return values of the caller's own type, use a type parameter.

The same reasoning is why the Policy interface stays an interface. Turning the runner into Run[P Policy](env, pol P, ...) would work, but every caller would pay for a more complicated signature and gain nothing, and you could not put policies of different kinds in one slice of a type parameter (you can in a []Policy, which the harness relies on).

A numeric helper package

The harness needs the mean and the standard error of a set of numbers, and later chapters will want them for integers (latencies, counts) as well as floats. That is a second natural home for generics, this time with a constraint we define ourselves.

Task 5: stat.Number and stat.Mean

A constraint can be a type set: a union of types written with |. The ~ in front of a type means "any type whose underlying type is this one", so a named type such as type Reward float64 qualifies; without the tilde it would not. Widen Number to ~int | ~int64 | ~float32 | ~float64, then write Mean; for an empty slice it returns not-a-number, which math.NaN() float64 produces. The tests call it with ints and a named float type, so they do not compile until Number is widened. Inside Mean, float64(x) is the only operation you need, and it is legal because every member of the union is numeric.

Answer

The constraint guarantees at compile time that the body is valid for every type the function may be called with. Sample[T any], below, is the opposite extreme: no operations on the elements at all, only copying, so its constraint is any.

The harness

The harness answers one question: how much regret does each policy accumulate, on average, in a given scenario? It runs each policy against many independent environments (one per seed), collects each run's regret curve, and reduces them to the mean and standard error at every step. The types and the reduction are given; the loop that drives the runs is your task.

Some design points before you write it:

  • The policies are strings. Spec.Policies holds the same spec strings the command line accepts, and runOnce builds a fresh environment and policy for every seed through bandit.NewPolicy. A policy has state, so each run needs its own.
  • Seeds are consecutive integers from BaseSeed, which makes runs reproducible: Compare with the same Spec always returns the same numbers, which a test pins down.
  • Errors carry context (which policy, which seed) with %w, as in the previous chapter.
  • It runs sequentially. Everything here is independent per (policy, seed), which is the ideal shape for parallel work. Chapter 5 uses this exact function as its first concurrency task.

An outer loop over spec.Policies and an inner loop over seeds, for i := range spec.Seeds. Answer

Up-front validation means summarise can assume at least one run and one step. Because the seeds are consecutive integers, any failure names the exact run to reproduce.

CSV and SVG output

Results should be usable outside Go. CSV is one encoding/csv writer, and it is given:

The method takes an io.Writer, not a filename. A file, a bytes.Buffer in a test, an HTTP response body and os.Stdout are all writers, and io.Writer is one of the most widely used interfaces in the standard library. It uses the generic stat.Sample to thin 5,000 steps to 100 rows per policy, so the file is small enough to open anywhere:

The chart is generated the same way, as a text SVG written with fmt.Fprintf into a strings.Builder. Two details make it fit a documentation site. First, colours are CSS custom properties with fallbacks (var(--series-1)), so the page can restyle it for dark mode while the standalone file still looks right. Second, it carries a <title> and <desc> that state the final numbers in words for screen readers, and each line is labelled directly at its right end with a marker in its colour. Lines also differ by dash pattern, so identity never rests on colour alone.

"Nice" tick values (round steps of 1, 2 or 5 times a power of ten) are the one piece of real plotting logic. The rest of WriteSVG is coordinate arithmetic: map a step to an x position, a regret to a y position, emit a <polyline> for each policy's mean and a translucent <polygon> for its ±1 standard-error band. What the numbers say

Run the harness on three scenarios with 100 seeds of 5,000 steps each:

The ± is the standard error of the mean regret across the 100 seeds. The mean curve is plotted at the top of this page; here are the other two scenarios:

What to take from this, and what not to:

  • Thompson sampling has the lowest mean regret in all three scenarios, by a wide margin in easy and needle. Its curve visibly flattens, which is what logarithmic regret looks like on a linear axis.
  • UCB1 is the worst of the four on needle and close. That comes from the standard √(2 ln t / n) bonus, which is large relative to the gaps in these scenarios: with ten arms, it keeps sampling all nine 0.10 arms until, roughly, the bonus falls below the 0.20 gap. Tuned or variance-aware UCB variants do much better; this is plain UCB1.
  • Epsilon-greedy's result depends heavily on ε, and the error bars tell you why. At ε = 0.01 the standard error is large (38.6 on needle, 18.8 on easy): some seeds lock onto a good arm early and pay almost nothing, others lock onto a bad arm and stay wrong for thousands of steps. On easy its mean beats ε = 0.1, but a policy whose outcome is a coin flip is not what you want in production. A single seed can't show this at all.
  • These are three fixed scenarios and one horizon. Nothing here says Thompson is always better; with delayed or batched feedback, which the serving chapters introduce, the ranking can change, and chapter 12 measures exactly that.

What you learned

  • A type parameter with a constraint ([T cmp.Ordered]) writes one function for many types; callers rarely spell out the type, because the compiler infers it.
  • A constraint can be a type set, ~int | ~float64, where ~ admits named types with that underlying type.
  • When a function only calls methods, an interface parameter is simpler than a type parameter, and a slice of an interface can hold different kinds of value.
  • io.Writer as a parameter lets the same code write to a file, a buffer in a test, or standard output; defer runs clean-up on every return path.
  • One seed proves little: compare policies over many seeds, with error bars.

Extra tasks

Three more, in _extras/ch04/extras.go with tests next to it; run them with go test ./_extras/ch04. They practise generic functions with two type parameters and a generic type, and they use the stat.Number constraint from Task 5.

Extra 1: SumBy and MaxBy

Total of a projection (say, total reward across a slice of result structs) and the element with the largest key. Notice that callers never write the type arguments. The second parameter, f func(T) N, is a function: call it as f(x). To return "nothing" for any type T, declare var zero T, which holds that type's zero value.

Answer

Two type parameters is normal when a function relates two types. var sum N is the generic way to say "zero of whatever this is": no literal 0 would compile for every N. MaxBy returns (T, bool) rather than a special value, the comma-ok idiom from chapter 1 applied to a generic type.

Extra 2: quantiles for a percentile band

A ±1 standard-error band assumes the regret is roughly bell-shaped across seeds; the spread in the ε = 0.01 results suggests it is not. Implement Quantile as its comment describes. Three library functions help: slices.Sort(x S) sorts a slice in place (so sort a copy; slices.Clone from chapter 1 makes one), and math.Floor(x float64) float64 and math.Ceil(x float64) float64 round down and up, returning a float64 you convert back with int(...) to use as an index. As an open-ended follow-up with no test, add a -band percentile flag to compare that draws the 10th to 90th percentile instead.

Answer

slices.Clone before slices.Sort protects the caller's slice, since sorting is in place. !(q >= 0 && q <= 1) handles NaN for the same reason as chapter 3's probability check.

Extra 3: a generic type with a useful zero value

Counter[K comparable] counts occurrences of keys (arms, policy names, anything comparable). Implement the three methods so that var c Counter[string] is usable immediately, with no constructor. The struct's map starts out nil: reading from a nil map is fine, but writing to one panics, so Inc must create it with make(map[K]int) the first time.

Answer

Generic types take type parameters on the type, and its methods repeat them in the receiver, (c *Counter[K]). The zero-value trick relies on two facts about maps: reading from a nil map is fine, and only writing panics, so Inc creates the map lazily. It is the pattern behind sync.Mutex and bytes.Buffer, both usable as declared. comparable is required because map keys must support ==.
