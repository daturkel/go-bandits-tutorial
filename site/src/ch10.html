What you will build

A service that remembers. Today banditd forgets everything when it stops: what it learned, and which selections were still waiting for a reward. You will store both in PostgreSQL, so a restart, a deploy, or a crash loses nothing. Along the way you will settle what a reward is allowed to do (arrive once, arrive late, never arrive) and back the answer with database guarantees and tests against a real database.

The chapter also introduces a pattern you will reuse: a small interface with two implementations, an in-memory one for tests and local runs and a PostgreSQL one for production, both held to the same behaviour by one shared test suite.

Concepts introduced

  • What state to persist, and why totals rather than the policy
  • Connecting to PostgreSQL with pgx; connection pools; parameterised queries
  • Atomic single statements (a CTE) and explicit transactions
  • Constraints and the database clock as sources of correctness
  • //go:embed
  • Injecting a clock to test expiry
  • Conformance tests shared by several implementations
  • Integration tests: a real database, one schema per test, skipping when it is absent
  • Delayed feedback: time-to-live, late rewards, and what silence means

What to store

There are two kinds of state, and they have different lifetimes.

  • What the policy has learned. Rather than saving the policy object, save the smallest summary from which any policy can be rebuilt: for each arm, the number of rewards recorded and their sum. Epsilon-greedy and UCB1 need the count and the mean (sum divided by count). Thompson sampling needs the successes and failures, which are the sum and the count minus the sum. This summary is the ArmTotals below. It has two properties that will matter later: it does not depend on which policy is running, so you can switch policies without losing data, and totals from different places add, which is what lets replicas combine what they know (chapter 12).
  • Selections waiting for a reward. Each one is a request ID, the arm it returned, and a deadline. The store keeps these until the reward arrives or the deadline passes.

The running policy stays in memory, where selecting is fast. The database is the source of truth, and the in-memory policy is a cache of it: rebuilt at startup with Restore, and updated as rewards arrive.

Step 1: restoring a policy from totals

Restoring is validated before anything is changed: a totals list with the wrong number of arms, arms out of order, negative counts, or a reward sum larger than the number of rewards is rejected with ErrBadTotals, and the policy is left as it was. (A sum can only exceed the count by floating-point noise, hence the small tolerance.) The check is written so that NaN fails it, for the reason given in chapter 3.

Step 2: the Store interface

The methods are chosen so that each is one atomic step from the caller's point of view:

Some choices to note:

  • Reward claims and counts together. The two facts, "this selection has been rewarded" and "this arm's totals went up", must change together or not at all. If a crash could separate them, a reward could be lost or counted twice.
  • AddPending takes a ttl, not a deadline. A deadline computed by the application would be compared with the database's idea of "now", and with several replicas, their clocks disagree. Passing a duration lets the store do all comparisons against one clock.
  • Every method takes a context.Context, so a slow database can be given up on (chapter 7) and a cancelled request stops its queries.
  • The interface is defined next to its users' needs and is small (chapter 2's advice).

Step 4: PostgreSQL

The schema

The constraints do real work. PRIMARY KEY on request_id makes a duplicate ID an error instead of a silent overwrite. The REFERENCES arm_totals (arm) foreign key means a selection cannot name an arm that has no totals row, so the reward path can never claim a selection and then find nowhere to count it. The index on expires_at lets the sweep find old rows without reading the whole table. Every statement is IF NOT EXISTS, so running the schema twice is harmless.

The schema lives in its own .sql file and is compiled into the binary with //go:embed, so a single executable carries everything it needs and there is no file to lose at deploy time:

Details:

  • //go:embed schema.sql above a string (or []byte, or embed.FS for a directory) fills the variable at compile time. The blank import of embed is what enables it.
  • pgxpool is a pool of connections. A pool is what you want in a server: concurrent requests take connections from it, and each is returned when the query finishes. Pool.Exec, Query, and QueryRow handle that for you. Use the pool, not a single connection, unless you need a transaction (below).
  • The parameters $1, $2 are sent to the server separately from the SQL text. Never build SQL with string concatenation or fmt.Sprintf from values you did not write; parameters are what prevent SQL injection.
  • On start it creates rows for any arms that are missing, and refuses to start if the database has more arms than configured. Silently ignoring learned data because of a typo in a flag would be worse than a startup error. (Growing the number of arms is fine: new arms start empty.)

Adding a selection and claiming a reward

The claim is a single SQL statement with a common table expression (WITH claimed AS (...)). The inner UPDATE marks the pending row as rewarded, but only if it is not already rewarded and has not expired, and RETURNING arm passes the arm to the outer UPDATE, which adds to that arm's totals. A statement is atomic, so no transaction is needed for this. The WHERE clause is the entire argument for correctness.

What if twenty clients send the same reward at once? PostgreSQL's default isolation level (read committed) makes concurrent updates of one row take turns. The second UPDATE waits for the first to commit, then re-checks its WHERE clause against the row as it now is. It finds rewarded = true, matches nothing, and returns no rows. Exactly one caller gets the arm.

When the statement returns no row, Reward runs a second query only to find out why, so that the caller can tell a duplicate (409) from an unknown or expired ID (404). That diagnosis is not part of the atomic step, and does not need to be.

Expiring selections, in a transaction

Expiry has several steps: delete the old rows, see which were never rewarded, and (optionally) count them as failures. These must succeed together, so this one uses an explicit transaction:

pgx.BeginFunc begins a transaction, runs the function, and commits if it returns nil. If the function returns an error or panics, it rolls back, so a failure halfway leaves the database as it was. The function uses tx, not the pool, for every statement, since only the tx connection is inside the transaction. pgx.CollectRows with RowToStructByPos scans result rows into a slice of structs by column position.

The Select call has already run when the store write fails. That is harmless because selecting does not change what the policy has learned; the client just gets a 503 and can retry. Every store call gets its own timeout, derived from the request's context, so a stuck database cannot hold requests open indefinitely.

The mapping of store errors to HTTP statuses is the interesting part. ErrUnknownID becomes 404 and ErrAlreadyRewarded 409, as before, matched with errors.Is (chapter 3). Anything else is a store failure:

A store failure returns 503 with a generic message and logs the real error with the request ID. The database's error text (host names, driver messages) is for operators, not clients. The health check now pings the store, so a load balancer stops routing to an instance that has lost its database.

The ordering in handleReward matters: the durable write happens first and the in-memory update second. If the process dies between them, the database has the reward and the restart rebuilds the policy from it. The reverse order could show a reward in memory that was never saved.

ExpireReward is a *float64 for the same reason Reward was one in chapter 8: nil means "do not count expired selections at all", while a pointer to 0 means "count them as a reward of zero", and a plain float64 cannot express both.

The sweeping goroutine follows the lifecycle rule from chapter 7: it has a context that ends it, and run waits for it with a WaitGroup before the deferred st.Close() runs. Closing the pool under a sweep in progress would turn a clean shutdown into an error.

Step 8: late feedback, or none

A reward names a selection, and sometimes the reward comes late or never. The store forces decisions the code cannot avoid, and they are modelling decisions as much as engineering ones.

  • How long is a selection valid? BANDIT_PENDING_TTL, ten minutes by default. Choose it from the real distribution of feedback delay, for example a high percentile of it. Too short and good data is thrown away; too long and the table grows and stale rewards get attributed to decisions the world has moved past.
  • What happens to a reward after the deadline? It is refused with 404 and does not change anything.
  • What does silence mean? With BANDIT_EXPIRE_REWARD unset, an expired unrewarded selection is simply forgotten, as if it never happened. Set to 0, silence counts as a failure: a click never arrived, so the pull was worth nothing. Which is right depends on the application. "No conversion within seven days" is a legitimate zero; "the client crashed before it could report" is not, and counting it biases the policy against whichever arms are shown more often to flaky clients.

The next section shows the effect. There is a second, subtler consequence of delay, first seen in chapter 8: while selections wait for rewards, the policy cannot use them. Chapter 12 measures what that costs.

Step 9: watch it survive

This script runs the real banditd against a real PostgreSQL database three times. First it makes six rewarded selections and leaves one waiting. Then it restarts and looks at what survived, and shows the tables. Finally it runs with a 2-second time-to-live and counts silence as failure.

  • After the restart the per-arm counts are identical, and the selection made before the restart can still be rewarded (204). A second attempt is refused (409).
  • The tables show what the service holds: three totals rows, and the selections with their rewarded flag.
  • In the third run, four selections are made and never answered. Immediately after, the counts are unchanged, since nothing has been learned. A few seconds later the sweep has expired them and counted each as a reward of 0, and arm 0 now has five pulls and a mean of 0. A reward that arrives after the deadline gets 404.
  • All four unanswered selections chose arm 0, because, as chapter 8 showed, a deterministic policy repeats itself while it waits. So the whole batch of failures was charged to one arm. That is the delayed-feedback problem in miniature.

A note on Redis (design only, not implemented or run in this course)

Redis would suit the same job with a different shape. Pending selections could be plain keys with the deadline built in: SET pending:<id> <arm> NX EX 600 creates the key only if it does not exist and lets Redis delete it after ten minutes, so no sweep is needed for that part. Claiming a reward would be an atomic get-and-delete (GETDEL) or a small Lua script that also increments per-arm counters (HINCRBY totals:<arm> pulls 1), since Redis runs one command or script at a time. The trade-offs: Redis is faster and simpler for expiring keys, but its durability depends on how persistence (RDB snapshots, AOF logging) is configured, and it has no transactions across your own tables or constraints such as the foreign key above. Distinguishing "already rewarded" from "expired" would need a tombstone key. The Store interface is designed so that a Redis implementation could be dropped in and checked with the same storetest suite. A Redis server binary was available in the environment used to write this course, but no Redis code was written or tested, so treat this paragraph as a sketch.

Exercises

Starters and tests are in exercises/ch10. None needs a database.

1. Do something at most once per key

Implement Once in exercises/ch10/ex1: Do(key, f) runs f only if no earlier call for that key ran within the last ttl. Of many concurrent calls with the same key, exactly one runs f; the others return immediately without waiting. If f fails, the claim is released so a retry can run.

Reference answer

The claim is made under the lock and f runs outside it, so a slow action does not block other keys, and the 49 losers in the test return at once instead of queueing. Releasing the claim when f fails is what keeps a transient error from blocking the key for the whole window. This is the in-process shape of the SQL claim in step 4: check and mark in one indivisible step, then do the work.

2. A map with expiry

Implement the generic Expiring[K, V] in exercises/ch10/ex2: Set(k, v, ttl), Get(k) that stops returning a value at its deadline, Sweep() that removes expired entries and counts them, and Len(). It takes a clock, so the tests move time by hand.

Reference answer

Expiry is checked on read (Get refuses a dead entry) and reclaimed on Sweep, so correctness never depends on how often the sweep runs; the sweep only bounds memory. The comparison is !now.Before(expiresAt), making the deadline itself expired, the same half-open rule as the stores. Deleting from a map while ranging over it is allowed in Go.

3. Retry with backoff until the database is up

When a service and its database start together (chapter 14 will do exactly that), the database is often not ready yet. Implement Retry in exercises/ch10/ex3: call f up to attempts times, waiting base, 2*base, 4*base, ... (capped at max) between failures, stopping at once on a Permanent error or when the context ends. Also implement SleepContext. The sleeping function is a parameter, so the tests do not actually wait.

Reference answer

Passing sleep in makes the timing testable: the tests record the requested delays instead of waiting for them. errors.As finds the permanent wrapper anywhere in the error chain. The loop does not sleep after the final attempt, since nothing follows it. SleepContext uses a timer and a select rather than time.Sleep, because time.Sleep cannot be interrupted, and stops the timer so it is not left running.
