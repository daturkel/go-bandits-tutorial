What you will build

A way to share one bandit policy between many goroutines safely, which is what a server's request handlers will need in chapter 8. You will first watch sharing go wrong, in a plain counter and then in the policy itself, using the race detector to find it. Then you will fix it with a mutex-guarded wrapper, Locked, add lock-free call counters with sync/atomic, and measure what all that locking costs.

Chapter 5's harness needed none of this because its goroutines shared nothing. The moment two goroutines touch the same variable, correctness becomes your problem.

Step 1: see it fail

A data race is two goroutines accessing the same memory at the same time, at least one of them writing, with nothing to order them. The simplest victim is a counter. counter++ looks like one step but is three: read the value, add one, write it back. If two goroutines interleave those steps, both read 41, both write 42, and an increment vanishes. The unprotected total is far below a million, and it will be a different number each time you run it. The two correct versions differ in mechanism. A sync.Mutex lets one goroutine at a time through Lock…Unlock. An atomic.Int64 performs the read-modify-write as a single indivisible CPU operation.

Go vs. Python

Python threads can lose updates on n += 1 as well, because that statement is also several bytecodes. The GIL protects the interpreter's own data structures, not your logic, though it does make individual operations such as list.append effectively atomic. Go gives you no such cushion: nothing is implicitly atomic, and goroutines really do run in parallel, so races show up faster and are more damaging. Go also gives you a detector for them, which is the next step.

The race detector

Go can instrument a program to watch every memory access and report any that are unordered. You turn it on with -race on go run, go build or go test. It slows the program down several times and uses more memory, so it is for development and CI, not production. It reports only races that actually happen during that run, so tests that exercise concurrency are what make it useful, but it has no false positives: every report is a real bug.

The report (addresses and goroutine numbers differ on every run) gives both goroutines and the full stacks for the read and the earlier write, so you can see exactly which lines collide. And the collision is not in bandit code at all, but inside math/rand/v2: a *rand.Rand is not safe for concurrent use, because generating a number updates its internal state. Even a policy that only reads its counts in Select would fail this way, as long as it draws a random number. (The Update side has its own race on the counts.) Any type holding a generator inherits that restriction.

Step 3: the Locked wrapper

The simplest correct fix is to allow one goroutine into the policy at a time:

Points to notice:

  • The mutex sits next to what it guards and the comment says so. Go does not enforce the association; the convention is that every access to p holds mu.
  • defer l.mu.Unlock() right after Lock releases the mutex on every return path, including a panic. Forgetting to unlock on one branch is a classic bug, and defer removes it at the cost of a few nanoseconds.
  • Snapshot returns a copy made while the lock is held. Returning the policy's own slice would hand out live state that the next Update modifies, and the lock would protect nothing.
  • The call counters are atomics, outside the mutex. They are independent single numbers, which is what atomics are for, and reading them never has to wait for a Select in progress. A metrics endpoint can call Calls as often as it likes.
  • Name takes no lock. It reads only data fixed at construction. If it ever read something a method could change, it would need one.
  • Zero values help. sync.Mutex and the atomic types are ready to use as declared, so &Locked{p: p} is complete.

Step 4: test under the race detector

Under real concurrency the arm each goroutine receives depends on scheduling, so a test cannot check which arms were chosen. It checks what must be true regardless: no update may be lost, and the counters must agree.

The second test guards the other side: wrapping must not change what a single goroutine sees, so a seeded run through Locked matches the bare policy step for step.

Run with -race, the first test hammers each policy with eight goroutines and the detector watches every access. Take the lock out of Select and this test fails with the same kind of report as above.

This also tells you where not to use Locked. Simulations should stay single-goroutine per policy, as in chapter 5: run many independent simulations in parallel rather than sharing one. A policy hammered from many goroutines gives results that depend on scheduling, so runs are not reproducible even with fixed seeds.

Step 5: never copy a mutex

A sync.Mutex is a value with state. Copy one and you get two independent locks, so the copy protects nothing. The compiler will not stop you, but go vet will:

This is why NewLocked returns a pointer and the doc comment says never to copy the value. Any struct that contains a mutex or an atomic gets the same treatment, and it has the same consequence for method receivers: use pointer receivers, as chapter 2 recommended for anything with state. Step 6: what locking costs

Mutual exclusion makes the code correct, and turns parallel goroutines into a queue at the lock. Two benchmarks show the effect. b.RunParallel runs the benchmark body on several goroutines at once, and -cpu 1,4 repeats it with one and four procs. The first hammers Select plus Update, both writes. The second is 19 Snapshot reads for every Update, comparing Locked's plain mutex with a reader-writer version:

Read ns/op here as wall-clock time divided by total operations, so lower means higher throughput. Two results matter.

  • Four goroutines are slower than one. Select plus Update takes about 196 ns per operation on one proc and about 427 ns on four. Every operation needs the same lock, so the work cannot overlap, and now the lock's cache line also bounces between cores and goroutines are put to sleep and woken. More cores made it worse. A single lock around hot state does not scale, however short the critical section.
  • sync.RWMutex is only a modest win even in the case it is designed for. It allows any number of readers at once, or one writer. With a read-heavy mix on four procs it is about 17% faster than the plain mutex (129 vs. 155 ns). On one proc there is no contention to relieve and the two are indistinguishable (69 vs. 68 ns), because RWMutex does more bookkeeping per lock. The critical section here, copying eight small structs, is so short that lock overhead dominates. RWMutex pays off when readers hold the lock for a long time relative to that overhead. Measure before assuming.

When a lock does become the bottleneck, the options are to hold it for less time, to shard the state so unrelated requests take different locks, or to avoid shared state altogether: give each goroutine its own copy and combine them later. Bandit counts are unusually good at that last one. Successes and failures per arm are just sums, so copies can be added together, which is the idea chapter 12 builds on.

Choosing a tool

SituationUse
Protect a struct with several fields that change togethersync.Mutex (the default)
Many readers, few writers, and long read sectionssync.RWMutex, after measuring
One independent counter or flagatomic.Int64, atomic.Bool
A read-mostly value replaced wholesale (config, published snapshot)atomic.Pointer[T] holding an immutable value (exercise 3)
Data that one goroutine can own, with others sending it requestsA goroutine that owns the state and receives on a channel
Hand a value from one stage to the nextA channel

The last two rows are the Go proverb "don't communicate by sharing memory; share memory by communicating". It is a useful default when work flows through stages, and a poor one for a shared counter, where a channel round trip costs far more than the mutex it replaces. The proverb says to think about who owns the data, and the answer is sometimes "everyone, behind a lock".

Exercises

Starters and tests are in exercises/ch06. Run them with go test -race ./ex1 too; the race detector reports things the plain test cannot.

1. Two thread-safe counters

In exercises/ch06/ex1, make LockedCounter safe with a sync.Mutex and AtomicCounter safe with atomic.Int64. Make sure Value is safe to call while other goroutines increment; only the race detector notices if it is not.

Reference answer

Reads need synchronisation too. A reader that skips the lock races with the writers even though it only looks. The atomic version is shorter and faster, but works only because the entire state is one number.

2. The struct that ignores its own lock

Stats in exercises/ch06/ex2 has a mutex, locks it in every method, and still records nothing. Run go vet ./ex2, read what it says, and fix the type without changing the tests.

Reference answer

Every method had a value receiver, so each call locked and updated a copy of the struct, and the caller's Stats never changed. Vet reports "passes lock by value". The fix is pointer receivers, plus a constructor that returns *Stats. The lock only means something when all callers share the same one.

3. A lock-free cell with a compare-and-swap loop

Cell[T] in exercises/ch06/ex3 stores an immutable value in an atomic.Pointer[T]. Load and Store are done. Implement Update(f func(T) T) T so that concurrent updates are never lost, using CompareAndSwap in a loop. The starter's read-then-write loses updates.

Reference answer

CompareAndSwap(old, new) stores new only if the cell still holds old, and reports whether it did. If another goroutine got in between, the swap fails and the loop retries with the fresh value. That is why f may run more than once and must be free of side effects. Readers just call Load: they never block and never see a half-written value, because a published value is never modified. This is the shape chapter 13 uses when an aggregator publishes a new snapshot for replicas to read.
