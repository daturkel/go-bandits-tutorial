See it fail

A data race is two goroutines accessing the same memory at the same time, at least one of them writing, with nothing to order them. The simplest victim is a counter. counter++ looks like one step but is three: read the value, add one, write it back. If two goroutines interleave those steps, both read 41, both write 42, and an increment vanishes. This program runs 100 goroutines that each add 1 ten thousand times: first unprotected, then with a mutex, then with an atomic. Before you run it, guess the first total.

The unprotected total is far below a million, and it is a different number every time. The two correct versions differ in mechanism. A sync.Mutex lets one goroutine at a time through Lock…Unlock. An atomic.Int64 performs the read-modify-write as a single indivisible CPU operation.

Go vs. Python

Python threads can lose updates on n += 1 as well, because that statement is also several bytecodes. The GIL protects the interpreter's own data structures, not your logic, though it does make individual operations such as list.append effectively atomic. Go gives you no such cushion: nothing is implicitly atomic, and goroutines really do run in parallel, so races show up faster and do more damage. Go also gives you a detector for them.

The race detector

Go can instrument a program to watch every memory access and report any that are unordered. Turn it on with -race on go run, go build or go test. It slows the program down several times and uses more memory, so it is for development and CI, not production. It reports only races that actually happen during that run, so tests that exercise concurrency are what make it useful; but it has no false positives: every report is a real bug.

And the collision is not in your bandit code but inside math/rand/v2: a *rand.Rand is not safe for concurrent use, because drawing a number updates its internal state. Even a policy whose Select only read its counts would fail this way, as long as it draws a random number. (The Update side has its own race on the counts.) Any type holding a generator inherits that restriction.

One goroutine at a time

The simplest correct fix for the race is to let one goroutine into the policy at a time. locked.go wraps any SnapshotPolicy in a type with a mutex next to it:

  • The mutex sits next to what it guards, and the comment says so. Go does not enforce the association; the convention is that every access to p holds mu.
  • Zero values help. sync.Mutex and the atomic types are ready to use as declared, so &Locked{p: p} is complete.
  • Name takes no lock. It reads only data fixed at construction. If it ever read something a method could change, it would need one.
Task 2: the lock

Make each of the three methods hold the lock while it calls the wrapped policy: l.mu.Lock(), then defer l.mu.Unlock() on the next line, then the call. defer releases the lock on every return path, including a panic: forgetting to unlock on one branch is a classic bug, and defer removes it at the cost of a few nanoseconds. Leave the counters for task 3. Run go test -race -run 'Locked|Snapshot' ./bandit: what still fails is about the counters.

Answer

Snapshot needs the lock too: it reads the counts while another goroutine's Update may be writing them. Its result is a copy made under the lock, so the caller can use it after the lock is released. (The answer also has task 3's counter lines, the calls to Add.)

Task 3: counters that never wait

A metrics page will want to know how many selections and updates a policy has handled, without waiting for a Select that holds the lock. That is what atomics are for: independent single numbers. Count each call with the counter fields' Add(1), outside the lock, and report them in Calls with Load(). Run go test -race ./bandit.

Answer

The counters are updated before the lock is taken, so a selection that is still waiting for the lock is already counted. Reading them with Load never blocks, however busy the policy is.

Under real concurrency, the arm each goroutine receives depends on scheduling, so the tests cannot check which arms were chosen. They check what must be true regardless: no update is lost, and the counters agree. A second test guards the other side: wrapping must not change what a single goroutine sees.

A policy hammered from many goroutines gives results that depend on scheduling, so runs are not reproducible even with fixed seeds.

Never copy a mutex

A sync.Mutex is a value with state. Copy one and you get two independent locks, so the copy protects nothing. The compiler will not stop you, but go vet will:

This is why NewLocked returns a pointer and the doc comment says never to copy the value. Any struct that contains a mutex or an atomic gets the same treatment, and that has the same consequence for method receivers: use pointer receivers, as chapter 2 recommended for anything with state. The second extra task is a bug of exactly this kind.

What locking costs

Mutual exclusion makes the code correct, and it turns parallel goroutines into a queue at the lock. Two benchmarks show the effect. b.RunParallel runs the benchmark body on several goroutines at once, and -cpu 1,4 repeats it with one and four procs. The first hammers Select plus Update, both writes. The second does 19 Snapshot reads for every Update, comparing Locked's plain mutex with a reader-writer version, sync.RWMutex, which lets any number of readers in at once, or one writer:

Read ns/op here as wall-clock time divided by the total operations, so lower means more throughput. Two results matter.

  • Four goroutines are slower than one. Select plus Update takes about 126 ns per operation on one proc and about 371 ns on four. Every operation needs the same lock, so the work cannot overlap, and now the lock's cache line also bounces between cores and goroutines are put to sleep and woken. More cores made it worse. A single lock around hot state does not scale, however short the critical section.
  • RWMutex is only a modest win even in the case it is designed for. With the read-heavy mix on four procs it is about 17% faster than the plain mutex (116 vs. 139 ns). On one proc there is no contention to relieve and the two are indistinguishable (51 vs. 50 ns), because RWMutex does more bookkeeping per lock. The critical section here, copying a few small structs, is so short that the lock's own overhead dominates. RWMutex pays off when readers hold the lock for a long time relative to that overhead. Measure before assuming.

When a lock does become the bottleneck, the options are to hold it for less time, to shard the state so unrelated requests take different locks, or to avoid shared state altogether: give each goroutine its own copy and combine them later. Bandit counts are unusually good at that last one. Successes and failures per arm are just sums, so copies can be added together, which is the idea chapter 12 builds on.

Choosing a tool

SituationUse
Protect a struct with several fields that change togethersync.Mutex (the default)
Many readers, few writers, and long read sectionssync.RWMutex, after measuring
One independent counter or flagatomic.Int64, atomic.Bool
A read-mostly value replaced wholesale (config, a published snapshot)atomic.Pointer[T] holding an immutable value (third extra task)
Data that one goroutine can own, with others sending it requestsA goroutine that owns the state and receives on a channel
Hand a value from one stage to the nextA channel

The last two rows are the Go proverb "don't communicate by sharing memory; share memory by communicating". It is a useful default when work flows through stages, and a poor one for a shared counter, where a channel round trip costs far more than the mutex it replaces. The proverb asks you to think about who owns the data, and the answer is sometimes "everyone, behind a lock".

What you learned

  • A data race is unordered access to the same memory with at least one write; n++ is three steps, and updates get lost.
  • -race finds races that happen during a run, with no false positives; concurrency tests are what give it something to see.
  • A sync.Mutex lets one goroutine at a time into a critical section; defer Unlock keeps it correct on every path. Never copy one: use pointers, and let go vet check.
  • Atomics suit independent single values that must never wait.
  • One lock around hot state does not scale with cores; measure before reaching for RWMutex, and prefer state that can be split and merged.

Extra 2: the struct that ignores its own lock

Stats has a sync.Mutex, locks it in every method, and still records nothing. Run go vet ./_extras/ch06, read what it says, and fix the type without changing the tests.

Answer

Every method had a value receiver, so each call locked and updated a copy of the struct, and the caller's Stats never changed. Vet reports "passes lock by value". The fix is pointer receivers, plus a constructor that returns *Stats. A lock only means something when everyone shares the same one.

Extra 3: a lock-free cell with a compare-and-swap loop

Cell[T] stores an immutable value in an atomic.Pointer[T]. Load and Store are done. Implement Update so that concurrent updates are never lost, using CompareAndSwap in a loop. The starter's read-then-write loses updates, and one test proves it deterministically.

Answer

CompareAndSwap(old, new) stores new only if the cell still holds old, and reports whether it did. If another goroutine got in between, the swap fails and the loop retries with the fresh value. That is why f may run more than once and must be free of side effects. Readers just call Load: they never block and never see a half-written value, because a published value is never modified.
