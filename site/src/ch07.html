select

A receive on a channel waits until a value arrives. select waits on several operations at once and runs the case of whichever becomes ready first. It looks like a switch whose cases are sends and receives. This program shows the forms you will use most:

  1. Timeout. time.After(d) returns a channel that receives one value after d. Putting it in a select next to the real operation bounds the wait.
  2. default makes the select non-blocking: if no other case is ready right now, it runs immediately.
  3. Several sources. The loop handles ticker events until the deadline channel fires. When more than one case is ready, Go picks one at random, so never rely on case order. The label loop: lets break loop leave the loop instead of only the select.
  4. Contexts. A context exposes "stop now" as one channel, ctx.Done(), which is closed when the context ends. That is why cancellation composes with select.
  5. Cancelling by hand, with a reason. context.WithCancelCause returns a cancel function that takes an error; context.Cause(ctx) reads that reason back, while ctx.Err() still reports plain context.Canceled.

A nil channel is never ready, so setting a channel variable to nil removes its case from a select. That is occasionally useful for turning a case off.

context

A context.Context carries a cancellation signal, and optionally a deadline, down a call tree. You create one from another: context.WithCancel(parent) returns a child and a cancel function; context.WithTimeout(parent, d) returns a child that cancels itself after d. Cancelling a context cancels every context derived from it, so one call at the top stops everything beneath. Once it has ended, ctx.Err() is context.Canceled or context.DeadlineExceeded; before that it is nil. At the top of a program, or in a test, the root is context.Background(), a context that never ends.

The conventions are worth following exactly, because the whole ecosystem does:

  • ctx is the first parameter, named ctx: func Run(ctx context.Context, ...).
  • Always call cancel, usually with defer cancel() right after creating the context. Releasing it frees the timer and the link to the parent. go vet warns if you forget.
  • Do not store a context in a struct; pass it along the call path. A context describes one operation, not an object.
  • Cancellation is cooperative. Nothing is interrupted. Code that can run for a long time must look at the context, either with ctx.Err() or by including <-ctx.Done() in a select.
  • Contexts can also carry request-scoped values. Use that sparingly, for things like a request ID that crosses API boundaries (chapter 8), never for ordinary parameters.

Go vs. Python

asyncio cancels a task by raising CancelledError at its next await, and a thread cannot be cancelled from outside at all. A Go context does neither: it sets a flag and closes a channel, and the code being cancelled decides where to look. That is less magical and more explicit, since every blocking point must handle it, and it is why Go APIs that block take a ctx. asyncio.timeout() is the closest equivalent of WithTimeout, and the idea of a deadline that propagates to everything beneath it is the same.

How goroutines leak

Chapter 5 said that a goroutine blocked forever goes unnoticed unless every goroutine in the program is blocked. It holds memory and everything it references for the life of the process, and a server that leaks one per request eventually runs out. The usual cause is a send with no receiver, like this one:

Both functions start a worker and wait for its result, giving up after a timeout. In fetchLeaky the channel is unbuffered, so if the caller has already left, the worker's send has nowhere to go and blocks for good. In fetchFixed the channel has room for one value, so the send completes and the goroutine exits. The program calls each a thousand times with a timeout shorter than the work, then asks the runtime what is still running:

Two ways to find this in a real program. runtime.NumGoroutine() gives a count, and a count that rises with traffic and never falls back is the signature. The goroutine profile (/debug/pprof/goroutine on a server, chapter 11) groups goroutines by where they are stuck: a thousand of them at the same send. Tests can assert on the count too, which is what the waitForGoroutines helper in this chapter's tests does.

The rule to take from this: for every goroutine you start, know how it will end. It ends when its function returns, so ask what it could be blocked on. A send needs a receiver or buffer space, a receive needs a sender or a closed channel, and any wait should also include ctx.Done().

A bounded worker pool

Chapter 5 started one goroutine per job. That works for thousands of jobs and not for millions, and it ignores the fact that only as many jobs can run at once as there are cores. The standard shape is a fixed number of workers that take jobs from a channel. You will write it as a generic function in its own package, so the harness and anything later can use it:

The contract is in Run's doc comment. There are four kinds of goroutine in it, and you write it in two passes: first the work, then failure and cancellation.

  1. Workers, a fixed number of them (never more than there are jobs), loop over a channel of job indexes until it is closed, call f, and send an outcome.
  2. A feeder sends the job indexes into that channel and closes it when done.
  3. A closer waits for all the workers and closes the outcome channel.
  4. The collector is the goroutine that called Run. It ranges over the outcomes, always to the end, and stores each result at its job's index.

Hint 1: the channels

Two unbuffered channels: work, of job indexes (chan int), and results, of outcomes. An outcome is a small struct with the index, the result and the error. The job values never travel through a channel; workers read jobs[i].

Hint 2: who closes what

The feeder is the only sender on work, so it closes it, with defer close(work) at the top of its goroutine; that is what ends each worker's for i := range work. The workers are the senders on results, and there are several, so a separate goroutine does wg.Wait() and then close(results), as in chapter 5.

Hint 3: generics

Inside Run, the type parameters are ordinary type names: out := make([]R, len(jobs)) holds the results, and the outcome struct has a field of type R. The outcome type can be declared inside the function, so it can use them.

Task 3: failures and cancellation

Now the rest of the contract:

  • Derive a context with context.WithCancel(ctx) at the top, defer cancel(), and pass the derived one to f. The first job that fails with an ordinary error calls cancel(), so jobs still running can stop and the rest are not started.
  • The feeder must stop handing out jobs once that context ends. Its send becomes a select with a second case, <-ctx.Done(), that returns. Without it, it would block forever on a send that no worker will ever take, and leak.
  • A job that fails because it was cancelled reports a context error, and that must not hide the real failure. After the loop, return the lowest-indexed ordinary error; failing that, the caller's own ctx.Err() (keep the original ctx in a variable before you replace it); failing that, any remaining context error. isContextErr at the bottom of the file tells the two kinds apart, by checking for context.Canceled and context.DeadlineExceeded:

Run go test -race ./pool again; the tests include one that checks no goroutine outlives Run.

Hint: the collector

Keep a []error with one slot per job, like the results. In the loop: store the result and the error; if the error is nil, count it and call OnDone; if it is an ordinary error, call cancel(). The loop still runs to the end, which is what guarantees a worker can always deliver its outcome, so the workers can send without a select.

What you learned

  • select waits on several channel operations; with time.After it bounds a wait, with default it never blocks.
  • A context.Context is the first parameter of anything that may need to stop; cancellation is cooperative, so long loops check ctx.Err() and blocking operations include ctx.Done().
  • Every goroutine needs a known way to end: a receiver for its send, a close for its receive, a context for its wait. A count that only rises is a leak.
  • A bounded pool (workers, feeder, closer, collector) handles any number of jobs with a fixed number of goroutines, and the first failure can cancel the rest.
  • At the edge of a program, signal.NotifyContext turns Ctrl-C into a cancelled context.

Extra 1: first success wins

Run all the functions at once, return the first successful value, cancel the rest, and do not return until every function has. This is the "hedged request" pattern: ask three replicas, use the fastest answer.

Answer

The results channel has room for every result, so no goroutine can block on its send even after First stops caring. The loop still receives all len(fns) results before returning, which is how it waits for the losers: they were told to stop by cancel() and return promptly, provided they watch their context. A function that ignores its context would make First wait for it, and that is the price of the "nothing left running" guarantee.

Extra 2: a semaphore from a buffered channel

Run every task with at most n running at once, and return when all have finished. Do not use a fixed pool of workers; use a channel with capacity n as a counting semaphore.

Answer

Sending on a full buffered channel blocks, so sem <- struct{}{} waits when n tasks hold slots, and the receive in the deferred function frees one. struct{} is the zero-size type, the idiomatic payload for a channel that only signals. This shape starts one goroutine per task but runs only n at a time, which suits a few heavy tasks; for millions of small ones, the pool is cheaper.

Extra 3: fix the leak

Fetch returns early when its context ends, but the goroutine it started blocks forever on the send. The test calls it a hundred times with a short timeout and checks the goroutine count afterwards. Fix it without making Fetch wait for the work.

Answer

One character of difference: make(chan string, 1). With room for the single result, the worker's send never blocks, so the goroutine finishes its work, sends into the buffer, and exits even if nobody ever reads it. The buffered value is then garbage collected with the channel. This does not stop the work itself; if work accepted a context it could be cancelled too, which is the better design when you control it.
