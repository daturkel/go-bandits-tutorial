What you will build

The system from chapter 13 as something you can start with one command: a multi-stage Dockerfile that builds small images for each service, a Compose file that starts PostgreSQL, the aggregator, the feedback service and three policy replicas in the right order with health checks, and a Python client that calls the replicas through a load balancer. Along the way you will settle a question that catches most people the first time they put gRPC behind a load balancer: why every request went to the same replica.

Read this first: what was and was not run

The environment this chapter was written in had the Docker command-line tools but no Docker daemon, so no image was built and no container was started. What was checked:

  • docker compose config parsed and validated compose.yaml, including variable interpolation, and its output is shown below. That checks syntax and structure; it does not check that the images build or that the services start inside them.
  • The Dockerfile was written and reviewed by hand and not built. Its go build line is the one the local scripts run, and the statically linked binaries it produces are the ones tested in the previous chapter.
  • The same four programs, with the same environment variables and the same health-check command, were run as ordinary processes by _examples/local-cluster.sh: three policy replicas, one database, a load-balancing client, a killed replica. That is real output, and it is what stands in for the containers.
  • The Python client and its tests were run for real, against fake servers and against the Go services.

Expect to fix small things the first time you run docker compose up --build on your machine (a registry tag, a permission). Everything that is about how the services behave, as opposed to how they are packaged, was exercised.

Concepts introduced

  • Multi-stage Docker builds: a large build stage and a small runtime image
  • Static Go binaries, CGO_ENABLED=0, distroless images, running as non-root
  • Layer caching: why go.mod is copied before the source
  • Health checks, depends_on: condition: service_healthy, and why the check is a program that exits 0 or 1
  • Exec-form ENTRYPOINT, PID 1 and SIGTERM
  • Load balancing gRPC: why a layer-4 balancer does not work, and client-side round robin
  • Evolving a protobuf schema (adding fields) and generating a client in another language
  • Retrying only what is safe to retry

Step 2: a health check that means something

Docker, Compose and Kubernetes ask a service whether it is healthy by running a command and looking at its exit status. Chapter 13's banditrpc health already called the gRPC health service and printed the answer; now it also fails unless the answer is SERVING, and it has a deadline, so a hung service fails the check instead of hanging it. Using our own client as the health checker has a practical reason: a minimal image has no shell, no curl, nothing to run a check with. The check is a second small binary copied into the image next to the service.

Step 3: the images

A Go service is one file, and it should ship as almost nothing else. The Dockerfile has a build stage that has the whole toolchain and a series of final stages that hold one binary each.

Points worth understanding rather than copying:

  • Two COPY steps. Docker caches each instruction's result and reuses it if its inputs did not change. go.mod and go.sum change rarely, source changes constantly. Downloading dependencies before copying the source means an edit to a .go file re-runs only the compile, not the download.
  • CGO_ENABLED=0. By default a Go program that uses some standard-library packages (DNS, user lookup) links against the system's C library. Turning cgo off makes the pure-Go versions be used, and the binary depends on nothing, which is what lets it run in an image with no C library. It is one of the practical wins of Go for operations.
  • distroless/static:nonroot. No shell, no package manager, no apt: an attacker who finds a way into the process has almost nothing to work with, and there is little to patch. The price is that you cannot docker exec a shell into it; use a debug sidecar or a debug image tag when you need one.
  • Exec-form ENTRYPOINT ["/policyd"]. With the shell form (ENTRYPOINT /policyd), Docker runs /bin/sh -c /policyd, the shell is process 1, and docker stop's SIGTERM goes to the shell, which does not forward it. The service would never start its graceful shutdown and Docker would kill it after the timeout. In exec form the service is process 1 and gets the signal, which is what chapter 9 built the shutdown for.
  • The .dockerignore file keeps the build context small and, more to the point, keeps the cache stable: if editing the Python client changed the context hash, every Go image would rebuild.

Build one image with docker build --target policyd -t banditlab/policyd .. The target names the final stage; stages the target does not depend on are skipped.

Step 4: Compose

Compose describes the whole set of containers, their networks and their start-up order in one file.

What to look at:

  • Configuration comes from the environment. Every setting the services read (chapter 9's BANDIT_* variables) is set here, and the database password comes from the host's environment with a development default (${POSTGRES_PASSWORD:-bandit}). No image contains a secret.
  • Start-up order is health, not "started". depends_on alone waits for a container to exist; with condition: service_healthy it waits for the health check to pass. PostgreSQL accepts connections only after it has initialised, and the aggregator must be serving before the policy replicas try to follow it. (The services also retry on their own; the ordering just avoids noisy logs at start-up.)
  • The health check is the command from step 2. test: ["CMD", ...] is exec form again, so no shell is needed.
  • stop_grace_period: 15s is longer than the services' own 10-second shutdown grace, so Docker does not kill a service that is finishing in-flight calls.
  • Three policy replicas, no published port. Three containers cannot bind the same host port. Other containers reach them by the service name policyd, and Compose's built-in DNS answers that name with the address of every replica.

Step 5: load balancing gRPC

Put three replicas behind a TCP load balancer and send it a thousand gRPC calls: they all land on one replica. The reason is in how gRPC works. A load balancer at layer 4 chooses a backend when a connection opens. gRPC runs over HTTP/2, which multiplexes many calls over one long-lived connection, so a client opens one connection and every call rides it. The balancer made its choice once.

The fix is to balance calls, not connections. Two ways:

  • A layer-7 proxy (Envoy, or the load balancer of a cloud provider with HTTP/2 support) that understands gRPC and picks a backend per call.
  • Client-side balancing. The client resolves a name to all the replicas' addresses, keeps a connection to each and rotates its calls. gRPC clients do this natively; it needs a resolver that returns every address (dns:///policyd:9090, where the name has several A records, which is how Compose's DNS and Kubernetes headless services present a replicated service) and a policy named round_robin in the client's service config.

Without that configuration the default, pick_first, uses the first address and stays on it. You can see both behaviours in the demo, from the Go client, before and after the flag. The script runs the topology of compose.yaml as plain processes:

Reading the output:

  • pick_first: twelve calls, one replica. Every call to policyd-1, though three are up.
  • round_robin: four each. The same command with -lb round_robin spreads them evenly.
  • The Python client, sixty calls: 19, 21 and 20. Its channel is configured for round robin (step 6). The last line is one replica's view of the world: policy replicas that never handled most of those rewards report all of them, learned through the aggregator's stream. The "waiting" counts are the 24 selections the earlier command-line runs made and never rewarded; they are still pending (until their time to live), and the pending-aware UCB1 of chapter 12 steers around arms with many waiting.
  • Killing a replica. With policyd-2 gone, calls go to the other two. gRPC notices the failed connection, marks the address unhealthy and stops sending calls to it; when Compose restarts the container, the client's DNS re-resolution will find it again. The health check of the dead replica fails with exit status 1, which is what makes Compose (or Kubernetes) restart or replace a container.
  • Shutdown. All four stopped services exit with status 0 after SIGTERM: the graceful shutdown from chapters 9 and 13.

For an ordinary docker compose up the client side of this is the Python program in the client service, whose target is dns:///policyd:9090. That path (Compose DNS returning three addresses) was not run; the scripted equivalent (three addresses given directly) was.

Step 6: a Python client

The point of a schema language is that the caller does not have to be written in Go. The same .proto file generates Python code. grpcio-tools bundles a copy of the protobuf compiler, so this needs only pip:

The generated stubs are low-level: protobuf messages in, protobuf messages out, and a grpc.RpcError whose .code() you have to inspect. A thin wrapper gives callers ordinary values and exceptions, retries only when retrying is safe, and sets the load-balancing policy once:

The rule in _call deserves a sentence, because it is easy to get wrong in the direction of "retry everything". UNAVAILABLE means the call did not get to the server, or the server was starting or draining, so the same call is fine to repeat. NOT_FOUND or INVALID_ARGUMENT will fail the same way each time. DEADLINE_EXCEEDED is ambiguous: the server may have done the work and be about to answer, so repeating a non-idempotent call can do it twice. Here, retrying a Reward after a timeout would get AlreadyExists at best; the store's claim is what keeps that harmless, which is a reason to make operations idempotent on the server whenever you can.

Where this leaves you

You have a system with a stateless-enough front (policy replicas that can come and go), a durable core (PostgreSQL), a fast path that keeps replicas current (the aggregator's stream), a reconciliation path that repairs it, health checks and graceful shutdown that let an orchestrator manage it, and a client in a different language. The capstone measures that system end to end.

Exercises

Starters and tests are in exercises/ch14. The module has the gRPC dependency already.

1. A health check that cannot lie

Implement Check(ctx, client, service) in exercises/ch14/ex1: call the gRPC health service and return nil only for SERVING. Anything else (NOT_SERVING, an unknown service, a failed call, a cancelled context) is an error.

Reference answer

The failure modes to avoid are all "returns nil by accident": ignoring the status field (an UNKNOWN response then looks healthy), or swallowing the error when the service name is not registered. A container that reports healthy while it is draining keeps receiving traffic, which is exactly what the health check exists to stop.

2. Wait until healthy

Implement WaitHealthy(ctx, interval, check) in exercises/ch14/ex2: run check now and then every interval until it succeeds, or until the context ends. When it gives up, the error should carry both the context's error and the last thing check said, so an operator can tell whether the service was refusing connections or answering NOT_SERVING.

Reference answer

The first check runs before the first tick, so a service that is already up costs nothing. errors.Join lets one error satisfy errors.Is for several causes at once, and the check receives the context, so a check that hangs is interrupted when the caller gives up.

3. Parse a list of replicas

Implement ParseTargets(spec) in exercises/ch14/ex3: turn "a:1, b:2," into ["a:1", "b:2"], and reject entries without a valid port, duplicates, and an empty list, naming the entry at fault.

Reference answer

net.SplitHostPort already handles the bracketed IPv6 form and rejects a bare ::1:9090, which is ambiguous (which colon separates the port?). Validating configuration at start-up, with a message that names the bad value, is much cheaper than discovering an empty or duplicated list as uneven traffic in production.
