What you will build

A command-line program that simulates a multi-armed bandit and reports how much reward it left on the table. You will create a Go module, define an environment whose arms pay out with fixed probabilities, write an epsilon-greedy policy that learns which arm is best, and run it for thousands of pulls with a seeded random number generator so every run is reproducible.

Everything later in the course is built on these types, so it is worth being precise about the problem before writing any code.

The bandit problem in one paragraph

There are k arms. Pulling an arm pays 1 with some hidden probability and 0 otherwise. You want the most total reward over a fixed number of pulls, but you do not know the probabilities. Pulling the arm that looks best exploits what you know; pulling another arm explores in case your estimate is wrong. The cost of not always pulling the best arm is regret: the sum, over every pull, of the gap between the best arm's probability and the probability of the arm you actually pulled. Lower is better, and a good policy's regret grows slowly as pulls accumulate.

Epsilon-greedy is the simplest policy: with probability ε pull a random arm, otherwise pull the arm with the best average reward so far.

Step 1: create the module

A Go module is a tree of packages versioned together, described by a go.mod file at its root. A package is a directory of .go files that share a package clause; it is the unit of compilation and of import. There is no separate build file, no virtual environment, and no install step: the toolchain reads go.mod and builds.

go mod init records the Go version you happen to have installed. This project pins both a language version and an exact toolchain so every reader builds with the same compiler:

The go line is the minimum language version the module needs; the toolchain line is the exact release the go command will use, downloading it if your local one is older. Nothing else is needed: this module has no dependencies, so there is no lock file yet.

The layout for this chapter is deliberately small:

The import path of the library package is the module path plus the directory: banditlab/bandit. Every file in bandit/ starts with package bandit, and anything defined in one file is visible to the others without importing. package main is special: it is the one whose main function becomes the program.

Go vs. Python

Python packages are found by searching sys.path, and a directory becomes a package by convention or an __init__.py. In Go the module path in go.mod is the root of every import, a package is exactly one directory, and the compiler rejects an unused import or an unused local variable. Whether a name is public is decided by its first letter: Env is exported, env is not. There are no _private conventions and no __all__.

Step 2: seeded randomness

A simulation you cannot reproduce is a simulation you cannot debug, so randomness comes from generators we create and seed ourselves, never from the global one. math/rand/v2 provides rand.New(rand.NewPCG(seed1, seed2)): a PCG generator whose entire state is the two numbers you give it.

The environment and the policy each get their own generator, created from the same seed but a different stream number. If they shared one, adding a single extra random draw to the policy would silently change every reward the environment produces, and results would stop being comparable between policies.

The const block uses iota, which counts up from zero within a constant group: StreamEnv is 1 and StreamPolicy is 2. Go has no enum type; a typed group of constants is the idiom.

Step 3: the environment

An environment is a set of arms with hidden success probabilities. A struct groups the data, and methods are functions declared with a receiver:

Three things to notice:

  • There are no constructors. NewEnv is an ordinary function that, by convention, returns a pointer to a ready-to-use value. The fields are lowercase, so code outside the package can only get an Env through it.
  • slices.Clone copies the caller's slice. A slice is a small header (pointer, length, capacity) onto an array, so assigning one shares the elements. Without the clone, the caller could change the probabilities under our feet.
  • Receivers are pointers (*Env). A method with a pointer receiver can modify the value it is called on and avoids copying the struct on every call. The next chapter is about when to choose a value receiver instead; for now, use pointers for anything with state.

The rest of the environment answers "which arm is actually best?", which the simulation needs in order to measure regret:

Best returns two values. The named results arm and p are declared as variables at the top of the function and start at their zero values, 0 and 0.0. That is what makes the loop work: the i == 0 check seeds them with the first arm, and an environment with no arms returns (0, 0) without any special case. (Chapter 3 makes that impossible by rejecting empty environments.)

Go vs. Python

Every type has a usable zero value: 0, "", false, nil for pointers, slices and maps. Variables are never "undefined", and there is no None to forget to check for a number or a string. Well-designed Go types try to make their zero value useful, and you will see that used deliberately when we count pulls per arm: make([]int, n) is already a correct set of zeroed counters.

Step 4: named scenarios with a map

To compare behaviours we want a few standard test beds we can select by name. A map is Go's dictionary:

Scenario returns ([]float64, bool). Reading a map with two variables, probs, ok := scenarios[name], is the comma-ok idiom: a missing key does not raise, it yields the zero value and ok == false. This is how Go says "may be absent" without exceptions or a sentinel, and returning a (value, ok) pair from your own functions is the same idea. Chapter 3 upgrades this to an error.

Map iteration order is deliberately randomised, so ScenarioNames collects the keys with maps.Keys and sorts them with slices.Sorted. The four scenarios are worth knowing, because later chapters compare policies on them:

Step 5: the epsilon-greedy policy

The policy keeps, for each arm, how many times it was pulled and the running mean of its rewards. Two parallel slices indexed by arm are all it needs:

Epsilon is capitalised, so callers can read and change it; counts, values and rng are private to the package. make([]int, nArms) allocates a slice of that length filled with zeros, which is exactly the initial state we want.

Selecting an arm is a coin flip between exploring and exploiting:

greedy is unexported, so it is an implementation detail of this package. It also contains a subtle point: at the start every mean is 0, so every arm ties. Picking "the first maximum" would always pull arm 0 first and bias the whole run, so ties are broken uniformly at random using reservoir sampling: when the n-th tied arm is seen, it replaces the current choice with probability 1/n, which leaves every tied arm equally likely without collecting them in a slice. The switch with no expression is Go's tidy replacement for an if/else if chain; each case is a condition, and there is no fall-through.

Learning is a one-line running-mean update:

The identity is mean += (reward − mean) / n. It avoids storing every reward or a separate sum, and never divides by zero because the count is incremented first.

Step 6: the simulation loop

A run plays the policy against the environment for a fixed number of steps and records what happened:

for t := range steps ranges over an integer (Go 1.22+): t takes the values 0 to steps-1. There is no range(steps) object; the loop form is the whole feature.

Regret here is expected regret. Each pull adds bestP - env.Prob(arm), the gap in probabilities, rather than comparing the random rewards drawn. A lucky pull of a bad arm therefore still counts against the policy, which makes the curve much less noisy and lets us compare policies with fewer runs. We record the cumulative value after every step in RegretCurve; chapter 4 averages these curves across seeds.

Run it:

Out of 10,000 pulls, arm 2 (the 0.8 arm) got 9,331; the rest went to exploring. Cumulative regret is about 304, and almost all of it is the price of exploring: exploring uniformly one time in ten across three arms wastes about 0.1 × (0.6 + 0.3) / 3 = 0.03 regret per pull, or 300 over the run. That is the price of a fixed ε, and one of the reasons the more sophisticated policies in later chapters exist.

Because generators are seeded, this output is identical on every machine. Change the scenario, ε, or step count to see how the numbers move:

On needle with a smaller ε, 95,310 of 100,000 pulls go to the good arm, but regret still reaches 938: with only 0.05 of exploration spread across ten arms, roughly nine in ten of those exploratory pulls go to a 0.10 arm that is 0.20 worse.
