What you will build

The service becomes a proper daemon, banditd, separate from the banditsim command-line tool. You will reorganise the project into cmd/ and internal/, read configuration from flags and environment variables with a clear order of precedence, set up structured logging that can switch between human-readable and JSON, and make the server stop cleanly: on SIGTERM or Ctrl-C it fails its health check, finishes the requests already in flight, and exits.

None of this changes what the service does. It changes whether you can run it in a container, ship its logs to a collector, and deploy a new version without dropping requests, all of which chapter 14 depends on.

Concepts introduced

  • The cmd/ and internal/ layout, and how the compiler enforces internal
  • Configuration from flags and environment variables, with testable inputs
  • log/slog handlers, levels, With, groups, and ReplaceAttr
  • The functional options pattern
  • Signals: SIGINT and SIGTERM, and signal.NotifyContext
  • Graceful shutdown with http.Server.Shutdown, grace periods, and drain delays
  • context.WithoutCancel
  • Exit codes, and a main that is a few lines long

Step 1: cmd/ and internal/

Until now the project has been flat: one main package at the root plus a directory per library package. That is fine for a single program, and it is the right way to start. It stops working when there are two programs (a simulator and a server) that share libraries, and when you want to say which packages other people may import.

What internal means

A package whose path contains an internal element can only be imported by code in the tree rooted at the parent of that directory. Here that is everything in this module, and nothing else. The compiler enforces it, so other modules cannot depend on your implementation details and you can change them freely. To see it, here is a second module that tries:

The replace directive points the dependency at the local copy of the project. Python has only a convention here (a leading underscore), which nothing enforces. In Go this is a build error.

Why Go does it this way

Anything exported from a public package becomes a promise: someone will depend on it. internal/ lets a library or service keep its packages exported within the project, so its own programs and tests can share them, without promising them to the world. Do not over-apply it. A small project can stay flat, and directories named pkg/, util/ or common/ are usually a sign that packages are being named for what they are (a bucket) rather than what they do. Names like bandit, server and config say what a package is for.

Step 2: configuration

A service needs settings: where to listen, which policy, how many arms, how loudly to log. Two sources are worth supporting. Flags are convenient at a terminal; environment variables are how containers and process managers configure programs, and they keep settings out of shell history and image contents. Supporting both raises the question of which wins, and the answer here is the usual one: a flag beats an environment variable, which beats the default.

How it works:

  • Each environment variable supplies the default of its flag: fs.IntVar(&cfg.Arms, "arms", env.int("BANDIT_ARMS", 3), ...). If the flag is given it overwrites the value; if not, the environment (or built-in) default stands. The -h output therefore shows the effective defaults.
  • getenv is a parameter. Calling os.Getenv directly would make every test depend on, and modify, the real process environment. Passing the function makes the environment an input, and the tests use a map. Anything you would otherwise read from global state (the clock, the environment, random numbers) is easier to test when passed in.
  • All problems are reported at once, as in chapter 3: a bad BANDIT_SEED and a bad -arms appear in one message, each naming the variable and value. Invalid input from any source wraps the sentinel ErrInvalid, so main can choose exit status 2 for it.
  • slog.Level parses itself: LogLevel.UnmarshalText accepts debug, info, warn, error.
  • Flag descriptions written with backticks (`address`) tell the flag package what to call the value in the help text.

Go vs. Python

This is what argparse plus os.environ, or pydantic-settings, does in a Python service. Go has nothing built in that merges the two, and this package is deliberately small, around 130 lines with no dependencies. Third-party libraries (viper, envconfig, kong) exist; the case for them is a large configuration surface, config files, or hot reload. For a dozen settings, plain code is easier to read and to test.

Step 3: structured logging

Chapter 8 used slog as a logger. Here is more of what it can do. A record has a level, a message, and key-value attributes, and a handler decides how it is written. The same calls produce different output through different handlers:

  • Text vs. JSON. Text (key=value) is pleasant at a terminal. JSON is what log collectors parse without regular expressions. The program's code is identical; only the handler changes.
  • Levels filter: the Debug record was dropped because the default minimum is Info.
  • With returns a logger that carries extra attributes on every record it writes, which is how a request-scoped logger keeps its ID, and how the daemon stamps everything with service=banditd.
  • Groups nest related attributes: server.addr in text, an object in JSON.
  • ReplaceAttr is a hook that sees every attribute just before it is written. Here it drops the timestamp so the demo's output is stable; exercise 2 uses it to hide secrets.
  • Prefer attributes over formatted messages: log.Info("request", "status", 200), not log.Info(fmt.Sprintf("request status=%d", 200)). The first can be filtered and aggregated by field.

Step 4: options, a delay, and a draining flag

Two small additions to the server support the rest of the chapter. First, New gains optional settings. The idiom for that in Go is functional options: each option is a function that adjusts the value being built, and the constructor takes a variable number of them.

Callers that need nothing write server.New(pol, log), as before; a caller that does writes server.New(pol, log, server.WithSelectDelay(time.Second)). New options can be added later without changing any existing call, and each option documents itself by name, which a long list of positional parameters or a config struct with many zero-value fields does not.

WithSelectDelay makes /select slow on purpose. A real policy may consult a model or a feature store and take tens of milliseconds, and a service with no slow requests is a poor place to test timeouts, shutdown, or load. The delay respects the request's context, so a client that gives up frees the handler immediately:

The response can never be delivered, but a log line saying 499 is more honest than one saying 200. Step 5: graceful shutdown

Chapter 8's server stopped by calling srv.Close(), which drops every connection immediately, including requests in the middle of being answered. During a deploy or a scale-down, that turns into errors for real users. Graceful shutdown means: stop taking new work, finish the work in progress, then exit.

Orchestrators do this in a standard sequence: send SIGTERM, wait some grace period, then send SIGKILL, which cannot be caught. The service's job is to finish before the SIGKILL. There is a subtlety with load balancers, too. A balancer learns that an instance is going away by failing its health check, and that takes a few seconds. If the instance stops listening at the instant it gets SIGTERM, requests the balancer sends in those seconds are refused. The fix is a drain delay: on SIGTERM, start failing the health check but keep accepting connections for a moment.

The sequence in Serve:

  1. Serve until either the listener fails or ctx is cancelled (by a signal, in the daemon).
  2. Call OnShutdown (the daemon passes srv.SetDraining) and wait DrainDelay, while still accepting requests.
  3. Call srv.Shutdown(ctx). It closes the listeners so no new connections arrive, closes idle keep-alive connections, and waits for active requests to complete, until its context ends.
  4. If the grace period runs out first, Shutdown returns the context's error and leaves the stragglers running, so Serve calls Close to cut them off and returns an error wrapping context.DeadlineExceeded.

One detail: the deadline for step 3 cannot come from ctx, since that context is exactly what was cancelled to start the shutdown, and a context derived from it would be dead on arrival. context.WithoutCancel(ctx) (Go 1.21) returns a context that keeps the parent's values but is never cancelled by it, and WithTimeout then adds the grace deadline.

Step 6: the daemon

With the pieces in place, cmd/banditd is short. main handles only what belongs to a process: signals and exit status. Everything else is in run, whose inputs are explicit so a test can call it.

  • SIGTERM is what Docker, Kubernetes, and systemd send to ask a process to stop; SIGINT is Ctrl-C. Handling both makes the daemon behave the same under a terminal and in a container. SIGKILL cannot be handled.
  • The small goroutine calls stop() after the first signal, which restores default signal handling. A second Ctrl-C therefore kills the process immediately, an escape hatch if a graceful shutdown hangs.
  • Exit status 2 is for configuration mistakes and 1 for runtime failure, the convention from chapter 3. A clean shutdown, and -h, exit 0.

Step 7: watch it stop

The script below starts the real binary twice with a deliberately slow /select (one second in the first run, three in the second) and sends SIGTERM while a request is in flight. Configuration goes in through environment variables, exactly as a container would supply it.

In the first run, the health check reads 200 before the signal and 503 during the drain delay, and the slow request still completes with 200 after the signal. The server exits 0, and its log shows the sequence: shutting down, the 503 health check, the finished request, shutdown complete.

In the second run, the grace period (300 ms) is shorter than the request (3 s). The server warns, closes the connection, and exits 1 with the deadline error. The client sees an empty reply (curl exit code 52), and the handler notices the closed connection through its request context and logs the request as 499. If you set the grace period higher than your longest normal request, and lower than your orchestrator's kill timeout, this second case only happens when something is wrong.

Exercises

Starters and tests are in exercises/ch09.

1. Flag, environment, default

In exercises/ch09/ex1, implement Load(args, getenv, stderr) for a two-setting config: -port / PORT (default 8080) and -debug / DEBUG (default false). A flag beats the environment, which beats the default. An unparsable environment value must produce an error naming the variable; a port outside 1-65535 is an error from any source.

Reference answer

The environment is applied first, then the flags are parsed over the top, so the flag wins whenever it is present without extra bookkeeping. flag.ContinueOnError plus SetOutput turns bad flags into returned errors rather than an exit, which is what makes the function testable. The port range is checked after parsing so that it applies whichever source supplied the value.

2. A logger that hides secrets

Implement NewRedactingLogger(w io.Writer, keys ...string) *slog.Logger in exercises/ch09/ex2. It writes JSON, and any attribute whose key is in keys has its value replaced with "[REDACTED]", including attributes inside groups and attributes added with With. Do not write a handler from scratch.

Reference answer

ReplaceAttr is called for every attribute at write time, at any group depth, so one small function covers all three cases in the tests. Returning the attribute unchanged keeps everything else, including the built-in time, level and msg. Matching by key is a safety net, not a guarantee: a secret logged under a different key, or embedded in a message string, is not caught. The reliable defence is not to log secrets.

3. Shut a server down gracefully

Implement Shutdown(srv *http.Server, grace time.Duration) error in exercises/ch09/ex3. It waits up to grace for in-flight requests; if they finish, it returns nil; if not, it closes the remaining connections and returns an error that wraps context.DeadlineExceeded.

Reference answer

The whole idea is two calls in the right order: Shutdown with a deadline, then Close if the deadline was hit. Shutdown does not abort stragglers when its context expires; it just stops waiting. Wrapping with %w keeps errors.Is(err, context.DeadlineExceeded) true for callers.
