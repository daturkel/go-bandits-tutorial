What you will build

An HTTP service around the policy from chapter 6. A client asks POST /select for an arm and gets back the arm plus a request ID. Later, when it knows whether the choice paid off, it calls POST /reward with that ID and the reward. Two more routes, GET /stats and GET /healthz, let you look inside and check that it is alive. Around the handlers sit three pieces of middleware: request IDs, request logging, and panic recovery.

The Go standard library is enough for all of it: net/http for serving, encoding/json for bodies, log/slog for logs, and net/http/httptest for testing without a network. No web framework is involved.

Concepts introduced

  • http.Handler, http.HandlerFunc, and http.ServeMux patterns with methods and wildcards
  • JSON with encoding/json: struct tags, pointers for optional fields, strict decoding
  • HTTP status codes and a consistent error shape
  • Middleware as functions that wrap handlers; embedding to intercept a ResponseWriter
  • Context values, with a private key type
  • Server timeouts
  • Type assertions
  • httptest: NewRequest, NewRecorder and NewServer

Go vs. Python

Flask and FastAPI sit on top of a separate server (gunicorn, uvicorn). In Go, net/http is the server, and it is the one production services run. It handles every request in its own goroutine, so handlers are ordinary blocking functions: no async def, no worker-process tuning. The other side of that is what chapter 6 prepared you for: handlers run concurrently, and anything they share must be safe to share. There is no pydantic here either. You decode into a struct, then validate by hand. Third-party routers such as chi exist, but since Go 1.22 the standard ServeMux handles methods and path parameters well enough that this course does not need one.

GET /healthznone200 {"status": "ok"}

Errors are JSON, {"error": "message"}, so a client can always parse the body. The status code carries the category (400 for a request that cannot be understood, 422 for one that is well-formed but has a bad value, 409 for a conflict with existing state) and the message carries the detail. Any other method on these paths gets 405 automatically.

Details:

  • Struct tags (`json:"request_id"`) map Go's capitalised field names to JSON keys. Only exported fields are encoded.
  • DisallowUnknownFields turns a misspelled field ("rewrad": 1) into a 400 instead of a silently ignored value that would look like a missing reward.
  • The trailing-data check matters because Decode reads one value and stops. {...} {...} would otherwise pass.
  • http.MaxBytesReader caps how much of the body is read. Without it, a client can send gigabytes. It reports the overflow as an *http.MaxBytesError, which badBody finds with errors.As (chapter 3) and turns into 413.
  • After WriteHeader, an encoding failure cannot change the status, so writeJSON discards it deliberately, with a comment saying why.

Step 3: remembering selections

A reward names an earlier selection, so the service has to remember which arm each request ID returned. For now that is a map behind a mutex, the same pattern as chapter 6:

claim does the lookup and the "mark as rewarded" step under one lock. That makes rewards idempotent: a client that retries after a network timeout gets a 409 and the policy is not updated twice. Two separate steps (look up, then mark) would let two concurrent retries both succeed.

This store only grows, and it vanishes on restart. A selection whose reward never comes stays in memory forever. Chapter 10 fixes both.

handleSelect reuses the HTTP request's own ID as the selection ID. That gives the client one identifier for both the response header and the later reward, and it means the ID exists before the handler runs, courtesy of the middleware below.

  • Reward is a *float64. A plain float64 cannot tell "the client sent 0" from "the client sent nothing", and both would look like a reward of zero. A nil pointer means the key was absent.
  • The checks run cheapest first, and everything is validated before the pending store is touched. A malformed request must not use up a request ID.
  • The reward test is written !(r >= 0 && r <= 1) for the same NaN reason as in chapter 3, even though JSON cannot carry a NaN. The habit is cheap.
  • Success is 204 No Content: nothing to say beyond "recorded".

Step 5: routes

Since Go 1.22, a ServeMux pattern can start with a method ("POST /select") and contain wildcards ("GET /arms/{arm}", read with r.PathValue("arm"); exercise 2 uses that). A request whose path matches but whose method does not gets 405 Method Not Allowed and an Allow header, with no code from you. One consequence: the automatic 404 and 405 responses are plain text, not the JSON used elsewhere. Adding a catch-all "/" route to make 404 JSON would also turn every wrong-method request into a 404, so this service accepts the inconsistency.

Request IDs and context values

Chapter 7 introduced context values as something to use sparingly, and a request ID is the textbook use: it crosses API boundaries and no function's signature should have to mention it. The key is a private empty struct type, ctxKey, so no other package can accidentally use the same key, and RequestID gives typed access. r.WithContext returns a shallow copy of the request carrying the new context. rand.Text() (Go 1.24) returns 26 random base32 characters from a cryptographic source, enough that IDs will not collide or be guessable. The server generates them itself and ignores a client-supplied X-Request-ID, because a client that could pick its own IDs could collide with someone else's pending selection.

Logging

To log the status code, the middleware needs to see what the handler wrote, and ResponseWriter has no getter for that. The trick is a wrapper that embeds the real writer, so every method passes through, and overrides just the two that reveal the status:

This is the embedding from chapter 2 again, applied to an interface: statusRecorder satisfies http.ResponseWriter because the embedded field does. One catch is that optional capabilities of the real writer (flushing, hijacking) are hidden by the wrapper. The Unwrap method lets http.ResponseController find them.

The logger is a *slog.Logger from log/slog, the standard structured logger. Each call takes a message and alternating key-value pairs, and the output is machine-parseable (key=value here; a JSON handler is a one-line change in chapter 9).

Recovering from panics

A panic in a handler unwinds that goroutine. Without this middleware, net/http catches it, logs it, and closes the connection without sending any response, so the client sees a dropped connection instead of an error. The deferred function calls recover(), logs the value and stack, and writes a 500 that does not include the panic message (which could leak internals). http.ErrAbortHandler is a deliberate signal to abort a response quietly, so it is re-panicked.

The order in Handler was chosen with this in mind. recoverPanic is innermost, so logging sees the 500 it writes and logs it. Put recovery outside logging, and a panicking request would never be logged at all.

Step 7: serving, with timeouts

The serve subcommand builds the policy from flags and runs the server until Ctrl-C:

Points worth knowing:

  • http.ListenAndServe is convenient and dangerous: the http.Server it creates has no timeouts. A client that opens a connection and sends nothing holds it, and a goroutine, forever. Set at least ReadHeaderTimeout; the others bound the whole request read, the response write, and idle keep-alive connections. Long-lived responses (streaming, server-sent events) need a longer or per-request write deadline.
  • Creating the listener with net.Listen first means "address already in use" fails before the program says it is listening.
  • serve takes a listener and a handler rather than an address, so a test can pass 127.0.0.1:0 (any free port) and learn the port from the listener.
  • On cancellation it calls srv.Close(), which drops connections immediately, including requests in flight. That is acceptable for a first version and not for production; chapter 9 replaces it with Shutdown, which drains.

Things to see in that output:

  • Every response has an X-Request-Id header, and for /select it equals the request_id in the body. The matching lines in the server log carry the same ID.
  • The reward is accepted once (204), then rejected as a conflict (409) when repeated. The malformed and unknown cases get 422 and 404. GET /select gets 405 with Allow: POST from the mux, in plain text.
  • Timestamps and IDs differ on every run. The rest is deterministic, because the policy is seeded.
  • The log's first /healthz entry is the script's own readiness check.
  • The final stopping line is the interrupt arriving, via the signal-aware context from chapter 7.

What the three back-to-back selections show

Near the end, three selections in a row return arm 1 each time. The first selection returned arm 0 and was rewarded, so UCB1 next wants an arm it has never tried. But arm 1 has no pulls until its reward arrives, and no reward has. A policy only learns from rewards, not from the fact that it made a choice, so until feedback comes back, a deterministic policy repeats itself. TestSelectionsWithoutFeedbackRepeat pins the behaviour down:

In the chapter 4 simulations, every choice was rewarded before the next one. A real service is different: rewards arrive late, out of order, or never. Randomised policies such as Thompson sampling spread their choices across plausible arms in the meantime, which is one reason they cope better. How much delay costs, and how to make UCB1 cope with it, is the subject of chapters 10 and 12.

Exercises

Starters and tests are in exercises/ch08.

1. Bearer-token middleware

Implement BearerAuth(token string) in exercises/ch08/ex1. It returns a func(http.Handler) http.Handler that lets a request through only if it carries Authorization: Bearer <token> with the exact token. Otherwise it responds 401 with a WWW-Authenticate header and a JSON body, and never calls the wrapped handler. Compare tokens with crypto/subtle.ConstantTimeCompare.

Reference answer

The early return after writing the 401 is the whole point of middleware that rejects: forget it and the request continues into the protected handler as well. strings.CutPrefix both tests for the scheme and strips it. A plain == on secrets can leak, through timing, how many leading bytes were right; the constant-time compare removes that signal. Note also that the expected token is converted to bytes once, outside the per-request function.

2. A route with a path parameter

In exercises/ch08/ex2, implement Routes(stats func() []ArmStat) http.Handler with two routes: GET /arms returns all arms as a JSON array, and GET /arms/{arm} returns one. A non-numeric arm is 400; a number outside the slice is 404. Read the wildcard with r.PathValue.

Reference answer

The pattern with {arm} matches exactly one path segment. strconv.Atoi distinguishes "not a number" (an error, so 400) from "a number that does not exist" (a range check, so 404), which are different client mistakes. Calling stats() inside each handler, not once at setup, means every request sees current data. The mux supplies the 405 for other methods without any code.

3. Shed load with a concurrency limit

Implement MaxInFlight(n int) in exercises/ch08/ex3: middleware that allows at most n requests inside the wrapped handler at once. When all slots are busy, a new request must not queue: it gets an immediate 503 with Retry-After: 1.

Reference answer

This is chapter 7's semaphore combined with select and a default case: the send on a full buffered channel would block, so the default turns "no slot free" into an immediate branch. The semaphore is created once, outside the returned functions, so every request shares it. Refusing quickly is usually better than queueing when a backend is slow: queued requests hold connections and memory, and the clients waiting on them have often given up already.
