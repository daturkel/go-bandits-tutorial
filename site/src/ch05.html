Goroutines and channels

Putting go in front of a function call starts it in a new goroutine and returns immediately. A goroutine is a lightweight thread managed by the Go runtime rather than the operating system. It starts with a stack of a few kilobytes that grows as needed, so programs routinely run tens of thousands at once. The runtime multiplexes them onto a small pool of OS threads, by default one per CPU core.

Go vs. Python

Python has two concurrency models, and neither maps directly. Threads share memory but the GIL lets only one run Python bytecode at a time, so CPU-bound work does not speed up; multiprocessing gets real parallelism at the price of separate processes and pickled messages. asyncio multiplexes many tasks on one thread, and every function that can wait must be marked async and called with await. Goroutines are closer to threads that are cheap and truly parallel: any ordinary function can be started with go, blocking calls are fine because the runtime parks the goroutine and runs another, and there is no async colouring to spread through your code. The trade-off is that goroutines share memory by default, which is what chapter 6 is about.

Goroutines need a way to hand values to each other. A channel is a typed conduit: ch <- v sends, v := <-ch receives. On an unbuffered channel, made with make(chan int), a send waits until another goroutine is ready to receive, and the reverse, so it doubles as synchronisation. A buffered channel, make(chan int, 2), holds up to that many values before a send waits. Before you run this program, predict how many messages it counts and in what order they arrive:

Run it with go run ./_examples/chanbasics:

Things to take from it:

  • sync.WaitGroup counts running goroutines: wg.Add(1) before starting one, wg.Done() when it finishes, wg.Wait() blocks until the count is back to zero. Done is usually deferred: defer wg.Done() as the goroutine's first line runs it however the function returns.
  • Only the sending side closes a channel, with the built-in close(ch), and only when nothing else will send. Here a helper goroutine waits for all the senders and then closes. Sending on a closed channel panics; receiving from one returns what is left and then the zero value.
  • for v := range ch receives until the channel is closed and drained. v, ok := <-ch reports the same condition with ok == false.
  • go func() { ... }() starts a function literal in a goroutine; the trailing () calls it. It can use the variables around it. Since Go 1.22 each iteration of a for loop has its own copy of the loop variables, so a goroutine started in a loop sees that iteration's values. Older code wrote i := i first; that is why, if you meet it.
  • The three messages arrive in whatever order the goroutines finish, so the program counts them instead of printing them.

Get the pairing wrong and the runtime tells you. A send with no receiver anywhere, in a program with nothing else running:

When every goroutine is blocked, the runtime detects it and aborts, naming the state each one is stuck in (chan send here). The detector only fires when all goroutines are stuck. In a larger program, one blocked goroutine among many running ones is silently leaked. Chapter 7 covers how to avoid and find those.

Fan out, fan in

The work is one job per (policy, seed) pair, all independent. The concurrent version starts a goroutine for each job (the fan-out), and every goroutine sends its outcome on one shared channel, which a single loop receives from (the fan-in). Three rules make it correct:

  1. Results go to fixed slots. Goroutines finish in an arbitrary order, and the report must not depend on it. An outcome carries the indexes of its job, and the collecting loop stores it at runs[policy][seed]; afterwards the curves are summarised in index order, exactly as the sequential loop would have produced them. Appending outcomes as they arrive would give a report that changes from run to run.
  2. Only the collecting loop touches the results. It runs on the calling goroutine, so the slices it fills need no protection.
  3. Everything sent is received. If the loop returned at the first error, the remaining goroutines would block forever on a send that nobody reads, and leak. So the loop drains the channel completely, and the channel is closed by a separate goroutine that waits for every sender, just as in chanbasics.

Errors need the same care as results. If two policies are misspelled, which error should the user see? Whichever goroutine happened to fail first would be a different answer on each run. Store errors in slots too, and after the loop report the first failure in (policy, seed) order, the one CompareSequential stops at.

Hint 1: the shape

Four parts, in order: declare a small outcome struct (policy index, seed index, the bandit.Result, an error) and an unbuffered channel of it; a double loop that starts one goroutine per job; a goroutine that waits for all of them and closes the channel; and a for o := range results loop that stores each outcome. After the loop, check the errors in order, then summarise.

Hint 2: the goroutines 
var wg sync.WaitGroup
for p, policySpec := range spec.Policies {
    for i := range spec.Seeds {
        wg.Add(1)
        go func() {
            defer wg.Done()
            res, err := runOnce(spec, policySpec, spec.BaseSeed+uint64(i))
            results <- outcome{policy: p, seed: i, res: res, err: err}
        }()
    }
}
go func() {
    wg.Wait()
    close(results)
}()
Hint 3: the slots

Before the loop, allocate runs := make([][][]float64, len(spec.Policies)), and in a loop over the policies give each runs[p] a slice of spec.Seeds curves; do the same for a [][]error, and keep a []string of policy names (each run's res.Policy). After the receive loop, walk the errors in order and return the first, wrapped as CompareSequential wraps it; otherwise build the report with summarise(names[p], runs[p]) for each policy.

Answer

The closer has to be its own goroutine: wg.Wait() in the calling goroutine, before the receive loop, would wait for senders that are themselves waiting for a receiver, a deadlock. Comparing curves from the two versions with !=, as the test does, is legitimate here because both compute each mean from the same numbers in the same order.

What this version does not do

  • It starts as many goroutines as there are jobs. With 4,000 runs that is fine. With 400,000 they would all exist at once, each holding a 40 KB regret curve. The usual remedy is a fixed number of worker goroutines pulling jobs from a channel, which chapter 7 builds.
  • It cannot be cancelled. Once started, Compare runs to the end, even after the first job has failed. Chapter 7 adds context.Context.
  • It shares nothing mutable. That is why no locks appear. When goroutines do share a policy, as a server's request handlers will, the next chapter's tools are needed.

What you learned

  • go f() starts a goroutine; goroutines are cheap, and the runtime spreads them across all cores.
  • Channels pass values between goroutines and synchronise them; only the sender closes, and range receives until the close.
  • A sync.WaitGroup waits for a set of goroutines; a separate goroutine that waits and then closes the channel lets the receiver finish.
  • Concurrent results stay deterministic when each one goes to a fixed slot and errors are chosen by order, not by arrival.
  • Every value sent must be received, or a goroutine blocks forever; the runtime reports a deadlock only when everything is stuck.

Extra 1: ParallelMap

Call f on every element in its own goroutine and return the results in input order. One test makes all calls wait for each other, so it only passes if they really overlap.

Answer

Each goroutine writes to out[i], a different memory location from every other goroutine's, so there is no race and no lock. wg.Wait() also guarantees the writes are visible to the caller before it reads the slice. It is the same idea as the harness's slots, without a channel.

Extra 2: merge several channels into one

Every value from any input must appear on the output, and the output must close after all inputs have closed. <-chan int is a receive-only channel; a function that only reads from a channel should say so in its type.

Answer

This is fan-in as a reusable function: one forwarding goroutine per input, plus one closer that waits for them all. Closing from the forwarders themselves would be a bug: the first one to finish would close a channel the others are still sending to, and that panics.

Extra 3: a two-stage pipeline

Generate sends the numbers, then closes; Square squares each value and closes when its input closes. The test chains them: Square(Square(Generate(1, 2, 3))).

Answer

Each stage owns the channel it creates: it is the only sender, so it is the one that closes it, and defer close(out) makes that hard to forget. Stages connected this way run concurrently, so a slow consumer applies backpressure all the way up the chain through the unbuffered sends. A consumer that stops reading early would strand the upstream goroutines; chapter 7 fixes that with cancellation.
