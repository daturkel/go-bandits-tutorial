What you will build

Chapter 2 left several failure modes unhandled: a probability of 1.7 was accepted, an unknown scenario returned a bare false, and a misbehaving policy would crash with an index error. This chapter makes every one of them an explicit, testable error, and then puts a real test suite around the simulator: table-driven tests, a golden-file test for the CLI's output, and benchmarks that tell you what a policy step costs.

Concepts introduced

  • error as an ordinary interface value; returning and checking errors
  • Sentinel errors, custom error types, wrapping with %w, and errors.Is, errors.As, errors.Join
  • When to panic instead
  • The testing package: table-driven tests, subtests, t.Helper, t.Fatal vs. t.Error, t.TempDir
  • Golden files and a custom -update flag
  • Benchmarks with b.Loop, allocation reporting, and coverage
  • gofmt and go vet

Step 1: errors are values

Go has no exceptions. A function that can fail returns an error as its last result, and the caller decides what to do about it on the very next line:

error is just an interface with one method, Error() string. Anything that has that method is an error, which is why the same mechanism covers a plain message, a rich struct, and a chain of causes.

Go vs. Python

In Python an exception unwinds the stack until something catches it, and any line can raise. In Go, control flow is visible: every place that can fail says so in its signature, and every caller writes down what happens. It is more typing, and the payoff is that reading a function tells you all of its exits. The unwinding mechanism does exist (panic and recover), but it is reserved for bugs, not for expected failures. As a rule: if a caller could reasonably cause it, return an error; if only a programmer mistake could cause it, panic.

The error vocabulary for this project lives in one file:

There are two kinds of error here, and they answer two different questions:

  • Sentinel errors such as ErrNoArms are package-level values made with errors.New. They answer "what went wrong?" Callers compare against them with errors.Is.
  • Error types such as ArmError carry data. They answer "where or with what?" Callers extract them with errors.As. The Unwrap method links the outer error to the one it wraps, so errors.Is(err, ErrInvalidProbability) still finds the sentinel inside an ArmError.

Note the pointer receivers again: *ArmError is the error type, and code creates and matches it as a pointer.

Step 2: validating the environment

Constructors now return (*Env, error). This one reports every bad probability at once, which is kinder than making the user fix them one at a time:

fmt.Errorf with %w wraps an error: the message gets added context ("invalid environment: ..."), and the original stays reachable through Unwrap. Use %v instead of %w and you get the text but sever the chain, which is a bug to avoid when callers need to inspect the cause. errors.Join combines several errors into one whose Unwrap() []error exposes all of them; errors.Is and errors.As search every branch.

The condition is written !(p >= 0 && p <= 1) rather than p < 0 || p > 1 on purpose: every comparison with NaN is false, so the second form would let NaN slip through as "valid".

Step 5: main becomes testable

A function that calls os.Exit cannot be tested. The standard fix is to move all the work into a function that takes its inputs and outputs as parameters and returns an error, leaving main a three-line shell:

flag.ContinueOnError makes flag parsing return errors instead of exiting, and io.Writer lets tests capture the output in a buffer while main passes os.Stdout. A second sentinel, errUsage, marks "you invoked the program wrong" so that main can choose exit status 2 for those and 1 for everything else, using errors.Is; with the two-%w form of fmt.Errorf (Go 1.20+) the error keeps both the usage marker and the specific cause.

The strconv message in the second case is the original error, still intact several layers down. (go run prints the exit status lines itself.) Note that nothing is printed before the error: run builds every environment and policy first, and only then starts writing the report.

Step 6: tests

A test is a function TestXxx(t *testing.T) in a file ending in _test.go, in the same directory (and by default the same package) as the code. go test compiles them together, runs them, and reports. There are no fixtures and no assertion library: you use ordinary if statements and report failures with t.Errorf (mark failed, keep going) or t.Fatalf (mark failed, stop this test).

Table-driven tests and subtests

The idiomatic shape for a function with many cases is a slice of structs, one per case, run in a loop with t.Run. Each case becomes a named subtest that can pass or fail and be selected on its own:

Adding a case is one line. The test checks the two ways errors are inspected: errors.Is for the category, and errors.As to reach the *ArmError buried inside the join and the wrapper.

Subtest names come from the case's name field, with spaces turned into underscores. The last policy case has an empty spec, so Go names it #00. You can run one case with go test -run 'TestNewEnvValidation/nan'.

Determinism and a golden file

Because every random draw comes from a seeded generator, simulations are ordinary deterministic functions and can be tested with equality: same seed, same result. The CLI's whole output is pinned with a golden file: the expected text lives in testdata/ (a directory the Go tool ignores when building), and the test compares against it:

-update is a flag the test registers itself. When you change behaviour on purpose, go test -run TestGolden -update rewrites the file and git diff shows precisely what changed. If a refactor changes a number by accident, the test tells you.

Step 8: benchmarks

A benchmark is a function BenchmarkXxx(b *testing.B). Since Go 1.24 the loop is for b.Loop() { ... }: the framework decides how many iterations to run, and setup before the loop is excluded from the timing. (Older code writes for i := 0; i < b.N; i++; it still works.)

b.Run creates sub-benchmarks, one per policy, and ReportAllocs adds memory statistics. Run only benchmarks (-run '^$' selects no tests):

Read the columns as: iterations run, nanoseconds per operation, bytes allocated per operation, allocations per operation. On the machine that produced this output, one Select plus Update costs on the order of a hundred nanoseconds with zero allocations, and a whole 10,000-step run takes about a millisecond. The 82 KB and 11 allocations per run are set-up costs paid once per simulation (the 80 KB regret curve, plus the environment, policy and generators the benchmark builds inside its loop), not per-step garbage. Those numbers are hardware-specific; only the relationships transfer. That matters later: when the service is under load (chapter 11), "zero allocations per decision" is the property to protect.

Benchmarks tell you what a change did, not what to change. Compare runs with benchstat and profile with pprof, which chapter 11 introduces.

Coverage

Coverage shows which lines tests execute, not whether they check anything. The uncovered part of the root package is mostly main itself, which is exactly why the logic was moved into run.

2. A typed error that unwraps to a sentinel

In exercises/ch03/ex2, fill in RangeError (message arm 7 out of range [0, 3)), make it Unwrap to ErrOutOfRange, and implement CheckArm. The last test guards against the typed-nil trap from step 3.

Reference answer

CheckArm ends with a literal return nil. Writing var e *RangeError; return e would return a non-nil error holding a nil pointer, and err != nil would be true.

3. Remove an allocation

Normalize in exercises/ch03/ex3 works but allocates a fresh slice on every call. Make it write into dst instead, so a caller who reuses a buffer pays nothing. The test uses testing.AllocsPerRun; run go test -bench . -benchmem ./ex3 before and after.

Reference answer

dst = dst[:0] keeps the backing array but resets the length, and append only allocates if the capacity runs out. This append-into-a-caller-buffer shape is used throughout the standard library (strconv.AppendInt, append(buf, ...) on []byte); the name of a function like that usually starts with Append.
