07 Part II: Concurrency · Chapter 7

Context, select, worker pools

Cancellation, timeouts and bounded worker pools without goroutine leaks.

Starting point

Your own project as it stood at the end of Chapter 6. If yours has drifted, or you are skipping ahead, tools/start.sh ch06 work/banditlab copies the reference version into a new directory.

What you will build

A harness that can be stopped. Chapter 5's Compare started one goroutine per run and could not be interrupted. Here it runs on a fixed-size pool of workers, honours a deadline or Ctrl-C within milliseconds, cancels the remaining work when one run fails, reports progress while it runs, and leaves no goroutines behind. The pool is a small generic package you can reuse for anything that fits "many independent jobs".

The same three ideas carry over to a server, which is where they matter most: a request that times out or whose client disconnects should stop consuming CPU, and a shutdown should let in-flight work finish or cancel it cleanly.

Concepts introduced

  • select: waiting on several channel operations at once, timeouts, and default
  • context.Context: cancellation, deadlines, WithCancel, WithTimeout, WithCancelCause
  • The convention that ctx is a function's first parameter
  • Bounded worker pools, and a generic pool.Run
  • Goroutine lifecycle: how a goroutine leaks, and how to find one
  • signal.NotifyContext for Ctrl-C
  • time.Ticker, and a goroutine that reports progress

Step 1: select

A receive on a channel waits until a value arrives. select waits on several operations at once and runs the case of whichever becomes ready first. It looks like a switch whose cases are sends and receives. This program shows the four forms you will use most:

  1. Timeout. time.After(d) returns a channel that receives one value after d. Putting it in a select next to the real operation bounds the wait.
  2. default makes the select non-blocking: if no other case is ready right now, it runs immediately.
  3. Several sources. The loop handles ticker events until the deadline channel fires. When more than one case is ready, Go picks one at random, so never rely on case order. The label loop: lets break loop leave the loop instead of only the select.
  4. Contexts. A context exposes "stop now" as one channel, ctx.Done(), which is closed when the context ends. That is why cancellation composes with select.

A nil channel is never ready, so setting a channel variable to nil removes its case from a select. That is occasionally useful for turning a case off.

Step 2: context

A context.Context carries a cancellation signal, and optionally a deadline, down a call tree. You create one from another: context.WithCancel(parent) returns a child and a cancel function; context.WithTimeout(parent, d) returns a child that cancels itself after d. Cancelling a context cancels every context derived from it, so one call at the top stops everything beneath. After cancellation, ctx.Err() is context.Canceled or context.DeadlineExceeded. WithCancelCause lets you record why, and context.Cause(ctx) reads it back (case 5 above).

The conventions are worth following exactly, because the whole ecosystem does:

  • ctx is the first parameter, named ctx: func Run(ctx context.Context, ...).
  • Always call cancel, usually with defer cancel() right after creating the context. Releasing it frees the timer and the link to the parent. go vet warns if you forget.
  • Do not store a context in a struct; pass it along the call path. A context describes one operation, not an object.
  • Cancellation is cooperative. Nothing is interrupted. Code that can run for a long time must look at the context, either with ctx.Err() or by including <-ctx.Done() in a select.
  • Contexts can also carry request-scoped values. Use that sparingly, for things like a request ID that cross API boundaries, never for ordinary parameters.

Go vs. Python

asyncio cancels a task by raising CancelledError at its next await, and a thread cannot be cancelled from outside at all. A Go context does neither: it sets a flag and closes a channel, and the code being cancelled decides where to look. That is less magical and more explicit, since every blocking point must handle it, and it is why Go APIs that block take a ctx. asyncio.timeout() is the closest equivalent of WithTimeout, and the idea of a deadline that propagates to everything beneath it is the same.

Step 3: make the simulation cancellable

A simulation is a tight loop, so the question is where to look at the context. Checking it on every step would cost noticeably more than the step itself (a step takes on the order of a hundred nanoseconds), so Run checks every 1,024 steps. That bounds the delay between cancellation and stopping to about a thousand steps, well under a millisecond.

The context becomes the first parameter, and the error wraps ctx.Err() so callers can test errors.Is(err, context.Canceled). The partial result is returned with it, as for the out-of-range arm error in chapter 3. Step 4: how goroutines leak

Chapter 5 said that a goroutine blocked forever is invisible unless every goroutine in the program is blocked. It uses memory and whatever it references for the life of the process, and a server that leaks one per request eventually runs out. The typical cause is a send with no receiver, like this one:

Both functions start a worker and wait for its result, giving up after a timeout. In fetchLeaky the channel is unbuffered, so if the caller has already left, the worker's send has nowhere to go and blocks for good. In fetchFixed the channel has room for one value, so the send completes and the goroutine exits. The program calls each a thousand times with a timeout shorter than the work, and then asks the runtime what is still running:

Two ways to find this in a real program. runtime.NumGoroutine() gives a count, and a count that rises with traffic and never falls back is the signature. The goroutine profile, pprof.Lookup("goroutine") (or /debug/pprof/goroutine on a server, chapter 11), groups goroutines by where they are stuck: 1,000 of them at main.go:20, the send. Tests can assert on the count too, which is what the waitForGoroutines helper in this chapter's tests does.

The rule to take from this: for every goroutine you start, know how it will end. It ends when its function returns, so ask what it could be blocked on. A send needs a receiver or buffer space, a receive needs a sender or a closed channel, and any wait should also include ctx.Done(). Exercise 3 is this bug to fix.

Step 5: a bounded worker pool

Chapter 5 started one goroutine per job. That works for hundreds of jobs and does not for millions, and it ignores the fact that only as many jobs can run at once as there are cores. The standard shape is a fixed number of workers that take jobs from a channel. Now that the lifecycle rules are in hand, here it is as a reusable generic function:

Walk through it in the order things happen:

  1. Workers (a fixed count, never more than the number of jobs) loop over work until it is closed, run f, and send an outcome.
  2. The feeder sends job indexes into work. Its select also watches ctx.Done(), so after cancellation it stops handing out jobs and closes work, which lets the workers exit. Without that case it would block forever on a send that no worker will ever take.
  3. The closer waits for all workers and closes results.
  4. The collector (the calling goroutine) ranges over results and always drains it to the end. That guarantee is why a worker can send without a select: the receiver never leaves early. The first ordinary failure calls cancel().
  5. Choosing the error. A job that fails because the pool cancelled it reports a context error, and that must not hide the real failure, so context errors are ranked below ordinary ones. The pool returns the lowest-index ordinary error, then the caller's own ctx.Err(), then any remaining context error.

Other design choices: results are indexed by job so the output order never depends on which worker finished first (as in chapter 5); OnDone is called from the collecting goroutine only, so the callback needs no locking; and the function's contract says that no goroutine it started keeps running after it returns. The tests check each of these, including the bound (peak concurrency is exactly the worker count) and the absence of leaks:

The standard library does not include a pool like this. The golang.org/x/sync/errgroup package covers the same ground (its SetLimit bounds concurrency); writing it out once here shows what such a package does, and this one adds ordered results and progress, which the harness wants.

The machine has four cores. Going from 1 to 2 to 4 workers cuts the time roughly in half each time; 16 workers do no better than 4, because there is no more CPU to use. The right pool size for CPU-bound work is about the number of cores; for work that waits on the network it can be far higher.

The progress reporter is a small goroutine with a full lifecycle, and each piece of it comes from this or the previous chapter:

  • The counters are atomic.Int64 (chapter 6): the pool's collector writes them and the reporter reads them, with no lock.
  • The select has three cases: print on the ticker, stop when asked, stop when the context ends.
  • stop closes quit and then waits on finished. Signalling a goroutine to stop is not the same as knowing it has stopped, and the wait is what guarantees no goroutine outlives the command and that its last write happens before stop returns.

Exercises

Starters and tests are in exercises/ch07.

1. First success wins

Implement First[T any](ctx context.Context, fns ...func(context.Context) (T, error)) (T, error) in exercises/ch07/ex1. It runs all functions at once, returns the first successful value, cancels the rest, and does not return until every function has. This is the "hedged request" pattern: ask three replicas, use the fastest answer.

Reference answer

The results channel has room for every result, so no goroutine can block on its send even after First stops caring. The loop still receives all len(fns) results before returning, which is how it waits for the losers: they were told to stop by cancel() and return promptly, provided they watch their context. A function that ignores its context would make First wait for it, and that is the price of the "nothing left running" guarantee.

2. A semaphore from a buffered channel

Implement Limit(n int, tasks []func()) in exercises/ch07/ex2: run every task with at most n running at once, and return when all have finished. Do not use a fixed pool of workers; use a channel with capacity n as a counting semaphore.

Reference answer

Sending on a full buffered channel blocks, so sem <- struct{}{} waits when n tasks hold slots, and the receive in the deferred function frees one. struct{} is the zero-size type, the idiomatic payload for a channel that only signals. This shape starts one goroutine per task but runs only n at a time, which suits few, heavy tasks; for millions of small ones, the fixed pool of step 5 is cheaper.

3. Fix the leak

Fetch in exercises/ch07/ex3 returns early when its context ends, but the goroutine it started blocks forever on the send. The test calls it a hundred times with a short timeout and checks the goroutine count afterwards. Fix it without making Fetch wait for the work.

Reference answer

One character of difference: make(chan string, 1). With room for the single result, the worker's send never blocks, so the goroutine finishes its work, sends into the buffer, and exits even if nobody ever reads it. The buffered value is then garbage collected with the channel. This does not stop the work itself; if work accepted a context it could be cancelled too, which is the better design when you control it.
