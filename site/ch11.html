11 Part III: Serving · Chapter 11

Observability and performance

Prometheus metrics, pprof, a load generator and one real bottleneck.

Starting point

Your own project as it stood at the end of Chapter 10. If yours has drifted, or you are skipping ahead, tools/start.sh ch10 work/banditlab copies the reference version into a new directory.

What you will build

The means to answer "how is the service doing?" and "why is it slow?" with numbers. You will add a /metrics endpoint in Prometheus format, a separate profiling server built on pprof, and banditload, a load generator that plays simulated users against the running service and reports throughput and latency percentiles. Then you will use them the way you would on a real problem: measure, look at a profile, find where the time actually goes, change one thing, and measure again.

The result is modest and honest. The code did not have a 10x problem. It had a 10% one, in a place you would not necessarily have looked, and the profile shows that the places you would have looked (the policy and its lock) are not the cost at all.

Concepts introduced

  • Logs, metrics, and traces as three kinds of evidence; what each is for
  • Prometheus metric types (counter, gauge, histogram), labels, and cardinality
  • A custom prometheus.Collector, and promhttp
  • net/http/pprof; CPU, heap, mutex and goroutine profiles; reading go tool pprof output
  • Benchmarks versus load tests: what each can and cannot tell you
  • Closed-loop and open-loop load, percentiles, and coordinated omission
  • Cost-aware logging: levels by outcome, and skipping work for disabled levels

Three kinds of evidence

  • Logs record individual events. They are what you read to understand one specific thing that happened, and they get expensive when you write one per request.
  • Metrics are numbers aggregated over time: requests per second, the 99th-percentile latency, how many selections each arm received. They are cheap to record whatever the traffic, and they are what you graph and alert on.
  • Traces follow one request across several services. They matter once a request crosses a network hop (chapter 13); OpenTelemetry is the standard for them, and this course only mentions it.

Chapter 9 gave the service good logs. This chapter adds metrics and profiles, and it also turns out that the logs were a cost.

Step 1: metrics

Prometheus pulls: it visits an HTTP endpoint on your service every few seconds, reads the current values, and stores each as a time series. The service's job is only to expose the current numbers in a text format. The official Go client, github.com/prometheus/client_golang, does the bookkeeping. It is this course's second dependency; use the version the course was tested with: go get github.com/prometheus/client_golang@v1.22.0.

Three metric types cover nearly everything:

  • A counter only goes up (requests served, errors, total reward). You never look at its value; you look at its rate of change, which survives restarts because a decrease is read as a reset.
  • A gauge goes up and down (requests in flight, the policy's current estimate for an arm).
  • A histogram counts observations into buckets (request durations). It is how you get percentiles: an average latency of 5 ms can hide 1% of requests taking a second.

Some choices here matter as much as the code:

  • Names and units. Counters end in _total, durations are in seconds and say so, and every metric starts with the service prefix. These conventions are what let generic dashboards and queries work.
  • Buckets. The default histogram buckets start at 5 ms. This service answers in tens of microseconds to a few milliseconds, so the defaults would put every request in the first bucket and hide everything. ExponentialBuckets(0.00005, 2, 16) gives 16 buckets doubling from 50 µs to about 1.6 s. Choose buckets around the values you care about, such as your latency target.
  • Its own registry. The package-level default registry is global state. A registry per Metrics lets tests build as many as they like.

Labels and cardinality

A label splits a metric into separate time series, one per distinct combination of label values. That is powerful and dangerous: every new value costs memory in Prometheus, forever. A label whose values come from user input (a raw URL path, a user ID, a request ID) has no upper bound, and one scanner requesting random paths can create millions of series. The request middleware therefore labels by route pattern, a small fixed set:

r.Pattern (added to http.Request in Go 1.23) is the ServeMux pattern that matched, such as "POST /select". The mux fills it in while routing, so it can only be read after next.ServeHTTP returns. A request that matched nothing has an empty pattern and is counted under one label, unmatched. Two tests pin this down: one requests 50 different nonsense paths and checks that none appears in the output.

Step 2: profiling on a private port

Metrics tell you that something is slow. A profile tells you where. Go ships a sampling profiler: while it runs, it interrupts the program about a hundred times a second and records what every running goroutine is doing. Enough samples show where the time goes. The same package can report heap allocations, lock contention, and goroutine stacks.

Two cautions. Profile endpoints are sensitive: they reveal your code's structure and let any caller make the process do costly work, so they go on a separate listener bound to localhost or an internal network, never on the public port. And a common import trap: importing net/http/pprof for its side effects registers the routes on http.DefaultServeMux, which is easy to serve by accident. Registering them by hand on your own mux avoids that.

The daemon gets a BANDIT_DEBUG_ADDR setting, empty (disabled) by default:

The debug server gets a two-minute WriteTimeout. The main server's 10 seconds would be a trap here: a CPU profile request for 30 seconds writes its response only at the end, and the standard handler refuses to start when the profile is longer than the server's write timeout. Mutex and block profiling are off by default because they cost a little on every contended lock; enabling them only when the debug server is on is a reasonable compromise. The debug server registers with the same WaitGroup as the expiry sweep, so run waits for it to stop, the goroutine lifecycle rule from chapter 7.

Step 3: a load generator

You cannot tune what you cannot reproduce, and typing curl in a loop does not scale. banditload plays the part of many users. Each simulated user asks for an arm, decides whether it "pays" using a real bandit.Env (chapter 1's Bernoulli environment, with a scenario such as needle), and reports the outcome back. So the generator is also an end-to-end check of learning: it reports which arms the service chose and the regret of those choices.

NewClient deserves a comment. The standard client keeps at most two idle connections per host. A load generator with 32 workers then closes and reopens most of its connections on every request, and ends up measuring TCP setup and running out of ports. Sizing the idle pool to the number of workers is the fix, and this is one of the most common mistakes in home-made load tests.

Each worker owns its own measurements (latency slices, counters, a random generator), so nothing is shared while the test runs and there is no locking on the hot path. The results are merged once at the end (the same idea as chapter 6's advice on avoiding a shared lock).

Closed loop and open loop

By default each worker sends its next request as soon as the previous one finishes: a closed loop. It is simple, and it has a flaw. If the server stalls for a second, each worker simply waits, sends fewer requests during that second, and the stall appears in the results as a few slow requests among many fast ones. Real users do not slow down politely when the server does. This is called coordinated omission: the test's own behaviour hides the problem it is trying to measure.

With -rate the generator runs an open loop: arrivals are scheduled at a fixed rate, and a request's latency is measured from the moment it was supposed to start. If the server cannot keep up, the arrivals queue, and the queueing time is counted:

A test proves the difference. The server is given a 50 ms service time and two workers, so its capacity is about 40 requests a second; the generator offers 200 a second. An open-loop test must show large latencies:

Which mode to use depends on the question. Closed loop asks "how much can this handle?" (find the saturation point). Open loop asks "what will users experience at N requests per second?" (measure latency at a load you choose).

Step 4: benchmarks and load tests answer different questions

You already have benchmarks (chapter 3). Here is one for the whole handler chain, run without a network:

A select costs about 10 to 13 µs here, on one core, with no other goroutines. If that were the whole story, four cores would serve on the order of 300,000 requests a second. The load test below measures about 35,000. The gap is not an error. The benchmark isolates one code path; the load test measures the system: the kernel's networking, 32 connections, the load generator competing for the same four cores, the garbage collector, goroutine scheduling, and the log file. A benchmark is the right tool to compare two versions of a function, and the wrong tool to predict capacity. A load test is the reverse. Use benchmarks to protect a hot path from regressions and load tests to answer "how much traffic can this take, and how does latency behave when it gets there?"

The four sub-benchmarks also show something about the fix to come. Logging every request (DEBUG) costs roughly 2.5 µs more per request than not logging (INFO) even when the output is thrown away, and about a microsecond more when it goes to a real file. A benchmark that wrote to io.Discard only would have understated the price by leaving out the write.

Step 5: find the bottleneck

The method, in order:

  1. Measure a baseline with something repeatable. Do not tune without a number.
  2. Profile while under load, not while idle.
  3. Read the profile before guessing. Then change one thing and measure again.

The service so far logs one line for every request. Here is a run with that behaviour (log level debug), 32 simulated users on the needle scenario, half of the selections rewarded. The script also collects a 6-second CPU profile from the debug port while the load runs, and reads it with go tool pprof:

How to read it. flat is time spent in the function itself; cum (cumulative) also includes everything it calls. Total samples above 100% just means more than one core was busy (the profile sums across cores).

  • The single biggest line is syscall.Syscall6, about a quarter of all CPU: reading and writing sockets, and writing the log. That is the price of doing I/O, and Go code cannot make it go away.
  • Garbage collection (gcBgMarkWorker) is about a tenth. Nearly all of the allocation behind it comes from net/http itself (headers, contexts), not from this project's code.
  • The line to notice is slog.(*Logger).LogAttrs: about 11% of CPU is spent formatting and writing log lines, at a volume nobody will ever read.
  • And the code you might have suspected: Locked.Select, which samples ten Beta distributions under a mutex, is about 2% and the store's AddPending is about 1.5%. Sharding the lock or optimising the sampler would have been effort spent on the wrong thing.

The last block, from the mutex profile, shows where goroutines wait for locks rather than where they burn CPU. The store's mutex is where they queue most. That is worth knowing and, at these rates, is not what limits throughput.

Step 6: the fix

A production access log with one line per request is ordinary and mostly useless at volume: nobody reads 33,000 lines a second, and the metrics already count every request. What is worth a log line is the exceptional request. The fix decides the level from the outcome:

  • Routine successes log at Debug: available when you turn the level down while investigating, free otherwise.
  • Client mistakes (4xx) log at Info, slow requests (over half a second by default) at Warn, and server failures (5xx) at Error. The default level shows what someone should look at.
  • log.Enabled(ctx, level) is checked before the record is built. A disabled level then costs a comparison, not the allocation of a list of attributes. This is what slog is designed for; log.Info(fmt.Sprintf(...)) would have formatted the string first and thrown it away.

Tests for the new behaviour check that nothing is logged for routine successes at the default level, that a 404 is Info, a slow success is Warn, a panic's 500 is Error, and the boundaries of the rule:

Now measure again. The profile at the default level, info:

LogAttrs is gone from the profile, and the share of CPU spent in syscalls drops. The throughput comparison uses alternating runs of debug (the old behaviour) and info (the new default), three rounds each, so that drift in the machine affects both equally:

With logging fixed, the median run goes from about 33,500 to about 36,700 requests a second (roughly 10% more), and median latency drops from about 650 µs to 570 µs. The 99th percentile barely moves; it is dominated by things this change does not touch, such as garbage collection pauses and scheduling. The log written drops from over 30 MB per 6-second run to nothing. That is a real, modest, measured improvement. Read results like these with suspicion: the load generator shares four cores with the server, runs vary by several percent, and a difference under about 5% would be noise. Three alternating rounds agreeing in direction is the minimum to believe a change.

What comes next in the profile

You could keep going, and the profile says where. Garbage collection and the store's lock are the next items in the profile. But there is a point at which to stop: when the numbers meet your service's targets, further tuning costs clarity for no benefit. The next real limit is not in Go code at all. Each request needs several system calls, and the load generator is on the same machine. To find the server's true ceiling, run the generator on another host.

Exercises

Starters and tests are in exercises/ch11. The first uses the Prometheus client, so its module has that dependency already.

1. Count responses by status class

Implement CountByClass(reg) in exercises/ch11/ex1: middleware that counts responses in a counter http_responses_total with one label, class, whose values are 2xx, 4xx, and so on. A handler that writes nothing counts as 200. The counter must be created and registered once, not per request.

Reference answer

Registering when the middleware is built, not inside the request handler, matters: registering the same metric twice panics, and creating a metric per request would leak. The recorder starts with status 200 because Go sends 200 if the handler never calls WriteHeader. The label is the class, not the exact code, to keep the number of series small.

2. Estimate a percentile from histogram buckets

A histogram does not keep observations, only counts per bucket. Implement EstimateQuantile(q, upper, counts) in exercises/ch11/ex2 the way histogram_quantile does: find the bucket holding the observation at rank q * total, assume the observations inside it are spread evenly, and interpolate.

Reference answer

The answer is only as precise as the buckets are narrow: within a bucket, the true values could be anywhere, and interpolation assumes evenly. That is why bucket boundaries should sit near the latencies you care about (your target, say), and why a p99 read from a histogram is an estimate while the load generator's, computed from every recorded latency, is exact.

3. Log one in n

Implement Sampler in exercises/ch11/ex3: Allow() returns true for the first call and then every nth, and must be safe for concurrent use without a mutex. This is the other standard answer to noisy logs: keep a sample of routine events.

Reference answer

One atomic add gives every caller a distinct sequence number, so exactly one call in n sees a multiple of n, however the goroutines interleave. A version that read the counter, compared, and wrote it back would have a race, and would let through too many or too few calls.
