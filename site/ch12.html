12 Part IV: Distributed · Chapter 12

Why naive replicas break the bandit

Watch replicas diverge, then fix it with mergeable counts and measure the cost of staleness.

Starting point

Your own project as it stood at the end of Chapter 11. If yours has drifted, or you are skipping ahead, tools/start.sh ch11 work/banditlab copies the reference version into a new directory.

What you will build

Everything so far ran as one process. To survive a crash or handle more traffic you run several copies (replicas) of banditd behind a load balancer, and that breaks something the earlier chapters took for granted: a bandit policy learns from what it has seen, and each replica sees only the requests routed to it. In this chapter you will watch three replicas drift apart, fix it by letting them share their counts through the database, measure what stale counts cost in regret with a simulation, and fix a related problem from chapter 8: UCB1 sends a burst of requests to the same arm while rewards are still in flight.

The design rests on one property of the bandit state. It can be reduced to per-arm counts, and counts from different places add. You do not need consensus, leader election or a distributed lock to combine them.

Concepts introduced

  • Why a stateful learning service cannot simply be copied behind a load balancer
  • Mergeable state: an operation that is commutative, associative and has an identity, and what it buys a distributed system
  • Periodic synchronisation, staleness, and the trade-off between freshness and load on the shared store
  • Advisory locks in PostgreSQL, for work that concurrent processes must not do at the same time
  • Pending-aware UCB1: counting selections that have no reward yet
  • Simulating a distributed system in a deterministic single-process model, before measuring the real one

What goes wrong

Suppose three replicas of the service from chapter 11 share one PostgreSQL database and a load balancer sends each user to one of them. The reward for a selection is written to the database, so no data is lost. But each replica's policy lives in memory and is updated only by the rewards that replica handled. Each one learns from a third of the evidence.

This costs you in two ways. Each replica needs about three times as long to become confident about the best arm, so the system as a whole explores three times as much as it should. And the replicas disagree with each other and with the database, so what /stats reports depends on which replica answers. The database holds everything (the last line), but each replica has learned from about a third of it.

Step 1: combining counts

Chapter 10 reduced every policy to two numbers per arm, Pulls and RewardSum, and gave each policy a Restore method that rebuilds it from them. Totals from different replicas describe disjoint sets of observations, so combining them is addition. Merge does that arm by arm:

Addition has three properties that matter here. It is commutative (a+b == b+a), so the order in which replicas report does not matter. It is associative ((a+b)+c == a+(b+c)), so it does not matter how the merging is grouped: one server can merge all three, or two can merge and hand the result on. And it has an identity (all zeros), so an empty replica changes nothing. A state with these properties is what the distributed-systems literature calls a CRDT-style or "mergeable" state; the practical meaning is that you can replicate it without coordination and every replica ends up with the same answer.

The tests check those laws on random inputs, and check the claim that matters for learning, that merging then restoring gives the same Thompson posterior as one policy that saw all the data:

One property is deliberately missing: Merge is not idempotent. Merging the same replica's totals in twice counts its data twice. Systems that gossip state directly between replicas need a structure that survives duplicates (a per-replica counter, the "G-counter" of the CRDT literature). This design avoids the problem differently: replicas never merge with each other, they all write to one database, and the database's totals are the merged state. Chapter 13 gives the merging job to a dedicated service, and exercise 1 below is the building block that makes that safe.

Step 2: the database as the meeting point

A bug that only appears with replicas

Starting three replicas at the same moment against an empty database failed on the first attempt of the demo at the end of this chapter, with duplicate key value violates unique constraint "pg_type_typname_nsp_index". CREATE TABLE IF NOT EXISTS reads as safe to repeat, and it is safe to repeat sequentially. Two sessions running it at the same instant can both find the table missing, and one of them loses a race inside PostgreSQL's catalog. Chapter 10 never started two servers at once, so nothing exposed it.

The fix is to make the replicas take turns. PostgreSQL's advisory locks are locks on an arbitrary number of your choosing, which the database enforces but attaches to no table. pg_advisory_xact_lock holds one until the transaction ends, so the schema setup, the arm rows and the lock's release all happen together:

Step 3: syncing the policy

The server replaces Restore with a more general Sync: reload the totals and the pending counts from the store and put both into the policy. It runs once at startup and then on a timer:

Two design points. The store is the source of truth and Sync replaces the policy's state rather than adding to it, which sidesteps the idempotence problem: syncing twice is the same as syncing once. And Sync does not stop the world. A reward handled between the read and the restore may be applied twice for one interval, and the next sync corrects it; the doc comment says so, because a reader debugging a count that is briefly off by one should be able to find out why.

If the store is unreachable, SyncLoop logs a warning and the replica keeps serving from what it has. Stale answers are better than none for a bandit, where a slightly out-of-date choice costs a little regret.

The rest is plumbing: a flag and environment variable for the interval (default off, with a warning at startup if a database is configured but syncing is not), a replica name in logs and /stats so you can tell instances apart, and the loop started next to the expiry loop:

Sync does not need to be fast, and its cost should be weighed against the price of staleness. Every replica runs two small queries each interval; with a handful of replicas that is nothing, and with hundreds, chapter 13's aggregator (which reads once and publishes to everyone) is the better design.

Step 4: rewards in flight

Chapter 8 ended with a puzzle: with UCB1, several selections in a row return the same arm, because a selection changes nothing and only a reward does. With one replica and a slow reward that is a curiosity. With three replicas and thousands of users per second it becomes a stampede, because between two rewards there are hundreds of requests, and all of them get the same answer. Only the first request of a burst should do the exploring.

The fix is to let a selection count as a pending observation. UCB1 chooses the arm with the highest mean + sqrt(2 ln t / n), where n is how often the arm was pulled and t the total. Treat the outstanding selections as if they had already happened, for the exploration term only. Both n and t include pending selections, so an arm that was just chosen looks better explored, its bonus shrinks, and the next request goes elsewhere. The mean is untouched, because there is no reward to average yet. When the reward arrives (or the selection is abandoned) the pending count drops and the real observation takes its place.

Things to notice in that code:

  • Select now changes state: it reserves a pending slot on the arm it picks. So does an unrewarded selection that the server later discards, which is why there is an Abandon method, called when recording the selection fails or when a selection expires without a reward being learned from.
  • The pending count is not part of the durable state. It is derived from the store (PendingCounts), and SetPending is how a sync installs it.
  • release only decrements when the count is positive. A reward for a selection made before a restart, or on another replica, arrives without a slot to release here; going negative would corrupt the exploration term.
  • The old behaviour is still available as ucb1:naive, so the comparison below is reproducible.

A small interface lets the server and the Locked wrapper use these methods on policies that have them and ignore the rest, since Thompson sampling and epsilon-greedy are randomised and do not herd:

The chapter 8 test that documented the herding is replaced by its opposite: three selections without feedback now go to three different arms.

The bandit tests cover the mechanism directly: selections spread while rewards are outstanding (the aware policy picks arms 0, 1, 2, 3; the naive one picks arm 0 four times), the bonus shrinks as selections pile up, and updates and abandons release their slots:

The server also has to release the slot when it will never see the reward. Recording a selection can fail (the database is down); the reserved slot is released, or a long outage would slowly convince UCB1 that every arm has been sampled hundreds of times. Measuring delay

To see the effect you need a simulator that delays rewards. RunDelayed keeps a queue of observations the policy has not seen yet: the reward for step t reaches the policy after step t + delay has been selected. Run becomes the zero-delay case, and the old behaviour is unchanged:

The comparison harness gets a Delay field and banditsim compare a -delay flag:

First, a delay of 200 selections on the easy scenario (three arms at 0.2, 0.5 and 0.8), which is about 4% of the run:

Naive UCB1 loses more than twice as much regret as the pending-aware version. It spends the first 200 or so steps on the initial tour of the arms: it pulls arm 0, has no result, so tries arm 1 as "untried", and so on; each arm gets stuck being "untried" for 200 steps. (Its standard error is 0.0 because that behaviour is identical on every seed.) Thompson sampling is still best, as it was in chapter 4. For reference, with no delay the same four policies score about 62 (UCB1), 12 (Thompson) and 158 (epsilon-greedy) on this scenario, so the delay adds roughly 18, 54 and 49 to them. Thompson sampling takes the largest hit: it has fewer observations to sharpen its beliefs with, and it does not use the pending count. Pending-aware UCB1 pays the least.

The numbers get more dramatic as the delay grows relative to the run. On the needle scenario (nine arms at 0.1, one at 0.3), with a delay of 1,000 selections:

Naive UCB1's regret is exactly 1,000.0 (and the line is straight) because the tour of ten arms costs a delay's worth of steps per arm, so within 5,000 steps it never finds out which arm is good and never stops paying. The pending-aware version is at 414, and the randomised policies are lower still. That last gap is real: pending-awareness rescues UCB1 from a failure mode but does not make a deterministic policy as good as a randomised one when feedback is very late.

I considered a simpler fix, adding a little randomness to UCB1 ("UCB plus epsilon-greedy"). It would break the herding, but it charges every request forever for a problem that exists only while rewards are outstanding, it makes the policy nondeterministic in tests, and it hides the actual cause. The pending count deals with the cause.

Step 5: what staleness costs

Syncing more often costs database queries; syncing less often costs regret. How much regret? Run a simulation before building a load test, since a simulation is deterministic, fast, and lets you vary things a real deployment makes hard to vary.

The model: R replicas share one stream of requests, sent round-robin. Every reward is added to shared totals immediately (the database), but a replica's own policy sees other replicas' rewards only every interval selections, when every replica is rebuilt from the shared totals. An interval of 0 means never (each replica learns from its own third or quarter of the data); an interval of 1 is the same as a single policy.

The work is spread over the worker pool from chapter 7, one job per (policy, interval, seed). Because every run uses the seed it is given, the answer does not depend on how many workers there are. Tests check that syncing every step beats never syncing, that repeat runs match, and that bad input is rejected:

Two small outputs go with it: a CSV writer and a chart in the style of chapter 4, with the sync interval as a category on the x-axis. They are plain formatting code and are printed in full in the repository:

Four replicas, the easy scenario, 5,000 selections per run, 40 seeds:

Reading the table:

  • Never syncing is expensive for the policies that learn quickly. Thompson sampling with four uncoordinated replicas has 37 regret against 11 for one shared brain, more than three times as much. UCB1 goes from 62 to 171.
  • Most of the benefit comes early. Syncing every 100 selections (with 5,000 in total) gets Thompson to 15.5 and UCB1 to 66, close to the limit. Every 10 selections buys a little more; every selection buys almost nothing more. The cost of staleness is convex: a little syncing recovers most of the loss.
  • Epsilon-greedy barely notices. Its regret is dominated by the exploration it does on purpose, which no amount of information sharing removes. Staleness costs you most when your policy is good enough to exploit what it knows.

This is a model, not a measurement of your system. It assumes rewards are instant and requests alternate strictly between replicas. Real traffic adds reward delay (compare the numbers in step 4) and skew, and the two costs compound. The point of the simulation is to tell you which knob matters and by roughly how much before you tune it in production.

Step 6: the real thing

Last, run it for real. The load generator learns to talk to several replicas: -url takes a comma-separated list, and worker i talks to replica i mod n, like clients pinned to different instances:

The test starts three test servers and checks that each receives requests:

The demo script starts three banditd processes on ports 8091 to 8093, all using one PostgreSQL database (start a local one with tools/pg.sh start; chapter 10 explains it). It runs the same 4-second load twice, with syncing off and then with a 200 ms interval, and after each run prints what every replica believes next to what the database holds:

With syncing off, the replicas each know about a third of the traffic and disagree with the database. The load generator's own numbers show the cost: about 151 units of expected regret over roughly 5,700 selections, or 2.6% of a unit per selection. With a 200 ms sync interval every replica reports exactly the database's counts, and the regret is about 59 over roughly 4,900 selections, 1.2% per selection. The load generator and the servers share one machine and timing varies from run to run (the number of selections in four seconds differs between the runs), so trust the pattern, not the digits. The counts add up because of the properties in step 1.

Rewards spread over replicas is only half of the design. Reads still hit one replica each, and each replica's view is up to one interval old. That is the trade-off this chapter measures. Chapter 13 changes who does the merging, and chapter 14 puts a real load balancer in front.

Exercises

Starters and tests are in exercises/ch12.

1. The difference between two readings

Implement Delta(newer, older) in exercises/ch12/ex1: what was added to a set of per-arm totals between two readings. A replica that reports deltas rather than totals can be merged into shared state with Merge without ever being counted twice, which is how an aggregator can accept the same message twice. Reject readings where a count went down.

Reference answer

Subtraction is the inverse of the merge operation, which is what makes deltas useful. A count going down means the store was reset, not that data arrived, and silently returning a negative delta would corrupt the shared totals. Reporting that as ok == false forces the caller to decide.

2. Jitter the sync interval

Replicas started together and syncing every 10 seconds will query the database at the same instant, every time. Implement Jitter(interval, frac, r) in exercises/ch12/ex2, which returns the interval shifted randomly by up to frac of itself in either direction, using the random source it is given.

Reference answer

Taking the random source as a parameter is what makes the function testable: the tests seed it and check the range and the determinism. In SyncLoop you would replace the fixed ticker with a timer reset to Jitter(interval, 0.2, r) after each sync.

3. Round-robin without a lock

Implement Picker in exercises/ch12/ex3: Next() returns the replica URLs in rotation and must be safe to call from many goroutines at once. The tests run 8 goroutines with -race and check that every URL is returned exactly the same number of times.

Reference answer

As in chapter 11's sampler, one atomic add hands every caller its own sequence number, so the calls are spread exactly evenly however the goroutines interleave. The constructor copies the slice, so the caller changing its slice later cannot change the rotation.
